# releases/ — what belongs here

## Belongs here

- What ships in each release, and the status of its scope.
- Evidence that a release shipped: each deliverable's version, tag, commit and
  verification result.

## Does not belong here

| Instead of | Put it in |
| -- | -- |
| A story's text, acceptance, design or status | its feature under `specs/` |
| Why a choice was made | an ADR under `adr/` |
| How to run a release | `runbooks/` |

## File types

### Release index — `releases/index.md`

Purpose: lists every release, newest first, so a reader finds the current one without
opening each page.

Path and naming: `releases/index.md`, one per repository.

Belongs / does not belong: one line per release, linking to its page and naming its
status; no scope, decisions or progress detail, which stay on the release page.

Template:

```markdown
# Releases

<one paragraph: what this page is, and where each deliverable's version and tag are
recorded>

- [Release <n> — <title>](release-<n>/index.md) — <status>
```

### Release page — `releases/release-<n>/index.md`

Purpose: everything about one release — its scope, decisions, breaking changes,
progress and, once shipped, its evidence.

Path and naming: `release-<n>/index.md`. `release-<n>` is permanent; a release is cut
when there is scope to put on it, not ahead of time.

Belongs / does not belong:

- A feature belongs to one release at a time; that assignment lives only on the
  feature's own `Iteration` field ([specs/_structure.md](../specs/_structure.md)). The
  Scope table below is a generated region built from it — never hand-edited.
- Done work the release carries that predates the story taxonomy goes in a `### Done
  before this release` table under Scope: epic, what it delivered, and its implemented
  dates. This table is hand-maintained, outside the generated region.
- Commit subjects name the story or feature IDs they deliver, so the Commits section can
  be regenerated.

Template:

````markdown
# Release <n> — <Title>

| | |
| --- | --- |
| **Status** | planned \| in progress \| shipped |
| **Start Date** | <date>              <!-- optional -->
| **Finish Date** | <date>             <!-- required iff Status is shipped -->

<one-paragraph summary of what the release carries>
````

## Metadata and scope

- A release's metadata table carries `Status` (`planned`, `in progress` or `shipped` —
  ADO iterations have no state of their own, so this vocabulary stays release-specific
  rather than becoming `State`), `Start Date` (optional) and `Finish Date` (required
  iff `Status` is `shipped`). `docs/_update_board.sh` validates this shape.
- The `<!-- scope:start -->` … `<!-- scope:end -->` region is generated by
  `docs/_update_board.sh` from every feature whose `Iteration` points at this release,
  and must not be edited by hand. Its table shares its column shape with an epic's
  feature table: the feature first, linked to its file, then `Epic`, then `State`
  last (`specs/_structure.md`'s [IDs and state
  vocabulary](../specs/_structure.md#ids-and-state-vocabulary)).

## Tracker mapping

A migration maps a release page directly onto an Azure DevOps Iteration; see
[specs/_structure.md's Tracker mapping](../specs/_structure.md#tracker-mapping) for how
work items map. Field by field:

| Release page | ADO |
| -- | -- |
| `release-<n>` and its title | Iteration name under the Iteration Path |
| `Start Date` / `Finish Date` | Iteration dates |
| `Status`: planned, in progress, shipped | No field — ADO derives past, current and future from dates; `Status` is kept because releases close on scope, not a timebox |
| Generated Scope | An iteration query |
| Commits | Work item development links via `AB#<id>` |
| Entry and exit criteria, Decisions, Breaking changes, Progress, Shipped | The release page, which stays in the repo and is published as a code wiki |
| `releases/index.md` | The iteration list plus the code-wiki index |

## Lifecycle

1. Cut a release page when there is scope to put on it, not ahead of time.
1. Fill the sections the template gives, and run `docs/_update_board.sh` to fill
   the Scope region. List the release in `index.md`, newest first.
1. Add or remove scope by setting or clearing a feature's `Iteration` field, then
   re-run `docs/_update_board.sh`; a moved feature leaves one release's generated
   Scope table and joins another's.

A release is `shipped`, with its `Finish Date`, once its exit criteria hold.
