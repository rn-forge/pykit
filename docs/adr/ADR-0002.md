# ADR-0002: Code is placed by what its API contains, and boundaries are one-way

**Status:** accepted (2026-09-12) · **Scope:** every `rn-forge-*` package, existing and future

## Decision

These rules decide which package a module belongs in. The current package graph is architecture, not part of this decision: [workspace boundaries](../architecture/workspace.md) describes it, and the root `.importlinter` enforces it.

1. **Place by signature, not by caller.** A module's package is decided by what its API's signature contains, not by who calls it today. A lock or an atomic symlink carries no installer policy, so it lives in commons even while only developer tools call it.
2. **Protocols low, adapters beside their technology.** A protocol lives in the lowest package that can define it without an adapter dependency. A concrete adapter lives with the technology it integrates.
3. **Runtime never depends on tooling.** Runtime packages hold what a deployed application needs. Generic command-line and file-generating or installation layers sit on a separate branch that runtime packages never import. A generic layer carries no product policy: `rn-forge-cli` builds commands from a generic `[cli]` table, while lifecycle verbs, their `[lifecycle]` table and `build_tool_app` belong to `rn-forge-tooling`.
4. **Framework-free means framework-free.** A package that defines a framework-neutral contract imports no web framework, and sibling framework packages do not import each other.
5. **No compatibility re-exports, in any direction.** When a symbol crosses a package boundary, it moves; it is not aliased.

A new package states its place in the graph by these rules and adds its contracts to `.importlinter`. That does not change this record.

## Consequences

A deployed application can use runtime packages without the file-owning tooling layer, and a batch application using only `[cli]` does not import tooling. A new shared protocol cannot be dictated by its first implementation. Package dependency declarations and the import contracts must agree.

## Alternatives considered

One large runtime package would make CLI and file-writing dependencies available to services that do not need them. Compatibility re-exports would hide a move while letting imports point against the graph. Placing a module by its current callers put `DirectoryLock` and `atomic_symlink` in tooling in the first extraction; the development-layer review moved them to commons because nothing in their signatures is installer policy. A CLI-owned `[cli.lifecycle]` table mixed product policy into the generic parser and needed a string `target` to route to tooling; it was retired on 2026-09-22.
