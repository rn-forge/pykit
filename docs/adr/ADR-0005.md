# ADR-0005: Tooling owns lifecycle composition; cli stays generic

This decision defines where product lifecycle commands are declared and assembled. It guides authors of command-line tools and maintainers changing either package.

**Status:** accepted

**Recorded:** 2026-09-24

**Scope:** `rn-forge-cli`, `rn-forge-tooling`

**Implemented:** `1a8241b` (2026-09-22)

## Decision

`rn-forge-cli` reads the generic `[cli]` command declaration and builds a `CliApp`. `rn-forge-tooling` owns lifecycle verbs, their configuration, and the factory that mounts them on a `CliApp`. A tool declares lifecycle configuration in a sibling `[lifecycle]` table and calls `build_tool_app`. Tooling uses the CLI's public generic mounting API.

## Consequences

A batch application using only `[cli]` depends on `rn-forge-cli` without importing `rn-forge-tooling`. A tool opting into lifecycle commands declares that dependency in its own assembly code. The `[lifecycle]` table has `product`, optional `verbs`, and optional `namespace`; its current usage lives in the [tooling lifecycle guide](../rn-forge-tooling/guides/lifecycle.md).

## Influences

This decision shapes [E5 tool lifecycle](../specs/epics/E5-tool-lifecycle/index.md) and [E12 kiln acceptance](../specs/epics/E12-kiln-acceptance/index.md). [ADR-0001](ADR-0001.md) supplies the package boundary.

## Alternatives considered

The CLI-owned lifecycle declaration mixed product policy into the generic command parser. Its `target` field existed to route to tooling through a string. Generic `CliApp.add_typer` mounting lets tooling call its factory directly, so that indirection is unnecessary.
