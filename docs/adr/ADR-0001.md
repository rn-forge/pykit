# ADR-0001: Libraries follow explicit runtime and tooling boundaries

This decision defines where shared runtime code and developer tooling live. It guides maintainers adding packages, modules, or imports.

**Status:** accepted

**Recorded:** 2026-09-24

**Scope:** `rn-forge-commons`, `rn-forge-cli`, `rn-forge-tooling`, `rn-forge-web`, `rn-forge-django`, `rn-forge-fastapi`, `rn-forge-sqlalchemy`

## Decision

`rn-forge-commons` holds runtime-neutral mechanisms. `rn-forge-cli` defines the generic command-line surface. `rn-forge-tooling` owns file-generating and installation mechanics and depends on `rn-forge-cli`. `rn-forge-web` owns framework-free HTTP contracts and depends on `rn-forge-commons`.

`rn-forge-django`, `rn-forge-fastapi`, and `rn-forge-sqlalchemy` are independent consumers above `rn-forge-web`. Framework packages may use a direct commons dependency or an optional extra where needed. The root `.importlinter` file enforces the import direction and framework fences. Public symbols move to their owning package; compatibility re-exports do not cross a boundary.

## Consequences

A deployed application can use runtime packages without the file-owning tooling layer. Adding a shared protocol starts in the lowest package that can express it without a framework dependency. Package dependency declarations and the import contracts must agree.

## Influences

This decision shapes [E1 foundation and boundaries](../specs/epics/E1-foundation-and-boundaries/index.md), [E3 framework adapters](../specs/epics/E3-framework-adapters/index.md), and [E11 framework code generation](../specs/epics/E11-framework-codegen/index.md). [ADR-0004](ADR-0004.md) sets the HTTP and persistence boundary within the runtime graph.

## Alternatives considered

One large runtime package would make CLI and file-writing dependencies available to services that do not need them. Compatibility re-exports would hide a move while allowing imports to point against the graph. Both conflict with the explicit package boundaries.
