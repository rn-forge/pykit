# ADR-0004: Frameworks share HTTP contracts without sharing an ORM abstraction

This decision sets the boundary between framework-neutral HTTP behavior and persistence code. It guides maintainers extending Django, FastAPI, or SQLAlchemy support.

**Status:** accepted

**Recorded:** 2026-09-24

**Scope:** `rn-forge-web`, `rn-forge-django`, `rn-forge-fastapi`, `rn-forge-sqlalchemy`

## Decision

`rn-forge-web` owns shared HTTP types, behavior, and conformance cases. Django and FastAPI adapt those contracts through their native request, response, schema, and authentication hooks. Django keeps its ORM and `django-import-export` integration. `rn-forge-sqlalchemy` supplies async SQLAlchemy helpers for consumers that use that ORM. Shared wire behavior does not require a shared repository, serializer, or ORM model base.

Each adapter can choose a native persistence idiom while satisfying the same observable contract. The conformance cases cover the behavior they can observe; package guides state the concrete API for each stack.

## Consequences

An application can combine the HTTP contract with its stack's native model and query patterns. New cross-stack requirements enter `rn-forge-web` only when the contract itself is framework-neutral. Persistence helpers stay with the package that owns their technology.

## Influences

This decision shapes [E2 HTTP contract](../specs/epics/E2-http-contract/index.md), [E3 framework adapters](../specs/epics/E3-framework-adapters/index.md), and [E4 standards re-baseline](../specs/epics/E4-standards-rebaseline/index.md). [ADR-0001](ADR-0001.md) enforces the direction of imports.

## Alternatives considered

The web plan considered a common ORM or repository layer and a shared serializer abstraction. Those would replace framework-native interfaces without creating a shared wire guarantee. SQLAlchemy's remaining SQL idempotency, session, and readiness helpers stay [deferred](../specs/epics/E13-on-demand-features/index.md) until a consumer asks.
