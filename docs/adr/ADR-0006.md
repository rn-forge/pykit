# ADR-0006: pykit verifies tokens an authorization server issued and never issues its own; browsers hold a session, not a token

**Status:** accepted (2026-10-26) · **Scope:** authentication across all
`rn-forge-*` packages

## Decision

pykit is a relying party and a service provider, never an authorization server.

- **Tokens come from an authorization server.** An IdP or broker issues every
  token. pykit verifies the tokens its APIs accept and maps them to a
  `Principal` under the shared 401/403 contract. It mints no token of its own,
  including a short-lived one after a login.
- **Browsers hold a session.** A browser authenticates with a server-side
  session behind an HttpOnly cookie. The backend is the browser's only party
  to the protocol (the backend-for-frontend pattern), and tokens, assertions
  and secrets stay on the server.
- **The locally issued JWT flows are removed**, not kept beside the session.

## Consequences

- Machine clients, native apps and several APIs need a broker that issues
  tokens. pykit does not become one when a second client appears.
- Every application serves its SPA and API from one origin or one site, and
  protects unsafe methods with CSRF checks, because a cookie is sent
  automatically.
- Revocation, "sign out everywhere" and back-channel logout take effect on the
  next request, at the cost of server-side session storage shared by every
  worker.
- `rn-forge-django` loses its `jwt` extra and the views behind it, a breaking
  release ([F13.7](../specs/epics/E13-auth/F13.7-legacy-removal.md)).

## Influences

[E13's design](../specs/epics/E13-auth/design.md): its

[token validation](../specs/epics/E13-auth/design.md#token-validation) and

## Alternatives considered

- **Authorization-code and PKCE flows that end in a pykit-issued token.** Every
  application becomes an unaudited authorization server with its own key
  management, revocation and replay concerns. The existing exchange token is
  also a valid SimpleJWT refresh token, redeemable at SimpleJWT's refresh
  endpoint.
- **The SPA as a public OAuth client, holding tokens in memory.** Script in the
  page can still acquire new tokens, revocation waits for expiry, and SAML and
  social login would always need a broker. The design's
  [browser-client alternative](../specs/epics/E13-auth/design.md#the-browser-client-alternative)
  compares the two.
- **A token-mediating backend.** It still puts an access token within reach of
  script, and adds the backend login flow as well.
