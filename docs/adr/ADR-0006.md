# ADR-0006: Optional integrations stay behind explicit extras and import boundaries

This decision governs dependencies needed by only some consumers. It guides maintainers adding framework, storage, data, or authentication integrations.

**Status:** accepted

**Recorded:** 2026-09-24

**Scope:** All `rn-forge-*` packages and their optional integrations

## Decision

Keep situational dependencies in named package extras. Code that needs an extra lives in the module for that capability and stays outside the base facade where importing it would require the extra. A base package remains importable with its base dependencies. The package manifest declares extras; the root `.importlinter` file enforces the package and framework direction.

Protocols belong in the lowest package that can define them without an adapter dependency. Concrete adapters live beside the technology they integrate. Framework code generators, when built, stay in their framework `codegen` modules behind explicit extras and fences.

## Consequences

Consumers select capabilities through extras. Tests and documentation can name the dependency needed for each optional module. The unbuilt generator fences in `.importlinter` reserve a boundary; they do not claim that generators exist.

## Alternatives considered

Making every optional SDK a base dependency would burden consumers that never use it. Placing an adapter protocol inside its first implementation would let that implementation dictate the shared contract.
