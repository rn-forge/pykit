# ADR-0003: Standards and adopted frameworks precede pykit wrappers

This decision guides maintainers choosing between an existing library, a framework hook, and new pykit code. It applies across the HTTP adapters and shared runtime packages.

**Status:** accepted

**Recorded:** 2026-09-24

**Scope:** Cross-package API behavior and implementation choices

## Decision

Use published protocol standards for wire behavior. Use an adopted framework or a maintained library for a concern it already handles. Add pykit code where it supplies a missing contract, a small adapter, or configuration needed for the agreed wire behavior. Record a concrete reason when a candidate cannot meet the contract.

Both framework adapters must meet the shared status, header, and body rules. Their OpenAPI documents must accurately describe what each service sends. Textual identity between the two generators is not a goal; component naming and schema spelling may differ while the wire behavior remains the same.

## Consequences

The conformance table tests cross-stack behavior. An implementation may keep a focused wrapper where an evaluated library cannot provide the agreed contract. Framework-native extension points remain the first choice for adapter wiring.

## Influences

This decision shapes [E4 standards re-baseline](../specs/epics/E4-standards-rebaseline/index.md), [E6 consumer reuse](../specs/epics/E6-consumer-reuse/index.md), and [ADR-0004](ADR-0004.md).

## Alternatives considered

Normalizing generated OpenAPI text would require post-processing each framework's generator output. The standards review instead requires accurate documents and shared wire behavior. Replacing focused code with a library that cannot produce the agreed contract would add a dependency without removing the code.
