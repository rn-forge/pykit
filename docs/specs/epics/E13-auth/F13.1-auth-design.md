## Open questions

Each question carries the recommendation from 2026-09-27. A question closes when the owner accepts or replaces the recommendation.

- **Where do the protocol adapters live?** *Recommendation:* in `rn-forge-auth`, behind extras ([Package placement](design.md#package-placement)).
- **Which SAML library?** *Recommendation:* python3-saml. It is SP-focused with strict defaults and is already in use. pysaml2 is a full IdP and SP stack that is harder to configure, and both need `xmlsec1`. Revisit only if a required feature is missing.
- **FastAPI session store.** *Recommendation:* the `SessionStore` protocol with an in-memory store for tests and single-process development, and a Redis store behind the `redis` extra. Redis is the common production choice for server-side sessions. A SQL store waits until an application asks for one. Django keeps its own session framework.
- **FastAPI account model.** *Recommendation:* protocols only in the first version. A SQLAlchemy link table and default `AccountResolver` arrive when a FastAPI application with interactive users needs them.
- **Tokens held for upstream calls.** *Recommendation:* out of the first version. The OIDC adapter hands upstream tokens to an application hook and pykit does not store them.
- **Tenancy.** *Recommendation:* keep `Principal.tenant`, set by the authorization context provider. How a tenant is chosen at login, and multi-tenant row scoping through `ResourcePolicy`, wait until a second application states its tenancy model.
- **Django OIDC settings.** Does OIDC configuration go through a Django `AUTH.OIDC` settings block? *Recommendation:* decide with [Package placement](design.md#package-placement): the configuration belongs to `rn-forge-auth`'s Django binding, and a settings block waits until a second consumer needs OIDC configured through the settings facade.
- **Step-up authentication.** *Recommendation:* the first version records `auth_time` and `amr` in the session and on the `Principal`. A `Requirement` clause for recent or multi-factor authentication waits for an application that needs it.
- **Test IdPs.** *Recommendation:* in-process fake OIDC and SAML IdPs for unit and integration tests, so acceptance runs offline inside this repository ([ADR-0008](../../../adr/ADR-0008.md)). A Keycloak container covers the broker profile in an optional CI job.
- Should a SAML post-back establish a session, issue a JWT for later frontend requests, or support both? *Recommendation:* a session (see [Why the browser holds a session](design.md#why-the-browser-holds-a-session-and-not-a-token)). This closes when proposed decision 1 becomes an ADR.

The questions below come from [the browser-client alternative](design.md#the-browser-client-alternative) (added 2026-09-28). The first one decides the rest: under a browser client, most of them fall away or change shape.

- **How is the SPA an OAuth client: through a BFF, a token-mediating backend or the browser?** *Recommendation:* a BFF, as proposed decision 1 says. Every pykit application has a backend, and the IETF browser-based-apps guidance ranks the BFF first for exactly that case. A browser client would also force a broker for SAML and social login. The token-mediating backend is the weakest of the three for this pattern: it still puts an access token within reach of script, and it adds the whole backend login flow as well. Settling this also settles the SAML post-back question above.
- **Is the browser-client model a documented secondary profile?** Examples are an SPA with no backend of its own, or one that calls a pykit API on another site. *Recommendation:* not in the first version. The bearer path already serves machine clients and native apps, and nothing stops an SPA from using it. The reference pattern and ngkit's client describe the BFF only, and the docs say that an SPA on another site uses a proxy on its own origin ([Deployment topology](design.md#deployment-topology)).
- **What does the UI's authorization vocabulary look like?** The alternative reads `scope`, `roles` and `groups` from a token, and this design sends `permissions` and `roles` from `/auth/session`. *Recommendation:* permissions are the UI's unit, as they are the server's ([Authorization model](design.md#authorization-model)): `hasPermission` and `hasAnyPermission`, with `hasRole` for display only. Scopes limit delegated tokens and do not apply to a session, so the SPA has no `hasScope`.
- **What are the field names in the `/auth/session` body?** The sketch in [HTTP surface](design.md#http-surface) uses `auth_time` and `expires_at`, which breaks the camelCase wire rule (API conventions §8). The alternative names profile fields after the OIDC claims (`sub`, `picture`). *Recommendation:* the body is pykit's own resource, not an ID token, so it follows §8: `subject`, `name`, `email`, `picture`, `provider`, `roles`, `permissions`, `attributes`, `authTime`, `expiresAt`. Its values come from the standard claims, and `picture` is added.
- **What challenge does a 401 carry on a route authenticated by session cookie?** RFC 9110 §15.5.2 requires `WWW-Authenticate` on every 401, but cookie sessions have no registered scheme. *Recommendation:* a route that accepts both session and bearer callers sends the existing `Bearer` challenge, which is truthful because the route does accept a bearer token. A session-only route (the `/auth/*` routes) sends none and records the deviation in the API conventions. The SPA acts on the status alone.
- **How does the SPA avoid a login loop?** The alternative re-authenticates once on a 401. Under this design, a 401 starts a full-page login, which loops forever if the session cookie is never stored (a `SameSite` or `Secure` misconfiguration, or a proxy that strips `Set-Cookie`). *Recommendation:* add a loop guard to the [ngkit client contract](design.md#ngkit-client-contract). The client records when it started a login, in `sessionStorage`. A 401 within a short window after the return navigation goes to the SPA's error route with `?error=session_not_established` instead of starting another login.
- **What replaces a no-auth mode for demos and unit tests?** The alternative keeps an explicit switch, and this design rejects any switch in favor of the development provider. *Recommendation:* no runtime switch. Running applications and end-to-end tests use the development provider. Unit tests and component stories seed a session through a testing-only provider, for example `provideRnForgeAuthTesting(session)` from a testing entry point, which a production build does not import.
- **Which origins receive credentials?** The alternative attaches its token only to allowlisted URLs. With cookies, the browser decides by origin, and Angular's XSRF interceptor adds its header to same-origin relative URLs only. *Recommendation:* the first version supports same-origin deployment only on the ngkit side. The sibling-subdomain topology in [Deployment topology](design.md#deployment-topology) needs an ngkit interceptor that adds the XSRF header and `withCredentials` for an allowlist of API origins. It waits until an application needs that topology.
- **How does the SPA learn that a session is about to expire?** A browser client renews silently. A server session slides on activity and ends at its absolute timeout. *Recommendation:* `/auth/session` returns `expiresAt`, the absolute end. The SPA warns before it and offers a fresh login, and it does not poll to keep an idle session alive. An idle expiry surfaces as an ordinary 401.
