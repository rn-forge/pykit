Removed 2026-10-24: Release 6 carries E18 and E19 together, so
[F19.3](../E19-version-ranges/F19.3-internal-ranges.md)'s cut re-tags every
dependent once, on ranges, and owns this version table.

The release tags every package whose internal pins move, not only the two whose
code changes. A consumer can then take `rn-forge-commons` 0.7.0 beside any
other rn-forge package.

## Context

uv refuses two different direct URLs for one distribution. Every package that
requires `rn-forge-commons` still pins `rn-forge-commons-v0.5.0`, including
`rn-forge-cli` 0.1.0, which tooling requires. A consumer that pins
`rn-forge-commons-v0.7.0` and also takes cli, tooling, web, data, django,
fastapi or sqlalchemy at their current tags therefore fails to lock. This
includes kiln, which every generated repository carries as a development
dependency. Tagging commons 0.7.0 and tooling 0.3.0 alone would release
features no such consumer can install.

[E19](../E19-version-ranges/index.md) replaces exact pins with version ranges,
so this is the last release that re-tags dependents only to move a pin.

## Design

At the cut ([release runbook](../../../runbooks/releasing-packages.md),
*Restore tag pins*), these versions and pins:

| Package | Version | Pins it moves |
| -- | -- | -- |
| `rn-forge-commons` | 0.6.0 → 0.7.0 | — |
| `rn-forge-cli` | 0.1.0 → 0.1.1 | commons → v0.7.0 |
| `rn-forge-tooling` | 0.2.0 → 0.3.0 | commons → v0.7.0, cli → v0.1.1 |
| `rn-forge-web` | 0.2.0 → 0.2.1 | commons → v0.7.0 |
| `rn-forge-data` | 0.1.0 → 0.1.1 | commons → v0.7.0 |
| `rn-forge-sqlalchemy` | 0.2.0 → 0.2.1 | web → v0.2.1 |
| `rn-forge-django` | 0.5.0 → 0.5.1 | commons → v0.7.0, web → v0.2.1, data → v0.1.1 |
| `rn-forge-fastapi` | 0.3.1 → 0.3.2 | web → v0.2.1, data → v0.1.1 |

`rn-forge-devops` requires no rn-forge package and is not re-tagged. Each
package that only re-pins gets the changelog line *Changed: requires
`rn-forge-commons` 0.7.0* (and the other moved pins), under its version.

## Stories

### S18.5.1 — Re-pin and re-tag every dependent

**State:** Removed

**Acceptance:**

- Before the merge, no internal requirement in any `pyproject.toml` names a tag
  older than this release's for a package this release tags.
- After the tags exist, one fresh environment installs `rn-forge-tooling`,
  `rn-forge-django`, `rn-forge-fastapi`, `rn-forge-sqlalchemy` and
  `rn-forge-data[pandas]` together from their new tags, and imports each.

```bash
set -euo pipefail
absent() { local rc=0; rg -q --hidden --glob '!.git' "$@" </dev/null || rc=$?; [ "$rc" -eq 1 ]; }
absent 'rn-forge-commons-v0\.[56]\.0|rn-forge-cli-v0\.1\.0|rn-forge-web-v0\.2\.0|rn-forge-data-v0\.1\.0' \
  --glob 'packages/*/pyproject.toml'
tmp=$(mktemp -d); uv venv -q -p 3.14 "$tmp/venv"
git_url() { echo "$1 @ git+https://github.com/rn-forge/pykit@$2#subdirectory=packages/${1%%[*}"; }
VIRTUAL_ENV="$tmp/venv" uv pip install \
  "$(git_url rn-forge-tooling rn-forge-tooling-v0.3.0)" \
  "$(git_url rn-forge-django rn-forge-django-v0.5.1)" \
  "$(git_url rn-forge-fastapi rn-forge-fastapi-v0.3.2)" \
  "$(git_url rn-forge-sqlalchemy rn-forge-sqlalchemy-v0.2.1)" \
  "$(git_url 'rn-forge-data[pandas]' rn-forge-data-v0.1.1)"
"$tmp/venv/bin/python" -c 'import rn_forge.tooling, rn_forge.django, rn_forge.fastapi, rn_forge.sqlalchemy, rn_forge.data.pandas, rn_forge.commons.generation'
```
