# S25.2.1 — Profile XLSX transfer and choose an approach

Brief for
[S25.2.1](../F25.2-faster-xlsx-transfer.md#s2521-profile-xlsx-transfer-and-choose-an-approach),
at `502723d3`. This is a decision story: you profile, prototype and compare. The
owner decides; do not ship the change.

## Goal

At 100,000 rows × 10 columns, FastAPI XLSX export takes about 31 s and import
about 19 s, nearly all of it in the workbook write and load (S22.10.3 baseline,
[performance baselines](../../../../guides/performance-baselines.md), section
"9bcf9b0 S22.10.3 FastAPI transfer baseline"). Find where the time goes and
recommend an approach with a target time.

## Settled

- Export path: `rn_forge.fastapi._tabular` builds a `tablib.Dataset` and calls
  `rn_forge.data.write_xlsx`
  (`packages/rn-forge-data/src/rn_forge/data/excel.py`), which already uses an
  `openpyxl` write-only workbook and wraps every value in a `WriteOnlyCell`,
  formatted or not.
- Import path: `_tabular` calls `tablib.Dataset().load(raw, format="xlsx")`,
  which uses openpyxl.
- The measurement harnesses exist: `packages/rn-forge-data/tests/measure/`
  (`test_excel.py`) and `packages/rn-forge-fastapi/tests/measure/`
  (`test_transfer.py`). Read their `conftest.py` and `test_contract.py`, and
  the baselines guide's description of how a measurement is collected, before
  measuring.
- The output must stay a valid `.xlsx` that round-trips the same values, and
  `column_formats` must keep working.

## Current behaviour

Re-measure the XLSX export and import cases at 10,000 and 100,000 rows on this
commit, the way the harness does, and record the numbers next to the S22.10.3
baseline. Then profile both paths at 100,000 rows (`cProfile` from a scratch
script run under `task`'s environment, or the harness's own profiling if it has
one) and record the top functions by cumulative time for each, split into
openpyxl XML writing/parsing, `WriteOnlyCell` creation, tablib, zip compression,
and our own code.

## Change

Prototype only, in scratch files outside `src/` (for example under
`packages/rn-forge-data/tests/measure/` as clearly named, uncollected scripts,
or in a temp directory). No change under `src/` and no dependency added to any
`pyproject.toml`; to try a library that is not installed, say so and estimate
from its documentation instead of installing it.

Compare at least these options on the same 100,000 × 10 data, with measured
times where they need no new dependency:

1. **Plain values when no format applies**: `write_xlsx` appends raw values and
   creates `WriteOnlyCell` only for formatted columns.
1. **lxml acceleration**: whether openpyxl picks up `lxml` here (check
   `openpyxl.LXML`), and the time with and without it. Adding it would be a
   new dependency.
1. **Import without tablib**: read with
   `openpyxl.load_workbook(read_only=True, data_only=True)` and
   `iter_rows(values_only=True)` directly, compared with tablib's load.
1. **Lower zip compression** for export, if openpyxl allows it, and its effect
   on file size.
1. **A different engine** (for example `xlsxwriter` for writing,
   `python-calamine` for reading): documented speed and licence, and what
   adopting it would mean for `write_xlsx`'s public behaviour. Do not install
   it.

For each option record: export and import time at 100,000 × 10, file size,
whether values and number formats round-trip, any public API change, and any new
dependency.

End with a recommendation, a target time at 100,000 × 10 for export and for
import, which packages change (`rn-forge-data`, `rn-forge-fastapi` or both), and
a draft settled contract for S25.2.2, so the owner can accept or amend it.
