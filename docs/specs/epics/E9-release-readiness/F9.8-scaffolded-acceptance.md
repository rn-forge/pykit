# F9.8 — Accept packages in scaffolded applications

**Status:** planned · **Owner:** pykit · **Epic:** [E9](index.md) · **Release:** [release-1](../../../releases/release-1/index.md)

**Depends on:** [ADR-0008](../../../adr/ADR-0008.md).

**Source:** `plans/archive/commons-upgrade-plan.md`, "D.9 — The acceptance ADR-0009 never had"; `plans/archive/fastapi-library-plan.md`, "Phase 8 — The golden-repo acceptance"; `plans/archive/plan-board.md`, "Downstream acceptance — kiln's work, not a pykit item".

Workspace tests import each package from source, beside every other package. They cannot show that a package works in an application that installs it the way a consumer does. Each story here scaffolds one kind of application in a temporary directory, installs the packages it needs from wheels built from the current commit, and exercises it. The application shapes are the ones pykit's packages are built for.

## Stories

### S9.8.1 — A command-line application

**Status:** planned

**Acceptance:** a scaffolded project declares its commands through `rn-forge-cli`, with no hand-written application construction. Installed from built `rn-forge-commons` and `rn-forge-cli` wheels, its console script runs a command, prints help, and maps an application error to its exit code.

### S9.8.2 — A tool with a lifecycle

**Status:** planned

**Acceptance:** a scaffolded tool declares a `[lifecycle]` table and builds its app with `rn_forge.tooling`'s `build_tool_app`. Installed from built wheels, with `$RNF_HOME` pointing at a temporary directory, it runs `install`, `status`, `upgrade` and `uninstall`, and each leaves the documented layout.

### S9.8.3 — A FastAPI service

**Status:** planned

**Acceptance:** a scaffolded service assembled with `rn-forge-fastapi`'s `FastApiApp`, installed from built wheels, passes every case in `rn_forge.web.conformance.CASES` over HTTP.

### S9.8.4 — A Django application

**Status:** planned

**Acceptance:** a scaffolded Django project using `rn-forge-django`, installed from built wheels with its `drf` extra, passes every case in `rn_forge.web.conformance.CASES` over HTTP.

## Acceptance

Each story is a test, so the feature's acceptance is that they run in CI and pass.

```bash
set -euo pipefail
uv run pytest -q -m scaffold    # S9.8.1–S9.8.4
```

## Design

- The tests share one helper that builds the needed wheels once per session and installs them into a fresh virtual environment under `tmp_path`, with no workspace source override. If it is generic enough, it belongs in `rn_forge.commons.testing`; otherwise it is a root `conftest.py` fixture.
- They carry a `scaffold` marker, registered at the root and in each package that uses it, because they are slower than unit tests. CI runs them in their own job.
- The `django-extras` CI job already builds wheels and installs them into a clean environment; reuse its approach rather than inventing another.
