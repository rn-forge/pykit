# F9.3 — Record the release mechanism

**Status:** in progress · **Owner:** pykit · **Epic:** [E9](index.md) · **Release:** [release-1](../../../releases/release-1/index.md)

**Depends on:** [ADR-0004](../../../adr/ADR-0004.md).

**Source:** `plans/reviews/docs-structure-review.md`, "F2 — Release scope and mechanics have no single accurate home" and "Open work register".

Historical plans describe a manual tag cut in dependency order: commons, cli, tooling, web, then the framework packages. CI does something else. On a push to `main`, each package's job in `_package-ci.yml` verifies the package, then creates and pushes its tag and a GitHub Release if the tag does not exist. All package jobs run in parallel from the same commit.

So the order of tags hardly matters: every tag points at the same commit, pushed within one run. The real risk is a **partial run**. If one package's job fails, packages that depend on it can still be tagged, and their manifests then pin a tag that does not exist. This applies to all seven package jobs once [F9.1](F9.1-sqlalchemy-ci.md) adds SQLAlchemy's.

## Stories

### S9.3.1 — Document current tagging

**Status:** done (2026-09-25)

**Acceptance:** the [release runbook](../../../runbooks/releasing-packages.md) states when CI tags, what it builds, what it does not enforce, and the order of steps a release follows.

### S9.3.2 — Decide how to handle a partial run

**Status:** done (2026-09-26)

**Acceptance:** the owner chooses how a partial run is prevented, and the runbook states the choice.

The owner chose two changes to the workflow. A failed package job blocks only the packages that depend on it, because each package job waits for its direct internal prerequisites' jobs. And CI runs only the packages a change affects: a package whose source changed, plus every package that depends on it, since each package's tests run against its prerequisites' workspace source.

### S9.3.3 — Scope CI jobs to changes and dependencies

**Status:** planned

**Acceptance:**

- A first job lists the packages whose files changed and adds every package that depends on one of them, read from the manifests' internal requirements. A `workflow_dispatch` run selects all seven.
- Each package job runs only when its package is in that list, and `needs:` the jobs of its direct internal prerequisites. It still runs when a prerequisite's job was skipped, and does not run when one failed.
- The `sonar` and `docs` jobs still run when some package jobs were skipped.
- A pull request that changes only `rn-forge-sqlalchemy` runs only its job; one that changes `rn-forge-commons` runs all seven, with web before django, fastapi and sqlalchemy.
- The [release runbook](../../../runbooks/releasing-packages.md) describes the scoping and the dependency order.

```bash
set -euo pipefail
grep -q '^  changes:' .github/workflows/main.yml
```

Not scriptable: the dependency edges between jobs and the two pull-request runs, which are observed in GitHub Actions.
