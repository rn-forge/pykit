# S23.2.1 — `install --ref` installs a commit of a GitHub repository

Brief for
[S23.2.1](../F23.2-install-from-a-ref.md#s2321-install-ref-installs-a-commit-of-a-github-repository),
at `79d0db5`.

## Goal

`install(product, ref=...)` and `<tool> install --ref <ref>` install the commit
a branch, a tag or a SHA names, from a GitHub repository with no release.
`state.json` records what was asked for and what was installed.

## Settled

Settled by the reviewer, 2026-11-17. This differs from the feature's Design in
one way: there is no new `GitHubRefs` class. `GitHubReleases` gains the two ref
methods, so every product that already declares a GitHub source can install a
ref without changing anything. The reviewer updates the feature's Design at
close; do not edit it.

- **`GitHubReleases`** (`install/release.py`) gains:

    - `resolve(ref: str) -> str`: `GET {api_url}/repos/{repo}/commits/{ref}`
      (URL-quote `ref` with `safe=""`), and return the response's `sha`, which
      must be 40 lowercase hex characters. An HTTP error (including 404), a
      network error, bad JSON or a malformed `sha` raises
      `AppException("Cannot resolve ref {!r} of {}: {}", ref, repo, error)`.
    - `download_commit(sha: str, destination: Path) -> Path`: fetch
      `{web_url}/{repo}/archive/{sha}.tar.gz` into
      `destination / f"{sha}.tar.gz"`, with the same error handling as
      `download`.

    `ReleaseSource` and `LocalArchive` are unchanged.

- **`lifecycle.install`** gains a keyword `ref: str | None = None`:

    - `version` and `ref` together raise `AppException`.
    - A ref needs a `GitHubReleases` source (the given `source`, or
      `product.source`). Any other source raises
      `AppException("{} cannot install a ref: its source is not a GitHub repository", product.name)`
      before anything is written.
    - `sha = source.resolve(ref)` runs before the lock, and so does the release's
      `latest()` today. The target (the version directory name) is `sha[:12]`.
    - `already-current` and `force` work as they do for a version.
    - Preparation downloads with `download_commit(sha, …)` and extracts with
      `extract_archive` into the same work layout `fetch_release` uses. There is
      no checksum, as for a generated tag tarball. Thread this through
      `_prepare` with the smallest change that keeps a release install's path as
      it is. A failed resolve or download leaves the home untouched.
    - `InstallResult.version` is the target, as for a release.

- **`state.json`** is written with four keys, always, by both install paths:

    - `version`: for a release install, the target, as today. For a ref install,
      `[project] version` from `<release_root>/pyproject.toml` (`tomllib`), or
      the target when that file or key is missing.
    - `ref`: for a ref install, the ref as given. For a release install, the tag:
      `source.tag_prefix + target` for a `GitHubReleases` source, and the target
      otherwise.
    - `commit`: the 40-character SHA for a ref install, and `null` for a release
      install.
    - `schema_version`: as today.

- **CLI** (`cli/lifecycle.py`, `install` verb): a `--ref` option ("Install a
  branch, tag or commit of the product's GitHub repository."). `--ref` with
  `--version` or `--archive` is `typer.BadParameter`, which exits 2.

- Reading the recorded `ref` and `commit` in `status`, `upgrade` and `doctor` is
  S23.2.2's job. This story does not change them.

- Changelog: `packages/rn-forge-tooling/CHANGELOG.md`, `[Unreleased]`,
  `### Added`: `install --ref` installs a branch, tag or commit of a GitHub
  repository, and `state.json` records `ref` and `commit`.

## Current behaviour

At `79d0db5`, `install` has no `ref` parameter, so each new lifecycle test fails
with `TypeError: install() got an unexpected keyword argument 'ref'`. The
`GitHubReleases.resolve` and `download_commit` tests fail with `AttributeError`.
The CLI test fails with exit 2 and "No such option: --ref". `state.json` holds
only `version` and `schema_version`.

There are no `GitHubReleases` tests today. `api_url` and `web_url` are fields,
so a fake server only needs a local URL.

## Change

1. `install/release.py`: `resolve`, `download_commit`, and docstrings.
1. `install/lifecycle.py`: `ref`, the ref preparation path, and the four-key
   `state.json`. Update `install`'s docstring (Args and Raises).
1. `cli/lifecycle.py`: `--ref`.
1. The changelog entry.

## Tests first

New fake: a `http.server.ThreadingHTTPServer` on `127.0.0.1:0`, in a thread,
started by a fixture. It serves:

- `/repos/o/r/commits/<ref>`, with `{"sha": "<40 hex>"}` for `main`, `v1.0.0`
  and that SHA itself, and 404 otherwise;
- `/o/r/archive/<sha>.tar.gz`, with a tarball holding one root directory whose
  tree is what the existing `Tool` product builds from, plus a
  `pyproject.toml` with `[project] version = "1.1.0.dev0"`.

Reuse the archive helpers `tests/install/test_lifecycle.py` already has. Put the
fake in that file, or in a `conftest.py` beside it if two files need it.

  `download_commit` writes the archive. `resolve` of an unknown ref raises
  `AppException` naming the ref.
- `TestRefInstall`:
    - `test_a_branch_installs_under_its_short_commit`: `versions/<sha[:12]>`
      exists, `current` points at it, and `state.json` is

    - `test_an_unknown_ref_leaves_the_home_untouched`: no `versions/`, no
      `state.json`.
    - `test_version_and_ref_together_are_rejected`.
    - `test_a_ref_needs_a_github_source` (a `FakeSource` product).
