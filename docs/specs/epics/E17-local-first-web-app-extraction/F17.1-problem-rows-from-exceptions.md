# F17.1 — Problem rows from an exception hierarchy

|  |  |
| -- | -- |
| **State** | New |
| **Parent** | [E17](index.md) |
| **Predecessors** | — |
| **Source** | Owner request, 2026-10-21 |

An application that raises its own exception hierarchy, each class carrying a
stable machine `code` and an HTTP `status_code`, registers one `ProblemType` per
class by hand and keeps the list in step with the classes. Apollo does exactly
that, and writes its own 5xx log function. This feature supplies both pieces,
plus a registry-guide recipe that keeps programming errors at 500. It touches
`rn-forge-web` and `rn-forge-fastapi`, and adds nothing to `rn-forge-commons`.

## Context

Entry criteria for adopting it: Apollo does not wait. Its rebuild writes
`problem_registry()` and the log function itself on today's pins
(`rn-forge-fastapi` 0.2.0, `rn-forge-web` 0.2.0, `rn-forge-commons` 0.5.0) and
deletes them after this ships and its pins move.

**The code travels as the problem `type`.** RFC 9457 makes `type` the problem's
machine-readable identifier, and the registry already derives it as
`type_base + slug`. `register_hierarchy` makes each class's `code` its slug, so
an application that sets `type_base` publishes the code with no extension
member. A relative base such as `/problems/` is enough. Without a `type_base`
the `type` is `about:blank` and the code does not reach the wire, so the guide
recipe sets one. Apollo's rebuild replaces its client's `error.code` envelope
with problem+json, so the client matches on `type` from the start.

## Design

**`ProblemRegistry.register_hierarchy`**, in `rn_forge.web.problem`:

```python
def register_hierarchy(
    self,
    base: type[Exception],
    *,
    code_attr: str = "code",
    status_attr: str = "status_code",
) -> Self: ...
```

It walks *base* and every subclass, base first and in `__subclasses__()` order,
and registers
`ProblemType(getattr(cls, code_attr), getattr(cls, status_attr), HTTPStatus(status).phrase)`
for each. A class missing either attribute everywhere in its MRO raises
`TypeError` at registration, naming the class and the attribute. The `code`
becomes the slug as written; the registry guide asks for hyphenated codes, like
every built-in row.

`__subclasses__()` sees only imported classes, so an application registers after
every module that declares part of the hierarchy is imported. The guide says so.

`problem_for` already walks the MRO, so a subclass row always resolves before
its parent's; registration order does not decide it. Registration order does
decide `problem_for_status`, which returns the first registered row with a
status, so walking the base first keeps the base's row the answer for a bare
status.

**Lookup errors stay 500: a guide recipe, not an API.** `default_registry()`
maps `LookupError` to `NOT_FOUND`, so a `KeyError` or `IndexError` from a bug
becomes a 404. The registry guide shows the two calls that prevent it:

```python
registry = (
    default_registry(type_base="/problems/")
    .register(KeyError, INTERNAL_ERROR)
    .register(IndexError, INTERNAL_ERROR)
)
```

They win over `LookupError` by MRO. The default stays: `rn-forge-fastapi`'s
soft-delete routes raise a bare `LookupError` for their 404s.

**A default 5xx log sink**, in `rn_forge.fastapi.problem`:

```python
def log_server_errors(logger: AppLogger | None = None) -> Log: ...
```

It returns a `Log` callable that, for `problem.server_error`, calls
`logger.error("{} | status={} | instance={} | trace_id={}", ...)` with
`exc_info=(type(exc), exc, exc.__traceback__)`, so the original traceback
reaches the log while the response body carries none. `AppConfig.log` stays
`None` by default; an application passes `log=log_server_errors()`. When
*logger* is `None` it uses `AppLogger.get_logger("rn_forge.fastapi.problem")`.

Prior art: Apollo's domain error hierarchy and its `problem_registry()`;
Apollo's exception handlers, which log 5xx responses with the traceback and
request context.

**Tests:** `register_hierarchy` over a three-level hierarchy resolves each class
to its own row, and a subclass that overrides `status_code` resolves to its own;
a class with no `code`, and one with no `status_code`, each raise `TypeError`;
`problem_for_status` returns the base's row; with `type_base` set, a 4xx body's
`type` ends in the raising class's code; the recipe turns a `KeyError` into 500
and leaves a plain `LookupError` at 404; `log_server_errors` records one event
whose `exc_info` traceback names the raising frame, and records nothing for a
4xx.

## Stories

### S17.1.1 — Register a hierarchy

**State:** New

**Acceptance:**

- `ProblemRegistry.register_hierarchy` behaves as under *Design*, with the tests
  listed there.
- It is exported from `rn_forge.web` and documented in the registry guide, with
  a `type_base` and the import-order note.
- `uv run pyright` and `uv run lint-imports` pass.

### S17.1.2 — Document keeping programming errors at 500

**State:** New

**Acceptance:**

- The registry guide carries the recipe under *Design* and names the
  `ValueError` → 422 default it leaves alone.
- A test proves the recipe's behaviour; `default_registry` is unchanged.

### S17.1.3 — Log 5xx problems with their traceback

**State:** New

**Acceptance:**

- `rn_forge.fastapi.log_server_errors` exists and is passed to `AppConfig.log`
  in a test application; a raising route produces one log record carrying the
  original traceback.
- `AppConfig.log` still defaults to `None`.
- The package site builds with `--strict`.

## Considered and rejected

- **A `CodedException` base publishing a `code` extension member.** With
  `type_base` set the `type` already carries the code, so the member repeats it,
  and the exception would hold a second code beside `AppException.error_code`.
- **`AppException` implements `HasProblemExtensions` by default.**
  `HasProblemExtensions` states that `error_data` is never published
  automatically because it routinely carries credentials and internal
  identifiers. Every `rn-forge-*` package raises `AppException`, so a default
  would put that data on the wire for all of them.
- **A `default_registry(programming_errors_are_500=...)` keyword.** It stands in
  for two `register` calls; the recipe is enough.
- **Normalising `_` to `-` in codes.** The code is the slug as written; Apollo
  renames its codes to hyphens.
- **Registering classes in reverse, subclasses first.** The MRO walk makes order
  irrelevant to `problem_for`; base-first order only matters to
  `problem_for_status`.
