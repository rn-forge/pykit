# F17.4 — SQLite engine and embedded migrations

|  |  |
| -- | -- |
| **State** | New |
| **Parent** | [E17](index.md) |
| **Predecessors** | — |
| **Source** | Owner request, 2026-10-21 |

A local-first application keeps its operational state in one SQLite file. Every
such application sets the same connection pragmas by hand (write-ahead logging,
foreign keys, a busy timeout) and runs its Alembic migrations from inside the
process at startup. Apollo wrote both. This feature adds them to
`rn-forge-sqlalchemy`, which today has models, upsert and keyset pagination but
no engine or migration helper.

## Context

Apollo does not wait for it; it keeps its own engine and migration code on
today's pins and adopts these helpers after release and a pin bump.

**Async only, like the rest of the package.** `rn-forge-sqlalchemy` works
through `AsyncSession` only, and an application behind FastAPI should too.
Apollo's synchronous engine serves only its threaded job worker. Its beets
library is not SQLAlchemy at all: beets keeps its own sqlite3 connection behind
[F17.2](F17.2-thread-actor.md)'s actor. The rebuild moves the worker and its
routers to `AsyncSession`, so no synchronous engine is needed, and none is
offered.

**A dependency outside this repository.** An application generated by kiln
can take `rn-forge-sqlalchemy` only once kiln's `rn-forge-deps` rule admits it
for `python-web-app`. Apollo's rebuild plan raises that as a kiln follow-up;
kiln already pins `rn-forge-sqlalchemy-v0.2.0`. Adoption waits on it.

## Design

**Two modules in `rn_forge.sqlalchemy`.** `rn_forge/sqlalchemy/sqlite.py`,
re-exported from the facade:

```python
def create_sqlite_engine(
    path: str | Path,
    *,
    wal: bool = True,
    busy_timeout_ms: int = 5000,
    foreign_keys: bool = True,
    synchronous: str = "NORMAL",
) -> AsyncEngine: ...
```

1. It creates *path*'s parent directory and builds an `AsyncEngine` for
   `sqlite+aiosqlite:///{path}`. The application declares `aiosqlite`; the
   package still declares no driver.
1. A `connect` listener on `engine.sync_engine` issues `PRAGMA
   journal_mode=WAL` when *wal* is true, `PRAGMA synchronous`, `PRAGMA
   foreign_keys=ON` when *foreign_keys* is true, and `PRAGMA busy_timeout`.
1. `path=":memory:"` is accepted for tests. It skips the directory step and
   WAL, and uses `StaticPool`, so every session sees the same database; with a
   per-connection pool each connection would open its own empty one.
1. The helper never creates tables; schema is the migrations' job.

`rn_forge/sqlalchemy/migrate.py`, behind a new `migrations` extra that adds
`alembic`:

```python
def run_migrations(
    script_location: str | Path,
    db_url: str,
    *,
    alembic_ini: str | Path | None = None,
    revision: str = "head",
) -> None: ...
```

It builds an Alembic `Config` (from *alembic_ini* when given, else an empty
one), sets `script_location` and `sqlalchemy.url`, sets
`config.attributes["configure_logger"] = False` so the application's own logging
is not reconfigured, and calls `command.upgrade(config, revision)`. A failure
propagates unchanged. Importing `rn_forge.sqlalchemy.migrate` without the extra
raises `ImportError`; it is not re-exported from the facade, per
[ADR-0003](../../../adr/ADR-0003.md).

`run_migrations` blocks. Alembic's async `env.py` template calls
`asyncio.run()`, which cannot run inside a running event loop, so an
application calls it from its lifespan as
`await asyncio.to_thread(run_migrations, ...)`. The guide shows that call, the
async `env.py` template with `render_as_batch=True` (SQLite cannot `ALTER` most
columns in place), and the package-resource form of `script_location`
(`"myapp:migrations"`), which keeps working once the application is installed
as a wheel.

Prior art: Apollo's SQLite session module and its embedded migration runner.

**Tests** (`packages/rn-forge-sqlalchemy/tests/`): a file engine reports
`journal_mode == "wal"`, `foreign_keys == 1` and the requested `busy_timeout`
through an `AsyncSession`; each flag set false leaves that pragma at SQLite's
default; the parent directory is created; a foreign-key violation raises when
enforcement is on; two sessions on a `:memory:` engine see the same table;
`run_migrations` over a temporary two-revision async script directory, called
through `asyncio.to_thread` from a running loop, reaches head on an empty
database and is a no-op the second time; a failing revision raises; it does not
reconfigure the root logger.

## Considered and rejected

- **A synchronous engine helper.** The package is async throughout, and its
  `upsert` and `keyset` take an `AsyncSession`, so a sync engine could not use
  them. `AsyncEngine.sync_engine` is no substitute: it runs on the async driver
  and raises `MissingGreenlet` outside SQLAlchemy's greenlet context, so it
  serves only as an event target.
- **Making `run_migrations` a coroutine.** Alembic's command API is
  synchronous; a coroutine wrapper would hide the thread hop that the async
  `env.py` needs anyway.
- **Creating tables with `metadata.create_all`.** It would bypass the migration
  history the application relies on.
