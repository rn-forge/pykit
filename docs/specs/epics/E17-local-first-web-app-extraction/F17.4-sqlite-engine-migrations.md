A local-first application keeps its operational state in one SQLite file, sets
the same connection pragmas by hand and runs its Alembic migrations from inside
the process at startup. Apollo wrote both, and this feature added them to
`rn-forge-sqlalchemy`.

**Outcome:** `create_sqlite_engine` and `run_migrations` (behind the
`migrations` extra) shipped on 2026-10-31. They are documented in the
`rn-forge-sqlalchemy` usage guide (`docs/guides/usage.md`, *SQLite engine* and
*Embedded migrations*).

## Context

Apollo does not wait for it; it keeps its own engine and migration code on
today's pins and adopts these helpers after release and a pin bump.

**Async only, like the rest of the package.** `rn-forge-sqlalchemy` works
through `AsyncSession` only, and an application behind FastAPI should too.
Apollo's synchronous engine serves only its threaded job worker. Its beets
library is not SQLAlchemy at all: beets keeps its own sqlite3 connection behind
[F17.2](F17.2-thread-actor.md)'s actor. The rebuild moves the worker and its
routers to `AsyncSession`, so no synchronous engine is needed, and none is
offered.

**A dependency outside this repository.** An application generated by kiln can
take `rn-forge-sqlalchemy` only once kiln's `rn-forge-deps` rule admits it for
`python-web-app`. Apollo's rebuild plan raises that as a kiln follow-up; kiln
already pins `rn-forge-sqlalchemy-v0.2.0`. Adoption waits on it.

## Design

`create_sqlite_engine` lives in `rn_forge.sqlalchemy.sqlite`, re-exported from
the facade, and never creates tables because schema is the migrations' job.
`run_migrations` lives in `rn_forge.sqlalchemy.migrate` behind the `migrations`
extra and is not re-exported ([ADR-0003](../../../adr/ADR-0003.md)). It blocks,
because Alembic's async `env.py` template calls `asyncio.run()`, which cannot
run inside a running event loop; an application calls it through
`asyncio.to_thread` from its lifespan. Prior art is Apollo's SQLite session
module and its embedded migration runner.

## Considered and rejected

- **A synchronous engine helper.** The package is async throughout, and its
  `upsert` and `keyset` take an `AsyncSession`, so a sync engine could not use
  them. `AsyncEngine.sync_engine` is no substitute: it runs on the async
  driver and raises `MissingGreenlet` outside SQLAlchemy's greenlet context,
  so it serves only as an event target.
- **Making `run_migrations` a coroutine.** Alembic's command API is synchronous;
  a coroutine wrapper would hide the thread hop that the async `env.py` needs
  anyway.
- **Creating tables with `metadata.create_all`.** It would bypass the migration
  history the application relies on.
