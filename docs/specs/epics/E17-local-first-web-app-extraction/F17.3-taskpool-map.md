# F17.3 — `TaskPool.map_settled`

|  |  |
| -- | -- |
| **State** | New |
| **Parent** | [E17](index.md) |
| **Predecessors** | — |
| **Source** | Owner request, 2026-10-21 |

`TaskPool` runs `Task` objects: subclass, name, props. Fanning one plain
function over many items, capturing each item's failure instead of aborting the
sweep, needs an adapter class and a per-item task name. Apollo wrote that
adapter for its file scans, plus a bounded worker count and a batching helper.
This feature gives `TaskPool` a `map_settled` method so no adapter is needed;
the worker count and batching stay out.

## Context

Apollo does not wait for it; its adapter stays until it adopts the released
method.

## Design

```python
@dataclass(frozen=True)
class Succeeded[T]:
    value: T

@dataclass(frozen=True)
class Failed:
    error: Exception

type Settled[T] = Succeeded[T] | Failed

class TaskPool[TaskType: Task]:
    def map_settled[I, T](
        self,
        fn: Callable[[I], T],
        items: Iterable[I],
    ) -> list[Settled[T]]: ...
```

1. **`map_settled` submits `fn(item)` for every item to the pool's executor
   and waits for all of them.** It returns one `Succeeded` or `Failed` per
   input, in input order, so `isinstance` or `match` narrows each result and a
   `None` value is a valid success. It raises nothing for an item failure and
   logs it at the same level as a failed `Task`, naming the item's index. The
   name differs from `Executor.map`, which is lazy and raises the first
   error.
1. **No `Task` is created.** `map_settled` works on the executor directly, so it needs
   no name and does not touch `TaskPool.tasks` or the duplicate-name check. It
   may be called more than once on one pool; it raises `AppException` after
   `shutdown`, like `submit`.
1. **`TaskPool.__init__` is unchanged.** The caller sizes the pool. The tasks
   guide says how to choose `max_workers` for work bound by subprocesses or
   I/O rather than by the CPU.
1. **Batching is not added.** `itertools.batched` covers it on Python 3.14.

Prior art: Apollo's per-file fan-out helper, whose `Task` adapter exists only
because `TaskPool` takes `Task` objects.

**Tests** (`tests/runtime/test_tasks.py`): results come back in input order when
later items finish first; an item that raises is captured as `(None, exc)` and
the rest still run; an empty input returns `[]`; a `None` return is a `Succeeded(None)`; no more than the pool's
`max_workers` run at once; two calls on one pool both work; a call after
`shutdown` raises.

## Considered and rejected

- **A free function `map_tasks(fn, items)`.** It would own its pool, so a caller
  could not share a bounded pool across calls.
- **Raising an aggregate `AppException` on any failure.** That is what
  `shutdown(fail_on_error=True)` does; the point of `map` is that the caller
  decides per item.
- **A `batched` helper.** `itertools.batched` already exists.
- **A `bounded_workers` helper.** It is one `min()`, and its ceiling of 8 tunes
  Apollo's ffprobe workload; capping a thread pool by CPU count is wrong for
  I/O-bound work in general.
- **A `(value, error)` tuple result.** Pyright does not narrow `value` once the
  tuple is unpacked, so every caller would check `None` twice.
- **The name `map`.** It promises `Executor.map`'s lazy, raise-first
  behaviour.
