Some libraries must be created, used and closed on one thread: those that wrap a
SQLite connection (the beets music library, for one), and single-session SDKs.
Apollo serialised every call onto one dedicated owner thread; nothing in that
code is specific to the library it owns, so this feature added the generic
version to `rn-forge-commons`.

**Outcome:** `rn_forge.commons.ThreadActor` shipped on 2026-10-31. It is
documented in the `rn-forge-commons` processes and tasks guide
(`docs/guides/processes-and-tasks.md`, *Thread actor*) and its API reference.

## Context

Apollo does not wait for it; it keeps its own actor on today's pins and adopts
this one after release and a pin bump.

## Design

`ThreadActor` lives in `rn_forge.commons.runtime.actor` and is re-exported from
the `rn_forge.commons` facade. The rule never to hold the actor during a network
call or other long external work is guidance in the runtime guide, not a
docstring, because the kit cannot detect a violation. Prior art is Apollo's
library actor.

## Considered and rejected

- **A `ThreadPoolExecutor(max_workers=1)`.** It cannot run the factory and the
  teardown on the owner thread, and it gives no startup-error contract.
- **An `asyncio`-only actor on a task.** The wrapped library blocks, so the
  event loop would stall; a dedicated thread is the point.
