# F17.2 — Single-owner thread actor

|  |  |
| -- | -- |
| **State** | New |
| **Parent** | [E17](index.md) |
| **Predecessors** | — |
| **Source** | Owner request, 2026-10-21 |

Some libraries must be created, used and closed on one thread: those that wrap a
SQLite connection (the beets music library, for one), and single-session SDKs.
An async application cannot hand such an object to arbitrary worker threads.
Apollo serialises every call onto one dedicated owner thread through a queue and
exposes the result as a `Future` and as an awaitable. Nothing in that code is
specific to the library it owns except two lines of setup. This feature adds the
generic version to `rn-forge-commons`.

## Context

Apollo does not wait for it; it keeps its own actor on today's pins and adopts
this one after release and a pin bump.

## Design

**One module, `src/rn_forge/commons/runtime/actor.py`**, re-exported from the
`rn_forge.commons` facade:

```python
class ThreadActor[R]:
    def __init__(
        self,
        factory: Callable[[], R],
        *,
        name: str = "actor",
        startup_timeout: float = 30.0,
        close_timeout: float = 10.0,
        on_close: Callable[[R], None] | None = None,
    ) -> None: ...

    def submit[T](self, fn: Callable[[R], T]) -> Future[T]: ...
    async def run[T](self, fn: Callable[[R], T]) -> T: ...
    def close(self) -> None: ...
```

1. **`factory` runs on the owner thread**, so the resource is born on the thread
   that uses it. The constructor blocks until the factory returns.
1. **Startup failure propagates.** An exception from `factory` is re-raised from
   the constructor as `AppException` with the original as `__cause__`.
   Exceeding `startup_timeout` raises `AppException`. If `factory` returns
   after that, the owner thread passes the resource to `on_close` and exits
   without serving a call; it never waits on its queue.
1. **`submit`** queues `fn(resource)` and returns a `concurrent.futures.Future`.
   A call queued before `close()` still runs. A call after `close()` raises
   `AppException`. A cancelled future is skipped.
1. **`run`** is `await asyncio.wrap_future(self.submit(fn))`.
1. **`close`** queues a stop marker, joins the thread for at most
   `close_timeout`, and calls `on_close(resource)` on the owner thread after
   the last queued call. It is idempotent.

An exception, including `BaseException`, from `fn` is set on that call's future;
it never ends the loop.

**Guidance in the runtime guide, not in a docstring:** never hold the actor
during a network call or other long external work. Every other caller waits
behind it, so do that work outside the actor and pass the results in. When one
job touches many files, split it into three phases: work on the actor, a cheap
projection to plain data on the actor, then fan out off it
([F17.3](F17.3-taskpool-map.md)). The kit cannot detect a violation.

Prior art: Apollo's library actor, whose only library-specific code is its
startup lines.

**Tests** (`tests/runtime/test_actor.py`): every call runs on one thread, and
that thread is the one that ran `factory`; calls from one producer thread run
in the order it submitted them, while several producers submit concurrently; an exception in `fn`
reaches only its future and the next call still runs; a `factory` that raises
makes the constructor raise with the cause attached; a `factory` slower than
`startup_timeout` raises, and when it later returns its resource reaches
`on_close` and the owner thread ends; `run` awaited under `asyncio` does not block the loop;
`close` drains queued work, calls `on_close` on the owner thread, is idempotent,
and a later `submit` raises.

## Considered and rejected

- **A `ThreadPoolExecutor(max_workers=1)`.** It cannot run the factory and the
  teardown on the owner thread, and it gives no startup-error contract.
- **An `asyncio`-only actor on a task.** The wrapped library blocks, so the
  event loop would stall; a dedicated thread is the point.
