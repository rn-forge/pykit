# F14.3 — Generated board

| **Parent** | [E14](index.md) |

| **Predecessors** | — |

The board in `docs/specs/index.md` answers two questions: what ships in which release, and what is on no release yet. Today it also carries four hand-maintained epic groups (In progress, Elaborating, Deferred, Done) that repeat what the epic pages say, and a generated per-feature Backlog table that repeats the groups again. This feature replaces both with two generated sections, Releases and Backlog, built by one script from the epic and release pages. The rules:

1. **A feature carries its own assignment:** its `State`, and, on a release, its `Iteration` field. The board and each release's Scope table are derived from feature pages alone.
2. **Every non-Removed feature with no `Iteration` is in the Backlog**, never both there and on a release.
3. **Inconsistent specs fail the script**, so CI or a pre-commit hook can enforce the rules the structure docs today leave to a reviewer.

> This design record predates pykit's later migration to Azure DevOps state vocabulary (`State`: New/Active/Closed/Removed, `Iteration` in place of a hand-authored release Scope table). The sections below describe the script as it now works; the vocabulary is current even though the feature shipped under the old names.

## Design

### Script

- Path `docs/_update_board.sh`, renamed from `docs/_backlog.sh` (`git mv`). Keep it executable. Replace `/_backlog.sh` with `/_update_board.sh` in `exclude_docs` in `mkdocs.yml`.
- **POSIX `sh` and POSIX `awk` only** — no Python, `jq`, `gawk` extensions (`match()` with an array argument, `gensub`, `asort`) or bash-isms — so the script can be copied into a Node or Java repository with the same `docs/` layout. It must produce byte-identical output under macOS `/bin/sh` with BSD `awk`, and under `dash` with `gawk`.
- Usage: `_update_board.sh [--check] [DOCS_DIR]`. `DOCS_DIR` defaults to the script's own directory.
- Without `--check`: rewrite the generated region of `DOCS_DIR/specs/index.md`, then report validation errors.
- With `--check`: leave the file unchanged; also fail when the region differs from what would be written.
- Every error goes to stderr, prefixed `update_board: `, and makes the exit status 1. All errors are reported in one run; the script does not stop at the first.
- Keep the existing script's structure (temp dir, `trap`, `awk` programs reading the pages, `cmp` against the board) and its header comment style; rewrite the header to describe the new behaviour.

### Inputs

Every epic, feature and release page carries a metadata table directly after its
title: a two-column `| | |` table whose rows are `| **Key** | Value |`, in a fixed
key order per file type (`specs/_structure.md`, IDs and state vocabulary). The script reads this
table and validates its shape. Feature pages (`DOCS_DIR/specs/epics/*/F*.md`) are the
source of truth for the board and each release's Scope table.

**Epics** — each `DOCS_DIR/specs/epics/*/index.md`:

- Epic ID: the directory name up to the first `-` (`E12`); sort epics by the number.
- Epic title: the `# ` heading (`E12 — HTTP contract extensions`).
- Epic state: the metadata table's `State` row; its `Tags` row, when present, for the `deferred` tag.
- Entry criteria: the metadata table's `Entry criteria` row, when present.
- Feature rows: every table row whose first cell contains `F<n>.<m>`, used only to validate that a `State` column exists and no feature ID repeats across epic tables — the row's own state cell does not feed the board.

**Features** — each `DOCS_DIR/specs/epics/*/F*.md`:

- Feature ID: the file name up to the first `-` (`F14.1`).
- Feature state: the metadata table's `State` row; its `Tags` row for `deferred`; its `Iteration` row names the release it is scoped to (`release-2` from a link containing `release-2`).

**Releases** — each `DOCS_DIR/releases/*/index.md`:

- Release title: the `# ` heading. Release status: the metadata table's `Status`
  row, with its `Finish Date` row appended in parentheses when present (`shipped (2026-09-28)`).
- Scope: the `<!-- scope:start -->` … `<!-- scope:end -->` region under `## Scope` is generated, not read as input — it is written from every feature whose `Iteration` points at this release.
- Order: newest first, by the number in the directory name (`release-2` before `release-1`).

### Generated region

The script owns everything between `<!-- board:start -->` and `<!-- board:end -->` in `specs/index.md` (the markers replace today's `<!-- backlog:start/end -->`), and, since the later ADO migration, the `<!-- scope:start -->`/`<!-- scope:end -->` region on each release page. The intro above the board's region, and the retired-epic line, the ideas-list link and `## Conventions` below it, stay hand-written. The board region, as it is generated once F14.1 and F14.2 carry an `Iteration`:

```markdown
<!-- board:start -->
## Releases

| Release | Status | Features |
| --- | --- | --- |
| [Release 2 — workspace automation](../releases/release-2/index.md) | in progress | 1 Active · 1 New |
| [Release 1 — the first coordinated tags](../releases/release-1/index.md) | shipped (2026-09-28) | 9 Closed |

## Backlog

Features with no Iteration, by State and epic.

### New

| Epic | Features |
| --- | --- |
| [E12 — HTTP contract extensions](epics/E12-http-contract-extensions/index.md) | F12.12, [F12.14](epics/E12-http-contract-extensions/F12.14-merge-patch.md), [F12.15](epics/E12-http-contract-extensions/F12.15-fastapi-resource-operations.md), [F12.16](epics/E12-http-contract-extensions/F12.16-expose-content-disposition.md) |
| [E13 — Authentication and authorization](epics/E13-auth/index.md) | [F13.1](epics/E13-auth/F13.1-auth-design.md) |

### Deferred

| Epic | Features | Entry criteria |
| --- | --- | --- |
| [E6 — Consumer reuse](epics/E6-consumer-reuse/index.md) | [F6.1](epics/E6-consumer-reuse/F6.1-log-redaction.md), [F6.2](epics/E6-consumer-reuse/F6.2-sse.md) | the owner schedules either feature for a release. |
| [E7 — Azure adapters](epics/E7-azure-adapters/index.md) | F7.1, F7.2, F7.3, F7.4, F7.5, F7.6, F7.7, F7.8 | the owner schedules the package and settles its namespace. |
```

Rules for the region:

- **Releases.** One row per release page. `Status` is the release's own metadata value (`planned`/`in progress`/`shipped`, with its `Finish Date` in parentheses when present); it is not a work-item `State`. Features: the count of scoped features per `State`, joined with ` · ` in the order Active, New, Closed, Removed, zero counts omitted; `—` for an empty scope.
- **Backlog.** A feature is in the Backlog when its `State` is not `Removed` and it carries no `Iteration`. An epic with no feature rows and a `State` other than `Closed` or `Removed` is in the Backlog as itself, with `—` in Features.
- Sections, in this order, each rendered only when it has rows:
    - `### New` — untagged `New` features (and epics) with no `Iteration`. Columns `Epic | Features`.
    - `### Deferred` — features and epics tagged `deferred`. Columns `Epic | Features | Entry criteria`. The epic's entry criteria; `Per feature; see the epic.` when the epic's metadata table has no `Entry criteria` row.
- When the Backlog is empty, the line under `## Backlog` reads `Every feature is on a release or Removed.` and no sections follow.
- One row per epic in a section, sorted by epic number. Features in a cell sorted by feature number, joined with `, `. A feature with a file is a link whose text is the bare ID, its target rewritten relative to `specs/index.md` (`epics/<dir>/<file>`); a feature without a file is the bare ID.
- An epic label is its `# ` heading, linked to its `index.md`.

Each release page's `<!-- scope:start -->`/`<!-- scope:end -->` region holds a `| Feature | Epic | State |` table, one row per feature whose `Iteration` points at that release, sorted by feature ID, followed by a "generated by `docs/_update_board.sh`: do not edit" comment matching the board's own.

### Validation

Each of these is an error, in both modes:

| Check | Message names |
| --- | --- |
| A table with feature rows has no `State` column | the epic file |
| An epic or feature's `State` is not one of `New`, `Active`, `Closed`, `Removed` | the file and the value |
| A feature ID appears in two epic tables | the ID and both files |
| A feature's `Iteration` names no existing release page | the feature and the release |
| An `Active` feature carries no `Iteration` | the feature |
| `Closed Date` present without `State: Closed`, or missing when `State: Closed` | the file |
| `Entry criteria` present without a `deferred` tag, or missing with one | the file |
| A release's `Status: shipped` carries no `Finish Date` | the release |
| `specs/index.md` lacks either marker, or a release page lacks the `scope:start`/`scope:end` pair | the file |
| `--check` only: either generated region is out of date | the file and the command to run |

An `Active` feature with no `Iteration` is the only hard "needs a release" error; a `New`, untagged feature with no `Iteration` is not an error, only a Backlog entry.

### Documentation changes

- `docs/specs/index.md`: replace the `## Board` section (the four epic groups and the Done table) and the `## Backlog` section with the marker pair and its generated content. Keep the retired-epic line and the ideas-list sentence after `<!-- board:end -->`. Rewrite the intro's second sentence to say that Releases and Backlog are generated by `docs/_update_board.sh` and must not be edited by hand.
- `docs/specs/_structure.md`:
    - Replace "and `index.md`'s board lists each epic in exactly one group" with the rule that the board's Releases and Backlog sections, and each release's Scope table, are generated.
    - `Active` work carries an `Iteration`; say so in the state table.
    - In **Adding an epic or a feature**, replace step "Add the epic's row to the board … and run `task docs:nav`" with "Run `docs/_update_board.sh` and `task docs:nav`."
    - In **Working on and closing out work**, drop "and move the epic's board row" and "its board row moves to Done".
    - Replace the **The backlog table** paragraph with one for `_update_board.sh`: run it after changing a feature's `State` or `Iteration`; `--check` is the CI form.
- `docs/_structure.md`, **Keeping it honest**: remove the items the script now enforces — "A release names a feature that does not exist, a feature is on two release pages, or a planned feature is on none", "A feature's `**Status:**` differs from its row on its release page", and the "board row is in the wrong group, or in two" clause — and add one line: `docs/_update_board.sh --check` must pass.
- `docs/releases/_structure.md`: the Scope table becomes a generated region built from each feature's `Iteration`, replacing the hand-authored table and the status-mirror rule.
- Epic feature tables without a `State` column get one, placed after the ID column: `Closed` on every row of E1, E2, E3, E4 and E5; `New` (tagged `deferred` at the epic level) on every row of E7. Keep every other column.

**Out of scope.** Wiring `--check` into CI or a pre-commit hook; changing kiln's docs templates; resolving F14.1 and F14.2, which were on no release while this feature was built (the script reported them; the owner later scheduled both on release-2).
