## Context

The [manual CI run](https://github.com/rn-forge/pykit/actions/runs/37126506381) analyzed commit `66b1df139ff937b7f8aeea047639b70e4cd39617` on `feature/release-2`. Package checks passed, but the scanner's awaited quality gate failed and `ci-ok` failed, as F14.2 requires. Sonar displayed this feature-branch analysis under `main`.

The [summary](https://sonarcloud.io/summary/new_code?id=rn-forge_pykit&branch=main) reviewed on 2026-10-03 showed 109 open issues in a three-month new-code period. Security D and Reliability C failed their required A ratings; coverage 94.16% passed the 80% minimum, and duplication 0% passed the 3% maximum. Four vulnerability findings and three bug findings block those ratings. The remaining findings still belong to this feature: passing the gate alone does not complete it.

The count is a baseline observation, not a fixed assertion. Refresh the complete inventory before fixing code. `.sonar-cleanup/issues-2026-08-24.json` contains only four older findings and cannot stand in for the current backlog. Local temporary exports belong in the already ignored `.sonar-cleanup/`; neither tokens nor authenticated request headers belong in committed artifacts.

F14.2's remaining failed-push baseline, release recovery and next-main-run checks remain separate. This feature must preserve its fork guard, awaited gate, `ci-ok` aggregation and independent package release gating.

## Design

### Inventory and disposition

Use Sonar's issue search API or UI, selecting the correct project and branch explicitly. Export every page, not just the first 50 or 100 results. Inventory overall code, without a new-code-only filter, and include Open, Confirmed and Accepted findings; review existing False Positive dispositions separately for relevance. Inspect security hotspots separately if any are present.

For each issue record: issue key/link, rule ID, file and current line, message, severity/quality, status, affected symbol, proposed disposition, implementation story, and validation. Group by package and rule after collecting the full list. Read the official rule explanation and surrounding code before choosing a fix. Issue lines can move; locate the affected symbol rather than applying a stale line number mechanically.

Each baseline issue must end as fixed or as a justified false positive. Accepted valid debt does not count as resolved. For a false positive, explain the actual contract, why the rule does not apply and the existing or added test that proves it. Prepare exact reviewable Sonar comments and status changes; apply them only with owner authorization. A false-positive proposal alone does not complete acceptance. Do not weaken quality profiles, gate thresholds, the new-code period, or analysis scope to make findings disappear; do not add blanket exclusions or `NOSONAR` comments.

### Branch attribution

Change only the Sonar job's targeting inputs in `.github/workflows/main.yml`. Pass branch names through step environment variables, never interpolate untrusted branch text directly into executable shell code. Keep branch/PR parameters out of the shared `sonar-project.properties`.

| Event | Analysis target | Required behavior |
| --- | --- | --- |
| Push to `main` | Branch `main` | Explicit `sonar.branch.name=main` |
| Manual dispatch on a branch | That exact `github.ref_name` | Explicit `sonar.branch.name`; `feature/release-2` stays intact, including `/` |
| Same-repository PR | PR number/head/base | Preserve GitHub PR autodetection; pass no branch-analysis parameter |
| Fork PR | None | Preserve F14.2's skip without a token |
| Manual dispatch on a tag | None | Fail before scanning with a clear unsupported-ref message |

Use a small parameter-preparation step and pass its branch argument to the existing pinned scan action alongside the discovered sources/tests and `sonar.qualitygate.wait=true`. For PRs, emit an empty branch argument. If PR autodetection proves unreliable in the validation run, explicitly pass `sonar.pullrequest.key`, `.branch`, and `.base` from PR metadata together; never combine those with `sonar.branch.name`.

Before the first upload, verify that the Sonar project's configured main branch is `main`, that CI-based analysis is enabled, and that the organization plan supports branch/PR analysis. Public repository visibility alone does not establish its plan. Sonar's OSS plan supports branch and PR analysis; other plans have their own limits. If branch analysis is unavailable, stop that validation and record the exact limitation; do not upload feature code as `main` or silently skip the gate. Changing a subscription or project settings requires owner approval.

The observed misattribution is consistent with a manual dispatch missing branch parameters. Verify the fix using scanner parameters and the resulting server analysis, not just the displayed branch selector. A correctly targeted scan of real `main` is needed to restore its latest result; changing future scanner arguments does not move the earlier analysis into another branch. Do not delete history or rename `main` to the feature branch.

### Local feedback

Use SonarQube for IDE in connected mode for immediate rule feedback. A full SonarScanner CLI run can analyze the local working tree before commit/push, but requires network access and uploads code/results to SonarCloud. Its result uses the project's server rules and gate; it is not an offline lint command. Some checks, including taint analysis, need server analysis and cannot be certified by an IDE-only check.

Add `.github/scripts/sonar_local.py` using the Python standard library and existing planner functions. It accepts `--dry-run` and `--branch <name>`; the default target is the current Git branch. It must:

1. Resolve the repository root and operate there. Read workspace membership through `workspace_ci`; reuse `plan("")` outputs for `cov-args`, `test-paths`, `sonar-sources` and `sonar-tests`, rather than maintaining a package list.
2. Parse planner output as `key=value`; use `shlex.split` only for the planner's shell-quoted coverage/test arguments. Do not execute planner output using `eval`, `source` or `shell=True`.
3. Reject detached HEAD unless an explicit non-main branch is supplied. Reject `main` as a local upload target, including an explicit override. If `--branch` is supplied while on another named branch, require it to equal that branch; do not label unrelated source as a different branch. Allow dirty working trees for pre-push feedback and state that an uncommitted scan is not CI evidence for a commit.
4. In dry-run mode, print the target and exact test/scanner commands without requiring a token, running tests or uploading. In scan mode, require `SONAR_TOKEN` in the environment and an installed `sonar-scanner`; never print the token or pass it as a command-line argument. Do not install tools or dependencies automatically.
5. Run the same workspace-wide coverage command as CI: `uv run pytest <cov-args> --cov-report=xml:coverage.xml <test-paths>`. Stop on test failure. Regenerate coverage for every full scan, so stale coverage cannot qualify the gate.
6. Run `sonar-scanner` with `-Dsonar.host.url=https://sonarcloud.io`, discovered sources/tests, the explicit branch, `-Dsonar.qualitygate.wait=true`, and `-Dsonar.working.directory=.sonar-cleanup/scanner`. Use argument arrays and preserve scanner failure status. Reuse root properties for project, organization, Python version and coverage report path. Set the subprocess environment for local execution so inherited GitHub CI metadata cannot accidentally activate PR autodetection.

Document official scanner installation, owner-provided token setup and plan prerequisites in the development guide. Do not introduce a project dependency for the scanner. The intended commands, after implementation and toolchain setup, are:

```bash
python3 .github/scripts/sonar_local.py --dry-run
python3 .github/scripts/sonar_local.py
```

The second command uploads results and requires a non-main target with branch-analysis support. It may still take about a minute for analysis plus test time; the reviewed CI scan took about 59 seconds after coverage tests. Use narrow package checks between edits and full scans at meaningful batch boundaries.

### Known gate blockers

| Finding | Location at baseline | Implementation guidance |
| --- | --- | --- |
| [JWT signature](https://sonarcloud.io/project/issues?open=AaDlAlizQZe-aMZiDjQE&id=rn-forge_pykit) | `commons/integration/auth.py:257`, `JwtVerifier.verify` | The unverified header supplies `kid`/`alg`; the allowlist and subsequent `jwt.decode` verify the signature and registered claims before returning them. Review as a likely false positive; retain this security flow. Do not remove verification, broaden algorithms or authenticate from header contents. |
| [Sequence DDL](https://sonarcloud.io/project/issues?open=AaDlAlrLQZe-aMZiDjQc&id=rn-forge_pykit) | `django/models/sequences.py:79`, `next_value` | Interpolates `self.name` into `CREATE SEQUENCE`. Constructor validation exists, but the public attribute can be reassigned. |
| [Sequence DDL](https://sonarcloud.io/project/issues?open=AaDlAlrLQZe-aMZiDjQd&id=rn-forge_pykit) | `django/models/sequences.py:98`, `ensure_at_least` | Same mutable identifier boundary. |
| [Sequence query](https://sonarcloud.io/project/issues?open=AaDlAlrLQZe-aMZiDjQe&id=rn-forge_pykit) | `django/models/sequences.py:99`, `ensure_at_least` | Interpolates the table/sequence identifier for reading its state. |
| [Repeated expression](https://sonarcloud.io/project/issues?open=AaDlAlzQQZe-aMZiDjRF&id=rn-forge_pykit) | `tooling/tests/test_state.py:102`, `TestContentHash.test_of_deterministic` | Use independently specified expected SHA-256 output plus a repeated-call check. Preserve different-content and str/bytes coverage. |
| [Repeated expression](https://sonarcloud.io/project/issues?open=AaDlAlvcQZe-aMZiDjQm&id=rn-forge_pykit) | `web/tests/test_idempotency.py:36`, `test_hash_is_stable_across_calls` | Freeze an expected digest derived from the documented canonical body encoding; verify repeatability without duplicating the same expression inside one assertion. Preserve key-order and type distinction tests. |
| [Repeated expression](https://sonarcloud.io/project/issues?open=AaDlAlwNQZe-aMZiDjQr&id=rn-forge_pykit) | `web/tests/test_pagination.py:39`, `test_encoding_is_stable_for_the_same_input` | Check a known cursor encoding and its decoded value as well as repeated calls. Keep the wire format unchanged. |

For sequences, keep `name`'s existing public behavior and revalidate the current value immediately before each PostgreSQL identifier use. Quote with the active Django connection's `ops.quote_name` after validation; keep values bound in `nextval`/`setval`. Use the same safe path for both methods. Test constructor rejection, reassignment to an unsafe name, and existing PostgreSQL allocation/backfill behavior. Do not claim a real injection vulnerability solely from Sonar's label; report the actual reachable boundary and any remaining analyzer false positive separately.

For repeated calls, assigning the two results to variables only to disguise identical expressions is insufficient. The test must fail for a wrong but deterministic implementation; fixed expected values make that behavior observable.

### Remaining issue families

The first page reviewed includes these families; the complete inventory may add more. Apply the same per-issue triage to every later page.

| Family/examples | Fix boundaries |
| --- | --- |
| Async functions without awaits: FastAPI app/auth/problem handlers, web in-memory idempotency store | Inspect the framework/protocol contract. Do not convert required async exception handlers or async store methods to sync, and do not add dummy awaits. Use a justified false-positive disposition when required by the contract; convert only functions whose callers and contract permit it. |
| Keyboard interruption: CLI `app.py:89` | Read lifecycle and exit-code tests; preserve intended cancellation/cleanup behavior. Fix only if interruption is swallowed incorrectly; prove exit behavior before changing it. |
| `Worksheet.add_table` type: commons `data/excel.py:289` | Check the installed openpyxl API/type stubs and existing table tests. It receives an openpyxl `Table`; do not change a correct runtime argument to satisfy a misinferred type. |
| Cognitive complexity: commons `lang/collections.py`, sqlalchemy `upsert.py`, tooling generation `apply.py`/`plan.py` | Extract cohesive private helpers only where they reduce real branching. Preserve order, transactional behavior, exceptions and public signatures; run the corresponding test module. |
| Repeated literals: Django DRF transfer, tooling facade, web conformance cases | Introduce meaningful module constants or actual type aliases according to use. Do not turn type annotations into runtime string constants. Keep optional imports outside curated facades. |
| Multiple calls in exception tests | Move setup outside `pytest.raises`; leave the one operation expected to raise inside it. Preserve the tested error and message. |
| Composite assertions, unused parameters, generic syntax | Split independent assertions; distinguish public/protocol parameters from unused private ones; use Python 3.14 generic syntax only where behavior and typing remain equivalent. |

Read each package's README and relevant tests before editing it. Respect `CLAUDE.md`, strict Pyright, import contracts and test layout. Add regression tests for behavior changes; avoid tests that merely mirror cosmetic edits. Do not remove valid test coverage to silence Sonar. Public behavior changes require an explicit compatibility assessment; do not assume Release 2 is CI-only once package code changes.

**State:** New

**Acceptance:** pagination is exhausted; every baseline issue has a key, proposed disposition and implementation story; ledger totals reconcile with the export; the stale four-issue export is not used as the baseline.

### S14.4.2 — Correct CI branch and PR attribution

**State:** New

Implement the event matrix above; verify project prerequisites before uploading. Add narrow tests of parameter preparation with mocked event metadata/scanner calls, covering slash-containing branch names, main push, dispatch branch, dispatch tag, same-repository PR and fork PR. Run `actionlint`.

**Acceptance:** manual `feature/release-2` analysis appears under that exact branch and leaves main's latest analysis untouched; PR analysis is attached to the PR; main push targets main; tag dispatch fails before scanning; the fork guard and gate failure propagation remain intact. Restore main's latest result by analyzing actual main through the normal workflow, with owner authorization for any manual trigger.

### S14.4.3 — Repeatable local scan and development instructions

**State:** New

Implement `sonar_local.py` and the development-guide instructions above. Add subprocess-mocked tests in `.github/scripts/tests/test_sonar_local.py` for package discovery, shell-safe arguments, dry-run, missing scanner/token, branch safeguards, inherited CI metadata and failed tests/scanner. Use root pytest configuration; add no `tests/__init__.py`.

**Acceptance:** dry-run matches CI's discovered scope and coverage arguments; an authorized full local scan analyzes unpushed changes on the intended branch, imports fresh coverage and returns the real gate status. It never overwrites main or exposes a token. Ruff check/format, targeted helper tests and the strict docs build pass.

### S14.4.4 — Resolve security findings

**State:** New

Triage all security findings from S14.4.1, starting with JWT verification and the three sequence queries. Preserve signature, issuer, audience, expiry and algorithm checks. Implement identifier safety and test reassignment at the query boundary. Prepare evidence-backed false-positive dispositions where the remaining warning does not describe a defect.

**Acceptance:** relevant JWT and Django sequence tests pass, including PostgreSQL checks for SQL changes; no valid unresolved security finding remains in the baseline; every false-positive status has authorized review evidence. Sonar's security gate condition passes.

### S14.4.5 — Strengthen the three reliability tests

**State:** New

Replace the repeated-expression assertions according to the blocker table. Derive expected values independently from the existing format/algorithm; do not alter production output to fit new fixtures.

**Acceptance:** the three targeted tests detect incorrect deterministic results, retain repeatability coverage and pass with current contracts. A full scan resolves all three baseline bugs and passes the reliability gate condition.

### S14.4.6 — Resolve remaining package and test findings

**State:** New

Work through every remaining inventory entry, grouped by package/rule, using the family guidance above. Update the ledger after each batch. Validate the changed package with Ruff, strict type checks for source changes and its affected test modules; run PostgreSQL or scaffold checks only where their paths change. Update package docs when a contract changes.

**Acceptance:** every remaining baseline issue is fixed or an authorized justified false positive; no valid issue is hidden by acceptance, exclusion, weakened rules or lost tests. Package checks pass and all newly raised findings from the remediation are also resolved.

### S14.4.7 — Server verification and close-out

**State:** New

Regenerate workspace coverage, scan the remediation branch, reconcile server dispositions with the full ledger, and run CI for the final committed revision. After merge, validate actual main separately; a short-lived branch or PR's differential report cannot prove the entire main backlog is resolved.

**Acceptance:** final branch/PR CI and quality gate pass; main's scan identifies actual main's commit, passes the existing gate and has zero unresolved valid findings across overall code. Every baseline key is accounted for, all necessary false-positive dispositions have been applied with authorization, and no remediation-introduced valid finding remains. Record analysis links/revisions and checks; then close the stories, feature and generated release scope.
