# F12.14 — JSON Merge Patch

| | |
| --- | --- |
| **State** | New |
| **Parent** | [E12](index.md) |
| **Predecessors** | — |
| **Source** | Owner request, 2026-09-28 |

The [API conventions](../../../rn-forge-web/guides/api-conventions.md) already say `PATCH` is RFC 7396 JSON Merge Patch, but no package implements it. `rn-forge-django`'s only JSON parser accepts `application/json`, so DRF answers a merge-patch request with 415, and DRF's partial update does not treat `null` as "remove this field": it validates the `null` against the serializer field. `rn-forge-fastapi` has no `PATCH` helper at all, and a `pydantic.ValidationError` raised inside a route is not mapped to a 422: it reaches the catch-all handler as a 500. Every application therefore writes its own merge, and each gets `null`, nested objects or arrays slightly differently.

RFC 7396 in one paragraph: the body is a partial copy of the resource. A member that is present sets the field, an absent member leaves it alone, a `null` member removes it, objects merge recursively and arrays are replaced whole.

## Context

The trigger fired when a browser client's resource screen named the need: it sends `PATCH` with `Content-Type: application/merge-patch+json` and `If-Match`, and expects the server to accept that media type and apply RFC 7396 semantics. The client's work does not gate this feature or any release ([ADR-0008](../../../adr/ADR-0008.md)).

This feature adds a module to `rn-forge-web` and bindings to `rn-forge-django` and `rn-forge-fastapi`. It changes `BaseModelViewSet`'s `PATCH` media type, which is a breaking change for a client that sends `application/json` there (see *Release*, under *Design*).

## Design

**One implementation, in `rn-forge-web`** ([ADR-0005](../../../adr/ADR-0005.md)). What a merge patch means is the same on every stack, so the merge, the media-type constant and the two request failures (415, non-object body) live in `rn_forge.web` and import no framework. Each adapter supplies only what its framework needs and calls the shared functions: DRF a parser and a view mixin, FastAPI a dependency, a merge-and-validate helper and an OpenAPI fragment. Neither adapter reimplements the merge, and the conformance cases (S12.14.3) hold them to the same behavior.

**Merge on the writable representation, then validate the whole document.** The merge runs on the resource as the client would read it, and the merged document is validated as a full update. The merge never bypasses the serializer or the pydantic model. On Django the parser has already turned camelCase keys into snake_case, and `serializer.data` is snake_case too, so both sides of the merge use the same spelling. On FastAPI `merge_into` dumps by alias and the model validates by alias or name.

### Request order

Every stack evaluates a merge-patch request in this order, and the first failure answers:

| Step | Failure | Status |
| --- | --- | --- |
| 1. Media type is `application/merge-patch+json` | `UnsupportedMediaType`, with `Accept-Patch` | 415 |
| 2. Precondition (`If-Match`), when the resource is versioned | absent and required / malformed / stale | 428 / 400 / 412 |
| 3. Body is a JSON object | `InvalidMergePatch` | 422 |
| 4. Merged document validates | field errors with pointers | 422 |

The media type comes first because a body in the wrong language has no meaning to check. The precondition comes before the body, so a stale request is 412 whatever it says, and nothing is written.

### `null` on a declared field

RFC 7396 says a `null` member removes the member. A relational resource has a fixed set of fields, and a field cannot be absent from it, so pykit applies this rule at the top level of a resource: **a `null` member that names a field sets that field to `null`**. A nullable field stores `null`. A non-nullable field fails validation with a 422 whose pointer names the field and whose detail is `NULL_FIELD_DETAIL`. Below the top level, inside a JSON-valued field, RFC 7396 applies unchanged, and `null` removes the member.

This rule avoids a silent failure: DRF's full update skips a missing optional field instead of clearing it. If `null` only removed the member from the merged document, the stored value would not change. Nested serializers with a fixed schema are not special-cased. A `null` inside one removes the member, and the serializer then validates what is left.

### Read-only, server-owned and unknown members

These are ignored. A patch that names `id`, `version`, an audit field (`createTime`, `updatedBy`) or a field the resource does not have changes nothing, and the rest of the patch applies. This is DRF's behavior for read-only fields, and pydantic's default (`extra="ignore"`) for `WireModel`. It is also the least surprising behavior for a client that sends back a whole representation it read. A version sent in the body is still read by `enforce_version` as the precondition when there is no `If-Match`, as it is today.

### Media type per method

Only `PATCH` accepts `application/merge-patch+json`, and a merge-patch route's `PATCH` accepts nothing else. `PUT` and `POST` keep `application/json`. A route opts in: `BaseModelViewSet` on Django, `merge_patch_body()` on FastAPI. The conformance fixture's `/conformance/items` route is not a merge-patch route, so the existing `concurrency.*` cases keep sending `application/json`.

### The conformance fixture

Each driver serves `/conformance/documents/1`. It is created fresh for each case with this state, version 1, and `EntityVersionETagCodec`:

```json
{"id": "1", "name": "widget", "note": "fragile", "tags": ["a", "b"], "settings": {"color": "red", "size": "L"}}
```

`name` is a required string, `note` a nullable string, `tags` a list of strings, and `settings` a JSON object. On Django it is a `VersionedModelMixin` model under a `BaseModelViewSet`. On FastAPI it is an in-memory dict with a version counter, and a route that uses `require_if_match(codec=EntityVersionETagCodec())` and `merge_patch_body()` in that order. Unless a case says otherwise, requests carry `Content-Type: application/merge-patch+json` and no `If-Match`.

| Case id | Request body or change | Expect |
| --- | --- | --- |
| `patch.nested-merge-keeps-absent-members` | `{"settings": {"color": "blue"}}` | 200; `settings` is `{"color": "blue", "size": "L"}` and the other fields are unchanged; `ETag: W/"1:2"` |
| `patch.null-inside-a-json-value-removes-the-member` | `{"settings": {"size": null}}` | 200; `settings` is `{"color": "red"}` |
| `patch.null-sets-a-nullable-field-to-null` | `{"note": null}` | 200; `note` is `null` |
| `patch.array-is-replaced-whole` | `{"tags": ["c"]}` | 200; `tags` is `["c"]` |
| `patch.read-only-members-are-ignored` | `{"id": "99", "name": "gadget"}` | 200; `id` is `"1"`, `name` is `"gadget"` |
| `patch.null-on-a-non-nullable-field-is-422` | `{"name": null}` | 422 `validation-error`, detail `Validation Error`, `errors` `[{"pointer": "/name", "detail": "This field may not be null."}]` |
| `patch.non-object-body-is-422` | `["name"]` | 422 `validation-error`, detail `A merge patch must be a JSON object.` |
| `patch.json-content-type-is-415` | `{"name": "gadget"}` with `Content-Type: application/json` | 415 `unsupported-media-type`; `Accept-Patch: application/merge-patch+json` |
| `patch.stale-if-match-is-412` | `{"name": "gadget"}` with `If-Match: W/"1:9"` | 412, detail `Precondition failed: expected version 1, got 9` |
| `patch.failed-precondition-changes-nothing` | `GET /conformance/documents/1`, depends on the previous case | 200; the original state |

**Release.** All three packages gain a minor version. `rn-forge-web` releases first, and each adapter's minimum `rn-forge-web` version rises to the one that carries `merge_patch`. A `BaseModelViewSet` client that sends `application/json` on `PATCH` must switch to `application/merge-patch+json`. pykit has no consumers on release-1 yet, so no deprecation window is kept. F12.12's `RequestUtils` fix ships in the same `rn-forge-django` version.

## Stories

### S12.14.1 — Check for a maintained library

**State:** New

**Acceptance:** PyPI is searched for a maintained RFC 7396 implementation, per [ADR-0001](../../../adr/ADR-0001.md) rule 1, and the result is recorded under *Design*: either the package is adopted, with the owner's approval of the new dependency, or the reason to hand-roll is named. If one is adopted, S12.14.2's `apply_merge_patch` wraps it and the module docstring says so.

A first look on 2026-09-28, to be confirmed: `json-merge-patch` 0.3.0 (released 2025-03-25) describes itself against RFC 7386, which RFC 7396 obsoletes; `jsonmerge` implements a different, configurable merge; `jsonpatch` is RFC 6902, a different format. The RFC's algorithm is about ten lines, so a hand-rolled function under rule 1's third condition (the slice is a few lines and the candidate is far heavier or not clearly maintained) is the expected outcome.

### S12.14.2 — The framework-neutral merge in `rn-forge-web`

**State:** New

**Acceptance:**

- A new module `rn_forge.web.merge_patch` defines, and `rn_forge.web` re-exports:
  - `MERGE_PATCH_MEDIA_TYPE = "application/merge-patch+json"`;
  - `apply_merge_patch(target, patch)`, which follows RFC 7396 §2 exactly and mutates neither argument;
  - `merge_representation(current, patch)`, which applies [the top-level `null` rule](#null-on-a-declared-field) and then `apply_merge_patch` below the top level;
  - `require_patch_object(body)`, which returns *body* when it is a JSON object and raises `InvalidMergePatch` otherwise.
- `rn_forge.web.problem` gains `UNSUPPORTED_MEDIA_TYPE = ProblemType("unsupported-media-type", 415, "Unsupported Media Type")` and `NULL_FIELD_DETAIL = "This field may not be null."` (DRF's own wording, so both stacks already agree on it). Both are re-exported beside `CONTENT_TOO_LARGE` and `REQUIRED_FIELD_DETAIL`.
- `rn_forge.web.exceptions` gains two `WebError` subclasses, both registered in `default_registry()`:
  - `UnsupportedMediaType` maps to 415. Like `TooManyRequests`, it carries a `response_headers()` result, here `Accept-Patch: application/merge-patch+json` (RFC 5789 §2.2). Its detail is `Use Content-Type: application/merge-patch+json for PATCH`.
  - `InvalidMergePatch` maps to 422 with detail `A merge patch must be a JSON object.`, and has no `errors` member.
- `tests/test_merge_patch.py` runs every example in RFC 7396 Appendix A through `apply_merge_patch`. It also covers: nested merge; `null` removing a member that is absent (a no-op); array replacement; a scalar or list patch replacing the target (RFC §2); no mutation of either argument; `merge_representation` keeping a top-level `null` and still removing a nested one; and `require_patch_object` rejecting a list, a string and `null`.
- The module imports no web framework, and `uv run pyright` and `uv run lint-imports` pass.

### S12.14.3 — Conformance cases

**State:** New

**Acceptance:** `ConformanceArea` gains `"patch"`, and `rn_forge.web.conformance.CASES` gains the cases in [The conformance fixture](#the-conformance-fixture), with ids beginning `patch.`. Both framework drivers serve `/conformance/documents/1` and run every case with no skips. Each driver's `issue()` sends the case's own `Content-Type` for a JSON body, rather than forcing `application/json`.

### S12.14.4 — Django binding

**State:** New

**Acceptance:**

- `rn_forge.django.drf.casing` gains `MergePatchParser`, a `CamelCaseJSONParser` subclass whose `media_type` is `MERGE_PATCH_MEDIA_TYPE`. `rn_forge.django.drf` gains `MergePatchMixin` (in `views/mixins.py`), and both are re-exported from `rn_forge.django.drf`.
- `MergePatchMixin.get_parsers()` returns `[MergePatchParser()]` for `PATCH` only. For `PUT` and `POST` it keeps the view's other parsers and never includes the merge-patch parser.
- `MergePatchMixin.partial_update` runs in this order:
  1. It checks the media type before reading `request.data`. Any `PATCH` whose media type, ignoring parameters, is not `MERGE_PATCH_MEDIA_TYPE` raises `rn_forge.web.UnsupportedMediaType`.
  2. It calls `get_object()`.
  3. When the instance is a `VersionedModelMixin`, it calls `enforce_version(request, instance, required=self.merge_patch_requires_if_match, codec=self.etag_codec)`. Both class attributes default to `False` and `None`.
  4. It calls `require_patch_object(request.data)`.
  5. It calls `merge_representation(serializer.data, patch)`, where `serializer.data` is the current instance serialized.
  6. It validates the merged document with `get_serializer(instance, data=merged)`, a full update rather than `partial=True`, and saves it through `perform_update`.
  7. It answers 200 with the new representation, plus `ETag` from `etag_for` when the instance is versioned.
- `MergePatchMixin.retrieve` adds the same `ETag` header for a versioned instance. That makes the read-then-`If-Match` round trip work without view code.
- `BaseModelViewSet` includes `MergePatchMixin`.
- The generated OpenAPI document lists `application/merge-patch+json`, and only that, as the `PATCH` request body's content type for a `BaseModelViewSet`.
- `tests/drf/test_merge_patch.py` covers: each step's failure (415, 428 when required, 412, a non-object 422, a null on a non-nullable field 422); `PUT` refusing the merge-patch media type; the `ETag` on `retrieve` and `PATCH`; the audit fields still set by `perform_update`; and the OpenAPI content type. `tests/test_conformance.py` passes with the new cases.

### S12.14.5 — FastAPI binding

**State:** New

**Acceptance:**

- A new module `rn_forge.fastapi.merge_patch` holds three functions, all re-exported from `rn_forge.fastapi`:
  - `merge_patch_body()` returns a dependency. The dependency raises `UnsupportedMediaType` unless the request's media type, ignoring parameters, is `MERGE_PATCH_MEDIA_TYPE`. It then reads the JSON body and returns `require_patch_object(body)`.
  - `merge_into(model, current, patch)` dumps *current* through *model* (`model_validate(current, from_attributes=True).model_dump(by_alias=True, mode="json")`), applies `merge_representation`, and validates the result with *model*. On a `pydantic.ValidationError` it raises `fastapi.exceptions.RequestValidationError` with each `loc` prefixed by `"body"`, so the existing handler renders a 422 with RFC 6901 pointers. It never lets a `ValidationError` reach the catch-all handler.
  - `merge_patch_openapi()` returns the `openapi_extra` mapping that declares the request body as `application/merge-patch+json` with schema `{"type": "object"}`.
- `rn_forge.fastapi.problem._validation_errors` maps an entry whose `input` is `None` and whose `type` is not `missing` to `NULL_FIELD_DETAIL`, as it already maps `missing` to `REQUIRED_FIELD_DETAIL`.
- The route order is the same as Django's: media type, then `require_if_match` when the route uses it, then the object check, the merge and validation. `merge_patch_body` is declared after `require_if_match` in the route signature, which the test pins.
- `tests/test_merge_patch.py` covers each function and the ordering, and `tests/test_conformance.py` passes with the new cases.

## Considered and rejected

- **Rejecting read-only members with a 422.** This is the strictest option, but it breaks a client that sends back a representation it read. It also differs from DRF's and pydantic's defaults, so each adapter would need its own detection.
- **`null` on a field resets it to the column default.** Hard to predict, because the default can live on the model, the serializer or the database. It also differs between the two stacks.
- **`null` removes the member, as RFC 7396 says for documents.** On a fixed-schema resource, DRF's full update then skips the field, so the stored value silently stays.
- **Accepting `application/json` on `PATCH` as a merge patch.** The media type is how a client says which semantics it wants. RFC 5789 §2.2 has the server refuse a patch format it does not support, and name the ones it does in `Accept-Patch`.
- **JSON Patch (RFC 6902).** The API conventions chose merge patch. JSON Patch's operation list is harder for a form-based client to produce and gives no benefit for flat resources.
