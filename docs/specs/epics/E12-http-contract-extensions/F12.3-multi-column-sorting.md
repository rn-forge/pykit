AIP-132 lets `orderBy` name several fields (`team, score desc`). The API
conventions allow one and answer a second with 400, because the page token holds
one sort value. This feature lifts that limit on both stacks and in
`rn-forge-sqlalchemy`. The token holds one value per term, the keyset predicate
compares them in turn with mixed directions, and `null` values get one defined
place in the order, so a nullable field can be sorted on.

## Context

**Outcome:** the owner scheduled this feature for release 3 on 2026-10-04. The
keyset predicate stays in pykit: neither `sqlakeyset` nor DRF's
`CursorPagination` can carry the shared opaque token, for the reasons recorded
in `rn_forge.sqlalchemy.pagination` and `rn_forge.django.drf.pagination`.

## Design

### Wire rules

**Outcome:** the
[API conventions](../../../rn-forge-web/guides/api-conventions.md) §4 state the
rules: several `orderBy` terms, the key as tie-breaker, `null` last in both
directions, and a token bound to the whole order.

### The keyset predicate

**Outcome:** the predicate is the expanded OR-of-ANDs form, not a row-value
comparison, because that works with mixed directions and is portable across
SQLite, PostgreSQL and MySQL; the
[`rn-forge-sqlalchemy` pagination reference](../../../rn-forge-sqlalchemy/reference/pagination.md)
documents `keyset`'s contract.

### API changes

**Outcome:** `Cursor`, `encode_cursor` and `next_page_token` take one sort value
per term, a breaking change to `rn-forge-web` and `rn-forge-sqlalchemy` made
with no compatibility shim ([ADR-0002](../../../adr/ADR-0002.md)), and a token
issued before it is a 400. The
[pagination reference](../../../rn-forge-web/reference/pagination.md) lists the
current API.

### New conformance cases

**Outcome:** the cases are in `CASES`, documented in the
[conformance reference](../../../rn-forge-web/reference/conformance.md), and
`pagination.order-by-two-fields-is-400` is gone.

## Considered and rejected

- **Row-value comparison, `(a, b, id) > (x, y, z)`.** It is short, but it only
  works when every term has the same direction, and SQLite before 3.15 and
  some MySQL plans handle it poorly. The expanded form handles mixed
  directions everywhere.
- **The database's own null placement.** PostgreSQL puts nulls last ascending
  and first descending, while SQLite and MySQL do the opposite. One stack
  would then disagree with another on the same data, which §9's identical-wire
  rule forbids.
- **Nulls first in both directions, or nulls as the smallest value.** "Smallest"
  moves nulls to the top of a descending list, where a UI shows empty cells
  first. Last in both directions matches what spreadsheet and table UIs do.
- **A cap on the number of terms.** The endpoint's list of sortable fields
  already bounds it, and each field appears at most once.
- **Accepting old single-value tokens.** A token lives for one request, so a
  client holding one across a deploy retries from the first page. A
  dual-format decoder would outlive its use.
