# F12.3 — Multi-column sorting

| | |
| --- | --- |
| **State** | Active |
| **Parent** | [E12](index.md) |
| **Iteration** | [Release 3](../../../releases/release-3/index.md) |
| **Start Date** | 2026-10-04 |

| **Source** | Owner request, 2026-10-04 |

AIP-132 lets `orderBy` name several fields (`team, score desc`). The API conventions allow one and answer a second with 400, because the page token holds one sort value. This feature lifts that limit on both stacks and in `rn-forge-sqlalchemy`. The token holds one value per term, the keyset predicate compares them in turn with mixed directions, and `null` values get one defined place in the order, so a nullable field can be sorted on.

## Context

The owner started the ideation, which is this feature's trigger, on 2026-10-04 and scheduled it for release 3.

The keyset predicate is still written in pykit. Neither `sqlakeyset` nor DRF's own `CursorPagination` can carry the shared opaque token, for the reasons already recorded in `rn_forge.sqlalchemy.pagination` and `rn_forge.django.drf.pagination`. A multi-column predicate does not change that: both libraries would still need the token translated both ways.

## Design

### Wire rules

- **`orderBy` is a comma-separated list of terms**, each a field name optionally followed by `asc` or `desc` (AIP-132). Whitespace around a term is ignored.
- **Each field appears at most once.** A repeated field is 400, detail `orderBy names '{field}' more than once`. An empty term (`team,,score`, or a trailing comma) is the existing malformed-term 400.
- **An unlisted or malformed term is 400**, as today.
- **The primary key breaks ties.** It is appended as a final term, in the last term's direction, unless it is already a term. For a one-term `orderBy` this is today's order, so every existing `pagination.*` case keeps its expected items.
- **`null` sorts last, in both directions.** Whatever a database does by default, an `asc` or a `desc` term puts the rows whose value is `null` after the rows that have one. This is the order a UI table shows, and it is the same on every stack and every database. The rule that an `orderBy` field must not be null is removed.
- **The page token binds the whole order.** It holds one sort value per term, plus the key and the canonical `orderBy` (`team,score desc`). A token presented under another `orderBy` is 400 `pageToken does not match orderBy`. A token whose number of values does not match the terms is 400 `Malformed page token`.
- **Sort values keep their JSON type** in the token: string, number, boolean or `null`. Dates and datetimes are ISO 8601 strings. A value that does not fit its column is 400 `Malformed page token`, never a 500.

### The keyset predicate

For terms *t₁…tₙ* (the key last), the last row's values *v₁…vₙ*, and each term's direction, the next page is the rows where, for some *i*, every earlier term is equal and term *i* is beyond:

```text
OR over i = 1..n of ( AND over j < i of eq(tⱼ, vⱼ) )  AND  beyond(tᵢ, vᵢ)

eq(t, v)     = t IS NULL                       when v is null
               t = v                           otherwise
beyond(t, v) = FALSE                           when v is null   (nulls are last; nothing follows inside them)
               (t > v OR t IS NULL)            when v is not null and t is asc
               (t < v OR t IS NULL)            when v is not null and t is desc
```

This expanded form works with mixed directions, where a row-value comparison `(a, b) > (x, y)` does not, and it is portable across SQLite, PostgreSQL and MySQL. The `ORDER BY` puts nulls last the same portable way: `(t IS NULL), t [DESC]` in SQLAlchemy, and `F(t).asc(nulls_last=True)` or `.desc(nulls_last=True)` in Django, which emulates the clause on backends that lack it. The key is never null, so its `IS NULL` arms are omitted.

### API changes

These break the public API of `rn-forge-web` and `rn-forge-sqlalchemy`. pykit has no live consumers, and release 3 already carries breaking changes, so no compatibility shim is kept ([ADR-0002](../../../adr/ADR-0002.md)).

| Package | Before | After |
| --- | --- | --- |
| `rn-forge-web` | `Cursor(sort_key: str, entity_id: str, order_by: str = "")` | `Cursor(sort_keys: tuple[SortValue, ...], entity_id: str, order_by: str = "")`, where `SortValue = str \| int \| float \| bool \| None` |
| `rn-forge-web` | `encode_cursor(sort_key, entity_id, order_by="")` | `encode_cursor(sort_keys, entity_id, order_by="")` |
| `rn-forge-web` | `parse_order_by` rejects a second term | accepts many terms; rejects a repeated field |
| `rn-forge-web` | `check_cursor_order(cursor, terms)` | also rejects a token whose value count does not match *terms* |
| `rn-forge-sqlalchemy` | `next_page_token(sort_value, entity_id, terms)` | `next_page_token(row_values, entity_id, terms)`, one value per term |
| `rn-forge-sqlalchemy` | `keyset(...)` orders by one term | orders and resumes by every term, nulls last |
| `rn-forge-django` | `CursorPagination` and `OrderByFilter` use the first term | use every term; `ordering_fields` may name nullable fields |
| `rn-forge-fastapi` | `order_by_param` describes one field | describes a list; behavior follows `parse_order_by` |

The token's JSON changes from `{"k": "<value>", "id": ..., "o": ...}` to `{"k": [<values>], "id": ..., "o": ...}`. Tokens issued before the change are rejected with 400. That is acceptable because a token is opaque and is never persisted beyond the next request (§4).

### New conformance cases

Each driver serves `/conformance/people`, with `id`, `team` and `score` listed in `orderBy`, a page cap of 5, and these rows. `score` is nullable.

| id | team | score |
| --- | --- | --- |
| 1 | a | 10 |
| 2 | b | null |
| 3 | a | null |
| 4 | b | 5 |
| 5 | a | 10 |

An item is `{"id": "<id>", "team": "<team>", "score": <score>}`. The tokens below are written in the case table with `encode_cursor`, as the existing `pagination.*` tokens are.

| Case id | Request | Expect, items by id |
| --- | --- | --- |
| `pagination.order-by-several-fields-sorts-by-each-in-turn` | `orderBy=team,score desc`, `pageSize=5` | `5, 1, 3, 4, 2`; `nextPageToken` `null` |
| `pagination.nulls-sort-last-ascending` | `orderBy=score` | `4, 1, 5, 2, 3` |
| `pagination.nulls-sort-last-descending` | `orderBy=score desc` | `5, 1, 4, 3, 2` |
| `pagination.first-page-carries-a-composite-token` | `orderBy=team,score desc`, `pageSize=2` | `5, 1`; token `encode_cursor(("a", 10), "1", "team,score desc")` |
| `pagination.composite-token-resumes-within-a-tie` | the same, with that token | `3, 4`; token `encode_cursor(("b", 5), "4", "team,score desc")` |
| `pagination.composite-token-resumes-after-a-null` | `orderBy=team,score desc`, `pageSize=3`, token `encode_cursor(("a", None), "3", "team,score desc")` | `4, 2`; `nextPageToken` `null` |
| `pagination.repeated-order-by-field-is-400` | `orderBy=team,team desc` | 400, detail `orderBy names 'team' more than once` |
| `pagination.token-with-the-wrong-number-of-values-is-400` | `orderBy=team,score desc`, token `encode_cursor(("a",), "1", "team,score desc")` | 400, detail `Malformed page token` |

`pagination.order-by-two-fields-is-400` is removed from `CASES`, since it asserts the rule this feature lifts.

## Considered and rejected

- **Row-value comparison, `(a, b, id) > (x, y, z)`.** It is short, but it only works when every term has the same direction, and SQLite before 3.15 and some MySQL plans handle it poorly. The expanded form handles mixed directions everywhere.
- **The database's own null placement.** PostgreSQL puts nulls last ascending and first descending, while SQLite and MySQL do the opposite. One stack would then disagree with another on the same data, which §9's identical-wire rule forbids.
- **Nulls first in both directions, or nulls as the smallest value.** "Smallest" moves nulls to the top of a descending list, where a UI shows empty cells first. Last in both directions matches what spreadsheet and table UIs do.
- **A cap on the number of terms.** The endpoint's list of sortable fields already bounds it, and each field appears at most once.
- **Accepting old single-value tokens.** A token lives for one request, so a client holding one across a deploy retries from the first page. A dual-format decoder would outlive its use.
