# F12.16 — Expose `Content-Disposition` to browsers

| | |
| --- | --- |
| **State** | New |
| **Parent** | [E12](index.md) |
| **Iteration** | [Release 3](../../../releases/release-3/index.md) |
| **Predecessors** | — |
| **Source** | Owner request, 2026-09-28 |

A browser lets script read a cross-origin response header only when the response names it in `Access-Control-Expose-Headers` (Fetch standard, CORS-safelisted response headers). `Content-Disposition` is not safelisted. `rn_forge.web.EXPOSED_HEADERS` is the list both stacks' CORS helpers send (`CorsPolicy.expose_headers` on FastAPI, `cors_settings()`'s `CORS_EXPOSE_HEADERS` on Django). It names `ETag`, `Link`, `Location`, `Retry-After`, `Deprecation` and `Sunset`, but not `Content-Disposition`, which this kit emits on every export and import template (API conventions §17). A cross-origin client therefore downloads the file but has to invent its name.

## Context

The trigger fired when a browser client on a different origin could not read the file name of an export or an import template. The client's work does not gate this feature or any release ([ADR-0008](../../../adr/ADR-0008.md)).

## Design

**Release.** This ships in the `rn-forge-web` minor version that Release 3 cuts for [F12.14](F12.14-merge-patch.md) and [F12.15](F12.15-fastapi-resource-operations.md). The adapters read the constant at runtime, so they need no code change. An application gets the header by pinning the new `rn-forge-web` tag.

Only headers this kit itself emits belong in the list. `Accept-Patch` (F12.14) is sent only on a 415, which a client handles from the status alone, so it is not added.

## Stories

### S12.16.1 — Add `Content-Disposition` to `EXPOSED_HEADERS`

**State:** New

**Acceptance:**

- `rn_forge.web.EXPOSED_HEADERS` (in `rn_forge/web/tracing.py`) ends with `"Content-Disposition"`, after `"Sunset"`. The order of the existing entries is unchanged.
- `tests/test_tracing.py`'s assertion on the list includes `Content-Disposition`.
- `rn_forge.web.conformance.CASES` gains `cors.export-exposes-content-disposition` in the `cors` area. The case sends `GET /conformance/orders` with `Accept: text/csv` and `Origin: https://example.com`, and expects the following:
  - status 200;
  - `Access-Control-Allow-Origin: https://example.com`;
  - `expect_header_patterns` `{"Access-Control-Expose-Headers": r"(.+, )?Content-Disposition(, .+)?"}`, written as a literal so it does not read back the constant it tests;
  - `expect_text` `id,name\r\n1,widget\r\n`.
- Both drivers pass the new case and the existing `cors.exposed-headers-are-comma-joined` with no fixture change.
- The API conventions' §16 lists `Content-Disposition` among the exposed headers and names the new case. `rn-forge-fastapi`'s wiring guide mentions it with `ETag` and `Link`, and the `rn-forge-web` `CHANGELOG.md` has an entry.
- The acceptance block below passes.

```bash
set -euo pipefail
grep -q '"Content-Disposition"' packages/rn-forge-web/src/rn_forge/web/tracing.py
grep -q 'cors.export-exposes-content-disposition' packages/rn-forge-web/src/rn_forge/web/conformance/cases.py
grep -q 'Content-Disposition' packages/rn-forge-web/docs/guides/api-conventions.md
grep -q 'Content-Disposition' packages/rn-forge-web/CHANGELOG.md
(cd packages/rn-forge-web && uv run pytest -q tests/test_tracing.py tests/test_conformance.py)
(cd packages/rn-forge-django && uv run pytest -q tests/test_cors.py tests/test_conformance.py)
(cd packages/rn-forge-fastapi && uv run pytest -q tests/test_cors.py tests/test_conformance.py)
(cd packages/rn-forge-web && uv run --group docs mkdocs build --strict -q --site-dir "$(mktemp -d)")
```
