`rn-forge-django` ships four mixins in `rn_forge.django.drf.transfer` (`ResourceExportMixin`, `ResourceImportMixin`, `BatchCreateMixin`, `BatchDeleteMixin`). A viewset gets export, `:import`, `:importTemplate`, `:batchCreate` and `:batchDelete` by listing them. `rn-forge-fastapi`'s `rn_forge.fastapi.transfer` has only the building blocks (`tabular_format`, `tabular_response`, `read_rows`, `problem_response`). Every FastAPI application therefore writes those five handlers itself, including the conformance driver. `tests/test_conformance.py` hand-writes `/conformance/orders:import`, `:batchCreate` and `:batchDelete`, which its own docstring treats as a missing adapter ("if a case needs more than a line or two over them, the adapter is missing"). `:importTemplate` has neither a FastAPI helper nor a conformance case on either stack.

This feature adds route factories that match the Django mixins one for one. It moves the wire rules that the two stacks now word differently into `rn-forge-web`, and adds the conformance cases that pin them.

## Context

The trigger fired when a browser client's resource screen needed a FastAPI backend that serves every row of the resource standards (list, get, create, merge patch, delete, `:batchDelete`, `:import` with `validateOnly`, `:importTemplate` with `prefill`, export). Today only `rn-forge-django` supplies handlers for all of them. The client's work does not gate this feature or any release ([ADR-0008](../../../adr/ADR-0008.md)).

[F12.14](F12.14-merge-patch.md) supplies the `PATCH` row. The two touch different modules and can be built in either order, but releasing them together gives a client one `rn-forge-fastapi` tag that covers the whole table.

## Design

**The wire is already decided; this feature supplies the handlers.** The API conventions' §17 and `rn_forge.web.transfer` define every response. The FastAPI factories add no wire decision, as the package README requires. Where the two stacks word a response differently today, the wording moves into `rn-forge-web` and both stacks use it (S12.15.1, S12.15.3), because a client must not be able to tell the stacks apart ([ADR-0001](../../../adr/ADR-0001.md) rule 5).

**Persistence is the application's, through a store protocol.** FastAPI has no ORM, and `rn-forge-fastapi` imports none. Each factory takes a FastAPI dependency that returns a store, a small structural protocol with async methods. The application implements the store over SQLAlchemy, another ORM or a remote service. The store owns the transaction, so all-or-nothing and `validateOnly` rollback are its job. The factory never calls a store method after a validation failure, so a failed request never reaches the database. The protocols are structural, so `rn-forge-sqlalchemy` could later ship a store without importing `rn-forge-fastapi`.

**One factory per operation, as Django has one mixin per operation.** An application mounts only the operations its resource offers. A client detects the rest by their absence (404).

### The FastAPI surface

All of this is in `rn_forge.fastapi.transfer`. *collection* is the collection path, for example `/orders`. Each route is mounted at `{collection}:<method>`.

**Store protocols**

| Protocol | Method | Contract |
| --- | --- | --- |
| `ImportStore[T]` | `async import_rows(rows: Sequence[T], *, validate_only: bool) -> ImportCounts` | Upsert every row in one transaction; roll back when `validate_only`. May raise `RowsInvalid` for failures only it can see, such as a foreign-key lookup. |
| `TemplateSource` | `async rows() -> Iterable[Any]` | The current filtered rows, for `prefill`. Called only when `prefill` is set. |
| `BatchCreateStore[T]` | `async create_many(items: Sequence[T]) -> Sequence[Any]` | Create every item in one transaction and return the created objects. May raise `ItemsDenied(root="requests")` before writing. |
| `BatchDeleteStore` | `async find(ids: Sequence[str]) -> Collection[str]` | Which of *ids* exist within the caller's scope. |
| | `async delete_many(ids: Sequence[str]) -> None` | Delete every id in one transaction. May raise `ItemsDenied(root="ids")` before deleting. |

**Factories**

| Factory | Route | Behavior, in order |
| --- | --- | --- |
| `import_router(collection, *, model, store, formats=("csv", "xlsx"), max_rows=None, dependencies=())` | `POST :import`, multipart `file` | missing `file` → 422 `/file` `REQUIRED_FIELD_DETAIL`; format not in *formats* (by extension, else content type) → 422 `/file` `unsupported_file_detail(formats)`; unparseable → 422 `/file` `unreadable_file_detail(ext)`; `total > max_rows` → `row_cap_problem("import")`; any row error → `row_errors_problem`; `store.import_rows(valid, validate_only=parse_flag(validateOnly))` → 200 `import_report_body` |
| `import_template_router(collection, *, model, source, formats=("csv", "xlsx"), max_rows=None, dependencies=())` | `GET :importTemplate` | format from `negotiate_tabular_format(Accept, format, formats)`, else `formats[0]`; without `prefill` the file has the header row only; with `prefill` it holds `source.rows()`, and more than *max_rows* → `export_cap_problem`; filename `import-template.<ext>`; columns are *model*'s aliases, so a template round-trips through `:import` |
| `batch_create_router(collection, *, model, response_model, resource_name, store, max_rows=None, dependencies=())` | `POST :batchCreate` `{"requests": [...]}` | missing `requests` → 422 `/requests` `REQUIRED_FIELD_DETAIL`; empty → 422 `/requests` `NON_EMPTY_LIST_DETAIL`; over *max_rows* → `row_cap_problem("batch")`; item validation → 422 `/requests/<i>/<field>`, all items reported; `store.create_many` → 200 `{resource_name: [response_model dumped by alias]}` |
| `batch_delete_router(collection, *, resource_label, store, max_rows=None, dependencies=())` | `POST :batchDelete` `{"ids": [...]}` | missing or empty `ids` as above, with `/ids`; ids may be strings or integers and are compared as strings; over *max_rows* → `row_cap_problem("batch")`; the first id not in `store.find(ids)` → 404 detail `{resource_label} {id} not found`; `store.delete_many` → 204 |
| `tabular_export(rows, model, fmt, filename, *, max_rows=None, instance)` | used inside the application's own list route | `len(rows) > max_rows` → `problem_response(export_cap_problem(...))`; otherwise `tabular_response(rows, model, fmt, filename)` |

`:batchCreate` declares a request model built with `pydantic.create_model` (`requests: list[model]`) for OpenAPI. A route dependency reads the raw body first: the missing-member, empty-list and cap checks, then each item validated against *model*, with every failure reported as `RowsInvalid(root="requests")`. Item errors therefore carry Django's detail, `One or more rows are invalid.`, and its pointers, rather than FastAPI's `Validation Error`.

Export stays on the application's list route, because that route also answers JSON. `tabular_format()` picks the format, and `tabular_export` applies the cap, as `ResourceExportMixin` does on Django.

### New conformance cases

Each driver serves the existing `/conformance/orders` fixture, in which order `1` is `widget` with quantity `0`. It also serves `/conformance/capped:import` and `/conformance/capped:batchCreate` with a row cap of 1. The import model's columns are `id`, `name` and `Quantity`.

| Case id | Request | Expect |
| --- | --- | --- |
| `transfer.import-template-is-the-import-columns` | `GET /conformance/orders:importTemplate`, `Accept: text/csv` | 200 CSV; `Content-Disposition: attachment; filename="import-template.csv"; filename*=UTF-8''import-template.csv`; text `id,name,Quantity\r\n` |
| `transfer.import-template-prefill-adds-the-rows` | the same with `?prefill=true` | 200; text `id,name,Quantity\r\n1,widget,0\r\n` |
| `transfer.import-without-a-file-is-422` | `POST /conformance/orders:import`, multipart with no part | 422, `errors` `[{"pointer": "/file", "detail": "This field is required."}]` |
| `transfer.import-over-the-cap-is-422` | `POST /conformance/capped:import` with two data rows | 422, detail `The import exceeds the limit of 1 rows.` |
| `transfer.batch-create-with-an-empty-list-is-422` | `POST /conformance/orders:batchCreate` `{"requests": []}` | 422, `errors` `[{"pointer": "/requests", "detail": "A non-empty list is required."}]` |
| `transfer.batch-create-over-the-cap-is-422` | `POST /conformance/capped:batchCreate` with two items | 422, detail `The batch exceeds the limit of 1 rows.` |
| `transfer.batch-create-denied-item-is-403-pointer` | `POST /conformance/orders:batchCreate` `{"requests": [{"name": "ok"}, {"name": "forbidden"}]}` | 403 `forbidden`, detail `Forbidden`, `errors` `[{"pointer": "/requests/1", "detail": "You may not create this order."}]` |
| `transfer.denied-batch-create-persists-nothing` | `GET /conformance/orders/count`, depends on the previous case | 200 `{"count": 1}` |

### Out of scope

- **Partial-save import.** Django's `import_rollback_on_validation_errors = False` commits the valid rows and returns 200 with an `errors` list. The FastAPI import is all-or-nothing only, until an application asks for more.
- **Large-file import as a long-running operation.** This is the pattern in §17 (`POST /imports` → 202). It stays unbuilt on both stacks.
- **`:batchGet` and `:batchUpdate`.** These remain [F12.1](index.md), with its own trigger.
- **A store implementation shipped by `rn-forge-sqlalchemy`.** The guide shows one in application code. Shipping it waits for a second FastAPI application that writes the same store.

## Stories

### S12.15.1 — Shared transfer rules in `rn-forge-web`

**State:** Closed (2026-10-04)

**Acceptance:**

- `rn_forge.web.transfer` gains the following, each re-exported from `rn_forge.web`:
  - `ImportCounts`, a frozen dataclass of `created`, `updated` and `skipped`.
  - `parse_flag(value)`, which is `True` only for `"true"` or `"1"`, case-insensitively, and `False` for anything else, including `None`. It is the one parser for `validateOnly` and `prefill`.
  - `row_cap_problem(kind, cap, *, instance, registry=None)`, where `kind` is `"import"` or `"batch"`. It renders a 422 `validation-error` with detail `The {kind} exceeds the limit of {cap} rows.` and no `errors` member, alongside the existing `export_cap_problem`.
  - `NON_EMPTY_LIST_DETAIL = "A non-empty list is required."`.
  - `unsupported_file_detail(formats)`, which returns `Unsupported file type; use one of: csv, xlsx.` for `("csv", "xlsx")`.
  - `unreadable_file_detail(extension)`, which returns `The file could not be read as csv.` for `"csv"`.
- `rn_forge.web.exceptions` gains two exceptions, both registered in `default_registry()` and both implementing `HasProblemExtensions`:
  - `RowsInvalid(errors, *, root="rows")`. It renders exactly as `row_errors_problem(errors, root=root)` does: 422, detail `One or more rows are invalid.`, and `errors[].pointer = /<root>/<row>[/<field>]`.
  - `ItemsDenied(errors, *, root)`, a `PermissionDenied` subclass. It renders a 403 `forbidden` with detail `Forbidden` and `errors[].pointer = /<root>/<index>[/<field>]`. That is the body `rn-forge-django` produces today for `PermissionDenied({"requests": {"1": [message]}})`.
- `tests/test_transfer.py` covers each new function and both exceptions' rendered bodies. `uv run pyright` and `uv run lint-imports` pass.

### S12.15.2 — Conformance cases

**State:** New

**Acceptance:** `rn_forge.web.conformance.CASES` gains the cases in [New conformance cases](#new-conformance-cases), in the `transfer` area. Both drivers run every case with no skips. `test_the_fixture_serves_every_path_the_table_uses` passes on FastAPI with the new paths.

### S12.15.3 — `rn-forge-django` adopts the shared rules

**State:** Closed (2026-10-04)

**Acceptance:**

- `rn_forge.django.drf.transfer` changes as follows:
  - It uses `parse_flag` for `validateOnly` and `prefill`.
  - It uses `row_cap_problem` for the import and batch caps, in place of today's `ValidationError`, which renders an `errors` entry with an empty pointer.
  - It uses `unsupported_file_detail` and `unreadable_file_detail` for the `file` field.
  - It answers a missing `file` part with `REQUIRED_FIELD_DETAIL` in place of `No file was submitted.`.
- `_list_member` answers a missing member with `REQUIRED_FIELD_DETAIL`, and an empty list or a non-list with `NON_EMPTY_LIST_DETAIL`. Both carry the pointer `/<key>`.
- The Django conformance fixture adds three things: `validate_batch_create_item` denies an item named `forbidden` with `You may not create this order.`; `/conformance/capped:import` and `/conformance/capped:batchCreate` run under a `MAX_ROWS` of 1; and the new cases pass.
- The existing `tests/drf/` transfer tests are updated for the changed details and pass.

### S12.15.4 — FastAPI route factories

**State:** Closed (2026-10-04)

**Acceptance:**

- `rn_forge.fastapi.transfer` (the `transfer` extra, still not imported by `rn_forge.fastapi`) gains the store protocols and route factories in [The FastAPI surface](#the-fastapi-surface), with the behavior its tables state. Every factory returns an `APIRouter` and takes `dependencies=` like `APIRouter` does. Each store is obtained through `Depends(store)`, so a store dependency can take a session, a principal or filter query parameters.
- `RowsResult` gains `total: int`, the number of data rows read. `read_rows` raises `ValueError` with `unsupported_file_detail(("csv", "tsv", "xlsx"))` or `unreadable_file_detail(extension)`.
- The OpenAPI document of an app that includes the four routers for `/orders` has these properties:
  - The operationIds are `ordersImport`, `ordersImportTemplate`, `ordersBatchCreate` and `ordersBatchDelete`.
  - `:import`'s request body is `multipart/form-data` with a binary `file`.
  - `:batchCreate`'s request body is `{"requests": [<model>]}`, and its 200 response is `{"<resource_name>": [<response_model>]}`.
  - `:batchDelete`'s request body is `{"ids": [string | integer]}`, and it responds 204.
  - `FastApiApp`'s problem repair adds the 403, 404 and 422 responses it can produce.
- `tests/test_transfer.py` covers each factory's rows in the tables below. Those include the cases no conformance case reaches: an unsupported and an unreadable file, a store raising `RowsInvalid`, `ItemsDenied` from `delete_many`, integer ids, a `dependencies=` guard, and the store never being called after a validation failure.
- The FastAPI conformance fixture serves `/conformance/orders:import`, `:importTemplate`, `:batchCreate`, `:batchDelete` and the `/conformance/capped:*` routes through these factories over one in-memory store class. It serves its export routes through `tabular_export`. No hand-written handler for these paths is left in `tests/test_conformance.py`, and the file passes.

## Considered and rejected

- **One `resource_router()` taking every operation's options.** One factory per operation matches Django's mixins, keeps each signature small, and lets an application mount only what it offers.
- **Callbacks in place of store dependencies.** A plain callback cannot declare FastAPI dependencies, so it could not get a session, a principal or filter parameters without application glue. A store obtained through `Depends` gets them the ordinary FastAPI way.
- **Store protocols in `rn-forge-web`.** They mention pydantic models and FastAPI's dependency style, and nothing outside FastAPI uses them. Because they are structural, a store elsewhere can satisfy them without importing them.
