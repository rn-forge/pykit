Soft delete in Google AIP-164's shape, on both stacks and both ORM packages. A
`DELETE` on a resource that offers soft delete sets its `deleteTime` instead of
removing it. `POST {resource}:undelete` reverses it, and `showDeleted=true`
brings deleted resources back into a list. The API conventions list AIP-164 as
"not adopted (deferred)"; this feature adopts it.

## Context

**Outcome:** the owner scheduled this feature for release 3 on 2026-10-04, ahead
of its original trigger. Taken up before the
[model-vocabulary](../../ideas/index.md#model-vocabulary) idea, it settled that
idea's status-based soft-delete question.

## Design

**Outcome:** soft delete shipped on both stacks and both ORM packages
(2026-10-04), with hard delete and purge out of scope. The
[API conventions](../../../rn-forge-web/guides/api-conventions.md) §21 own the
wire rules and case ids; the
[Django models guide](../../../rn-forge-django/guides/models.md), the
[`rn-forge-sqlalchemy` guide](../../../rn-forge-sqlalchemy/guides/usage.md) and
the [FastAPI soft-delete guide](../../../rn-forge-fastapi/guides/soft-delete.md)
show the bindings, and the
[soft-delete reference](../../../rn-forge-web/reference/soft_delete.md) lists
the shared symbols.

### Why a `delete_time` column, not a status

**Outcome:** [ADR-0010](../../../adr/ADR-0010.md) records the decision and its
reasons.

### New conformance cases

**Outcome:** the `soft-delete` area's cases are in `CASES`, documented in the
[conformance reference](../../../rn-forge-web/reference/conformance.md).

## Considered and rejected

- **Status-based soft delete (`status = DELETED`), from the model-vocabulary
  idea.** It cannot produce AIP-164's `deleteTime` once the resource is
  written again, and `:undelete` is such a write. It also mixes lifecycle
  state with retention.
- **A default manager or global session hook that hides deleted rows.** A get
  must return a deleted resource (AIP-164), and a hidden row breaks
  related-object lookups and the Django admin in ways that are hard to see.
  Visibility is decided in the view or the query, where the action is known.
- **`DELETE` answering 204, as §10 does for a hard delete.** AIP-164 returns the
  resource, and the client needs the new `deleteTime` and `ETag`. Answering
  204 would cost every client a second request.
- **`:batchDelete` returning the soft-deleted resources, as AIP-235 allows.** It
  would give the method two response shapes depending on the resource. It
  stays 204, and a client that needs the result lists with `showDeleted=true`.
- **A purge route or `expireTime`.** Purging is a retention decision with its
  own authorization. Nothing in the kit schedules it, so the kit does not
  advertise an expiry.
- **`django-safedelete` 1.5.0 (checked 2026-10-04).** It is maintained: 1.5.0
  was released 2026-08-17 and its tox matrix covers Django 4.2 to 6.1. It
  ships no `py.typed` marker and its classifiers stop at Python 3.8, so strict
  pyright sees untyped code. It hides deleted rows through its default manager
  (`DELETED_INVISIBLE`), which ADR-0010 rejects. Its `save()` undeletes a
  soft-deleted row unless `keep_deleted=True`, so an ordinary `PUT` would
  undelete, where the wire rules answer 409. It adds cascade policies and
  `deleted_by_cascade` that the design does not use. `soft_delete` and
  `undelete` as a few lines on a nullable field are cheaper than overriding
  that much of the library.
- **`sqlalchemy-easy-softdelete` 0.9.1 (checked 2026-10-04).** It is maintained
  (released 2026-06-16), typed (`Typing :: Typed`, `py.typed`), and supports
  Python 3.10 to 3.14. It installs a hook that rewrites every select on tables
  carrying its mixin, which ADR-0010 rejects, and `GET` of a deleted resource
  would need `include_deleted` on each query. Its SQLAlchemy range is
  `>=1.4,<2.1`, narrower than the package's `sqlalchemy>=2.0`. It provides no
  version bump and no `updated_by`, so the wire rules would still need our own
  helpers.
