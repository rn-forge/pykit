Soft delete in Google AIP-164's shape, on both stacks and both ORM packages. A `DELETE` on a resource that offers soft delete sets its `deleteTime` instead of removing it. `POST {resource}:undelete` reverses it, and `showDeleted=true` brings deleted resources back into a list. The API conventions list AIP-164 as "not adopted (deferred)"; this feature adopts it.

## Context

The owner scheduled this feature for release 3 on 2026-10-04, ahead of its original trigger ("a consumer needs soft delete on the wire").

The [model-vocabulary](../../ideas.md#model-vocabulary) idea proposes status-based soft delete, with `status = DELETED` and no timestamp column, and says that whichever of the two is taken up first settles the other. This feature is taken up first, so it settles the question. S12.2.1 records the decision as an ADR and rewrites the idea's soft-delete section to follow it.

## Design

### Why a `delete_time` column, not a status

AIP-164 puts `deleteTime` on the wire. A status value cannot supply it: deriving it from `update_time` breaks on the first write after the delete, and `:undelete` itself is such a write. Every maintained soft-delete library on both ORMs keys on a nullable timestamp (`django-safedelete`'s `deleted`, `sqlalchemy-easy-softdelete`'s `deleted_at`). A nullable timestamp also indexes well for the common filter, `delete_time IS NULL`. The column is independent of `status`. Django's existing `Status.Deleted` value does not mean soft-deleted, and the model-vocabulary idea keeps the question of whether to remove it.

### Wire rules

A resource either offers soft delete or does not; it never offers both kinds of `DELETE`. A soft-deleting resource's representation carries a read-only `deleteTime`: an RFC 3339 UTC timestamp, or `null` while the resource is live (§18).

| Request | Resource live | Resource soft-deleted |
| --- | --- | --- |
| `GET /notes/{id}` | 200 | **200**, with `deleteTime` set (AIP-164: a get returns the deleted resource) |
| `GET /notes` | listed | omitted, unless `showDeleted=true` |
| `DELETE /notes/{id}` | **200** with the resource, `deleteTime` set, `version` bumped | 404, detail `{Label} {id} not found` |
| `POST /notes/{id}:undelete` | 409 `conflict`, detail `{Label} {id} is not deleted` | 200 with the resource, `deleteTime` `null`, `version` bumped |
| `PUT` / `PATCH /notes/{id}` | as today | 409 `conflict`, detail `{Label} {id} is deleted` |
| `POST /notes:batchDelete` | soft-deletes every id; 204 | the id is not found: 404 for the whole batch |
| `GET /notes:batchGet` ([F12.1](F12.1-batch-get-update.md)) | returned | returned, as `GET` returns it |

- **`DELETE` answers 200 with the resource**, as AIP-164 says, in place of §10's 204. The client gets the `deleteTime` and the new `ETag` without a second request. A hard-deleting resource still answers 204.
- **Preconditions.** `DELETE` and `:undelete` honor `If-Match` (§3) on a versioned resource, in the same order as a merge patch: absent and required is 428, malformed is 400, stale is 412, and nothing is written. Both answer with the new `ETag`.
- **`showDeleted`** is parsed by `parse_flag`, like `validateOnly` and `prefill`: `true` or `1` includes deleted resources, and anything else excludes them. The page token does not bind it.
- **Hard delete and purge** are out of scope. Neither stack offers a route that purges a soft-deleted resource, and AIP-164's `expireTime` is not emitted. Retention-driven purging is the application's job, through its own authorized operation.

### Shared pieces in `rn-forge-web`

| Symbol | Contract |
| --- | --- |
| `ResourceDeleted(DomainConflict)` | 409. `ResourceDeleted(label, id)` renders detail `{label} {id} is deleted`. |
| `ResourceNotDeleted(DomainConflict)` | 409. `ResourceNotDeleted(label, id)` renders detail `{label} {id} is not deleted`. |
| `SHOW_DELETED_PARAM` | `"showDeleted"` |
| `require_live(delete_time, *, label, id)` | Raises `ResourceDeleted` when *delete_time* is not `None`. |

### Persistence

**Django — `rn_forge.django.models`.** `SoftDeleteModelMixin` is an abstract model with `delete_time = DateTimeField(null=True, blank=True, db_index=True)`. It adds `soft_delete(*, actor)` and `undelete(*, actor)`, which set or clear `delete_time`, set `updated_by`, and save; a `VersionedModelMixin` model bumps its version on that save as it does on any other. `SoftDeleteQuerySet` adds `.live()` and `.deleted()`. The default manager is **not** filtered. The view decides what is visible, so the admin, related-object lookups and `GET` of a deleted resource keep working.

**SQLAlchemy — `rn_forge.sqlalchemy`.** `SoftDeleteMixin` adds `delete_time: Mapped[datetime | None]` (`UTCDateTime`, indexed). `live(stmt, model, *, show_deleted=False)` adds `delete_time IS NULL` unless *show_deleted*. `soft_delete(obj, *, actor, now=None)` and `undelete(obj, *, actor, now=None)` set the columns and bump `version` on a `VersionMixin` row. Nothing hooks the session globally.

Both take the time from an overridable source: the Django mixin's `get_delete_time()` and the SQLAlchemy helpers' `now=` argument. That is how a conformance fixture pins it.

### Django view — `rn_forge.django.drf.views`

`SoftDeleteMixin`, listed before `BaseModelViewSet`'s own mixins:

- `get_queryset()` excludes deleted rows for `list` and `batch_delete` unless `showDeleted` is set for `list`; `retrieve`, `batch_get`, `destroy`, `undelete` and the update actions see every row.
- `perform_destroy` soft-deletes, and `destroy` answers 200 with the serialized resource and its `ETag`.
- `undelete` is `@action(detail=True, methods=["post"], url_path="undelete")`, served at `/notes/{id}:undelete` by `CustomMethodRouter`.
- `update` and `partial_update` call `require_live` before anything else that can fail, except the media-type check.
- `soft_delete_requires_if_match: ClassVar[bool] = False`.

`BatchDeleteMixin` deletes through `perform_destroy` in place of `instance.delete()`, so a soft-deleting viewset soft-deletes in a batch too. For every other viewset the behavior is unchanged.

### FastAPI — `rn_forge.fastapi`

| Symbol | Contract |
| --- | --- |
| `SoftDeleteStore` protocol | `async find(id) -> SoftDeleteState \| None`, where `SoftDeleteState` has `row: Any`, `version: int \| None` and `delete_time: datetime \| None`; `async soft_delete(id) -> Any`; `async undelete(id) -> Any`. The store owns the transaction and the clock. |
| `soft_delete_router(collection, *, response_model, resource_label, store, require_if_match=False, codec=None, dependencies=())` | Mounts `DELETE {collection}/{id}` and `POST {collection}/{id}:undelete` with the rules above. Each answers with *response_model* by alias and an `ETag` when the row is versioned. |
| `show_deleted_param()` | A dependency yielding `bool` from `showDeleted`. |

The application's own `GET` list and `PUT`/`PATCH` routes use `show_deleted_param()` and `require_live`. `batch_delete_router` needs no change, because its store's `find` and `delete_many` already decide scope and effect.

### New conformance cases

A new `soft-delete` area. Each driver seeds `/conformance/notes`: versioned notes `1` `first` (live, version 1), `2` `second` (deleted at `2026-01-01T00:00:00Z`, version 2) and `3` `third` (live, version 1). The fixture's clock reads `2026-01-02T00:00:00Z`. A note's representation is `{"id", "text", "deleteTime"}`, and the list is the AIP-158 envelope with every note on one page.

## Considered and rejected

- **Status-based soft delete (`status = DELETED`), from the model-vocabulary idea.** It cannot produce AIP-164's `deleteTime` once the resource is written again, and `:undelete` is such a write. It also mixes lifecycle state with retention.
- **A default manager or global session hook that hides deleted rows.** A get must return a deleted resource (AIP-164), and a hidden row breaks related-object lookups and the Django admin in ways that are hard to see. Visibility is decided in the view or the query, where the action is known.
- **`DELETE` answering 204, as §10 does for a hard delete.** AIP-164 returns the resource, and the client needs the new `deleteTime` and `ETag`. Answering 204 would cost every client a second request.
- **`:batchDelete` returning the soft-deleted resources, as AIP-235 allows.** It would give the method two response shapes depending on the resource. It stays 204, and a client that needs the result lists with `showDeleted=true`.
- **A purge route or `expireTime`.** Purging is a retention decision with its own authorization. Nothing in the kit schedules it, so the kit does not advertise an expiry.
- **`django-safedelete` 1.5.0 (checked 2026-10-04).** It is maintained: 1.5.0 was released 2026-08-17 and its tox matrix covers Django 4.2 to 6.1. It ships no `py.typed` marker and its classifiers stop at Python 3.8, so strict pyright sees untyped code. It hides deleted rows through its default manager (`DELETED_INVISIBLE`), which ADR-0010 rejects. Its `save()` undeletes a soft-deleted row unless `keep_deleted=True`, so an ordinary `PUT` would undelete, where the wire rules answer 409. It adds cascade policies and `deleted_by_cascade` that the design does not use. `soft_delete` and `undelete` as a few lines on a nullable field are cheaper than overriding that much of the library.
- **`sqlalchemy-easy-softdelete` 0.9.1 (checked 2026-10-04).** It is maintained (released 2026-06-16), typed (`Typing :: Typed`, `py.typed`), and supports Python 3.10 to 3.14. It installs a hook that rewrites every select on tables carrying its mixin, which ADR-0010 rejects, and `GET` of a deleted resource would need `include_deleted` on each query. Its SQLAlchemy range is `>=1.4,<2.1`, narrower than the package's `sqlalchemy>=2.0`. It provides no version bump and no `updated_by`, so the wire rules would still need our own helpers.
