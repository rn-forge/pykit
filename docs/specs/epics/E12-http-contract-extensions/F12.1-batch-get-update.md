The API conventions' §19 spells `:batchGet` and `:batchUpdate` (AIP-231,
AIP-234) and says they are built when a consumer needs them. Neither stack has
them. This feature adds the handlers on both stacks, with the wire rules in
`rn-forge-web` and conformance cases that pin them. It follows
[F12.15](F12.15-fastapi-resource-operations.md)'s pattern: Django mixins,
FastAPI route factories over application stores, one wording for both.

## Context

**Outcome:** the owner scheduled this feature for release 3 on 2026-10-04, ahead
of its original trigger, to complete the batch set that `:batchCreate` and
`:batchDelete` started, reusing F12.15's shared list rules.

## Design

**Outcome:** both methods shipped all or nothing on both stacks (2026-10-04).
The [API conventions](../../../rn-forge-web/guides/api-conventions.md) §17 own
the wire rules; the
[Django transfer guide](../../../rn-forge-django/guides/transfer.md) and the
[FastAPI transfer guide](../../../rn-forge-fastapi/guides/transfer.md#batch-get-and-update)
show the bindings.

### Shared pieces in `rn-forge-web`

**Outcome:** the
[transfer reference](../../../rn-forge-web/reference/transfer.md) documents the
shared symbols and their contracts.

### New conformance cases

**Outcome:** the cases are in `CASES`, in the `transfer` area, documented in the
[conformance reference](../../../rn-forge-web/reference/conformance.md); the API
conventions name each case id beside its rule.

### Out of scope

- **Partial success.** AIP-234 allows an `allow_missing` upsert and partial
  results. Both batch methods stay all or nothing, as `:batchCreate` and
  `:batchDelete` are.
- **`readMask` on `:batchGet`.** [F12.9](F12.9-read-mask.md) adds it.

## S12.1.1 — Shared batch rules in `rn-forge-web`

**State:** Closed (2026-10-04)

**Acceptance:**

- `rn_forge.web` exports `InvalidBatchGet`, `batch_get_ids`,
  `NON_EMPTY_IDS_DETAIL`, `DUPLICATE_ID_DETAIL`, `BatchUpdateItem`,
  `parse_batch_update` and `check_item_precondition`, with the contracts in
  [Shared pieces](#shared-pieces-in-rn-forge-web).
- `PreconditionRequired`, `MalformedPrecondition` and `VersionConflict` accept
  an optional `errors` argument. Without it, their rendered bodies are
  unchanged; every existing concurrency case still passes.
- `tests/test_transfer.py` and `tests/test_concurrency.py` cover each new
  function: every step of both tables, ids given as strings or integers, empty
  `ids` values dropped, and `*` as an item's `ifMatch`.

## S12.1.2 — Conformance cases

**State:** Closed (2026-10-04)

**Acceptance:** `RequestSpec.query` accepts `str | tuple[str, ...]` values, and
both drivers send a tuple as a repeated parameter. `CASES` gains the cases in
[New conformance cases](#new-conformance-cases), in the `transfer` area. Both
drivers run every case with no skips.

## S12.1.3 — Django binding

**State:** Closed (2026-10-04)

**Acceptance:**

- `rn_forge.django.drf.transfer` exports `BatchGetMixin` and `BatchUpdateMixin`,
  served by `CustomMethodRouter` at `{collection}:batchGet` and
  `{collection}:batchUpdate`.
- The Django conformance fixture serves `/conformance/books` and
  `/conformance/capped-books` through them, and the new cases pass.
- `tests/drf/` covers what the cases do not reach: `validate_batch_update_item`
  denying an item (403, nothing written), `batch_update_requires_if_match`
  (428 with the pointer), audit fields set on every updated row, an
  unversioned model ignoring `ifMatch`, and a `filter_queryset` scope hiding
  an id (404), and an id the key cannot hold (404, also for `:batchDelete`).
- The drf-spectacular schema names the operations `booksBatchGet` and
  `booksBatchUpdate`.

## S12.1.4 — FastAPI binding

**State:** Closed (2026-10-04)

**Acceptance:**

- `rn_forge.fastapi.transfer` exports `BatchGetStore`, `BatchUpdateStore`,
  `batch_get_router` and `batch_update_router`.
- The FastAPI conformance fixture serves `/conformance/books` and
  `/conformance/capped-books` through them over an in-memory store, with no
  hand-written handler for those paths, and the new cases pass.
- `tests/test_transfer.py` covers a store raising `ItemsDenied` (403,
  `update_many` writes nothing), `require_if_match=True`, integer ids, a
  `dependencies=` guard, and the store never being asked to write after a
  validation failure.
- The OpenAPI document has `booksBatchGet` with a repeated `ids` query parameter
  and `booksBatchUpdate` with the `requests` item schema, and both list their
  problem responses.

## S12.1.5 — Documentation and release notes

**State:** Closed (2026-10-04)

**Acceptance:**

## Considered and rejected

- **`POST :batchGet` with the ids in a body.** It escapes URL length limits, but
  AIP-231 makes the method a `GET`, and a `GET` is cacheable and safe to
  retry. The row cap keeps the URL short.
- **AIP-234's per-item `updateMask`.** §10 rejects field masks for updates. A
  merge patch per item keeps one partial-update language across `PATCH` and
  `:batchUpdate`.
- **`PUT` semantics per item (full replacement).** A UI that edits several rows
  sends only the changed members, which is what a merge patch expresses.
- **Partial success with a per-item status list.** Every existing batch method
  is all or nothing. A mixed outcome would need a second response shape and
  client logic to reconcile it.
