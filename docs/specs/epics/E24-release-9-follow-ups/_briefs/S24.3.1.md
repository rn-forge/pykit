# S24.3.1 — Load the surface strictly

Brief for
[S24.3.1](../F24.3-strict-cli-surface.md#s2431-load-the-surface-strictly), at
`c3fc2b8`.

## Goal

`CliSurface.load` rejects a `[cli]` key that names no field, at any level,
instead of silently dropping it.

## Settled

- Settled by the reviewer, 2026-11-17: `CliSurface` and `CommandSurface` in
  `packages/rn-forge-cli/src/rn_forge/cli/surface.py` subclass
  `rn_forge.commons.lang.dataclasses.StrictDataclassMixin` instead of
  `DataclassMixin`. That mixin already raises
  `AppException("Invalid CliSurface: unknown key(s) <dotted paths>")`; no new
  message or validation code.
- `CliSurface.load`'s `Raises:` gains: a key names no field.
- A whole document passed with no `cli` table but a top-level `name` is still
  read as the surface itself, so its other top-level keys now fail. That is
  intended.
- Changelog: `packages/rn-forge-cli/CHANGELOG.md`, `[Unreleased]`,
  `### Changed`: a `[cli]` table with a key that names no field fails to load.

## Current behaviour

At `c3fc2b8`, `DataclassMixin.from_dict` drops unknown keys:
`CliSurface.load({"name": "demo", "comands": []})` returns a surface with no
commands, and
`{"name": "demo", "commands": [{"name": "a", "target": "m:f", "hlep": "x"}]}`
loads with `help=None`. Neither raises, so `pytest.raises(AppException)` fails
with "DID NOT RAISE".

## Change

1. `surface.py`: the base-class swap and the `Raises:` line.
1. The changelog entry.

## Tests first

In `tests/test_surface.py`, `TestCliSurfaceLoad`:

- `test_an_unknown_top_level_key_is_refused`: the `comands` mapping above;
  `AppException` whose message contains `comands`.
- `test_an_unknown_command_key_is_refused`: the `hlep` mapping above; message
  contains `commands.0.hlep`.
- `test_an_unknown_key_in_a_file_is_refused`: a TOML file with `[cli]`,
  `name = "demo"` and `colour = "red"`; message contains `colour`.

All three fail today with DID NOT RAISE.
