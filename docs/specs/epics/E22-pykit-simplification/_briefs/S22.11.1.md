# S22.11.1 — Settle count semantics and resource targets

Brief for

at `1a8da87`.

## Goal

Observe how `upsert` behaves with competing writers and measure its resource
cost, then compare count-semantics options with a recommendation. The owner
decides; the algorithm does not change.

## Settled

- Decision story: no change to the algorithm, chunking or transaction handling
  (F22.11). The owner decides from `## Result`.
- Settled by the reviewer, 2026-11-14: an invalid empty `key` raises a
  deliberate `ValueError` that says `key` must not be empty, instead of the
  current `ZeroDivisionError`. Valid empty `rows` stays a no-op with no query.
  This is the only code change allowed here, with a regression test; the owner
  may strike it.
- `upsert` never commits; the caller's transaction decides (E22 scope).
- Measurements name inputs, environment, time, peak memory and operation counts;
  no flaky wall-clock assertions in ordinary tests (E22 `design.md`).

## Current behaviour

`packages/rn-forge-sqlalchemy/src/rn_forge/sqlalchemy/upsert.py`:

- `upsert` (`:30`): validates model, `_keyed` (`:81`, raises on missing column
  or duplicate key), `_existing` (`:133`) reads current rows, `_changes`
  (`:101`) classifies created/updated/skipped, then one
  `INSERT ... ON CONFLICT DO UPDATE` for the changed rows (`:66-80`).
- Docstring (`:42`) says "The existing rows are read first, so the counts are
  exact". Classification is a pre-write snapshot, so a concurrent writer
  between read and write can make counts wrong.
- `_existing` chunks reads by `_MAX_PARAMETERS // len(key)` (`:141`); with
  `key=[]` that divides by zero. Empty `rows` still reaches `_existing` with
  an empty identity list (no chunk, so no query), which should be confirmed.
- Created rows hold full row dicts in `to_write` (a second materialization of
  the input).

Tests: `packages/rn-forge-sqlalchemy/tests/test_upsert.py` (`Product` key `sku`,
`Line` composite). Existing cases: counts, audit stamps, no rewrite of skipped
rows, rollback, duplicate key, missing column, 33,000 rows, composite key.
`tests/conftest.py` parametrizes `engine` over `sqlite` and `postgres`; the
postgres case is skipped unless `RN_FORGE_TEST_POSTGRES_DSN` is set (a bare
`postgresql://` DSN is rewritten for asyncpg). CI supplies it from the
`postgres:17` service (`.github/workspace-ci-handoff.md:60`). Set the variable
to a local PostgreSQL 17 when running `task test`; if none is reachable, say so
in `## Result` and report the postgres cases as skipped, not passed.

## Tests first

All use the `session`/`engine` fixtures; competing-writer tests open a second
`AsyncSession` on the same `engine`.

1. `test_competing_writer_between_read_and_write_miscounts` (marked `postgres`;
   SQLite variant if it can interleave): session B inserts a key after A's
   `_existing` read (patch `upsert._existing` to run B's commit once). Assert
   the observed counts and final rows. If counts differ from the documented
   claim, strict xfail naming S22.11.1; if equal, a passing observation.
1. `test_two_sessions_upserting_the_same_new_keys` (both dialects): concurrent
   `asyncio.gather`; record outcomes (success, counts, error) as assertions
   that describe what happens; SQLite may raise a lock error, so assert the
   observed type.
1. `test_serial_upserts_report_exact_counts` (passing): control for the above.
1. `test_empty_rows_runs_no_query` (passing): count statements with a
   `before_cursor_execute` event; assert 0 after `upsert` of `[]`.
1. `test_an_empty_key_raises_value_error`: fails before with
   `ZeroDivisionError`.
1. Baselines (passing): single and composite key, audit preservation across
   update, rollback, duplicate rejection, for empty, unchanged, mixed and
   large (33,000) input; record statement counts.

Measurement (in `## Result`, not an assertion): per input shape, statement count
and `tracemalloc` peak, SQLite and PostgreSQL; state environment.
