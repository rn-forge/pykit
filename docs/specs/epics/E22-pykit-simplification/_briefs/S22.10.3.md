# S22.10.3 — Set the transfer resource targets

Brief for
[S22.10.3](../F22.10-fastapi.md#s22103-set-the-transfer-resource-targets), at
`01a8985`. This is a **decision story**: you build the measurement, record the
baseline and propose target options with evidence. You do not pick the target.
The owner does, afterwards, and
[S22.10.2](../F22.10-fastapi.md#s22102-keep-route-assembly-thin) must then meet
it ("measured transfer memory/event-loop delay improves or stays within the
target S22.10.3 set").

## Goal

Add an opt-in measurement of the FastAPI transfer adapter
(`packages/rn-forge-fastapi/src/rn_forge/fastapi/transfer.py`) that records peak
traced memory, wall time and event-loop delay for large imports, exports and a
large batch create; record the baseline in
`docs/guides/performance-baselines.md`; find and evidence the cause of each
outlier; and put 2-3 target options per metric, with a recommendation, in
`## Result`. S22.10.2 will re-run the same measurement file unchanged, so the
cases, inputs and record fields you create are the contract it is judged by.

## Settled

- Settled by the reviewer, 2026-11-16: what is measured. Model `Row` has ten
  columns (`ID` int, `SKU`, `Name`, `Note`, `Region`, `Owner` str, `Quantity`
  int, `Price` float, `Due` date, `Active` bool), declared as
  `Field(alias="<Header>")` with
  `ConfigDict(from_attributes=True, populate_by_name=True)` (aliases are the
  file headers on import and the column headers on export; `populate_by_name`
  lets the export rows be plain dicts keyed by attribute name). Rows are
  generated, never random: `id=i`, `sku=f"sku-{i}"`, fixed other values. Cases
  (case name, then inputs recorded in the record):

    | Case | Inputs | Count |
    | -- | -- | -: |
    | `fastapi_export` | `format` csv or xlsx; `rows` 10,000 or 100,000; `columns` 10 | 4 |
    | `fastapi_import` | `format` csv or xlsx; `rows` 10,000 or 100,000; `columns` 10; `dry_run` false | 4 |
    | `fastapi_import` | csv, 100,000 rows, `dry_run` true (`?validateOnly=true`) | 1 |
    | `fastapi_batch_create` | `rows` 10,000 or 100,000; `columns` 10 | 2 |

    That is 11 cases. The routes are `tabular_export` behind `tabular_format()`
    (GET, `?format=`), `import_router` (POST `/rows:import`, multipart part
    `file`) and `batch_create_router` (POST `/rows:batchCreate`, JSON
    `{"requests": [...]}`), with no `max_rows`. The store is a stub:
    `import_rows` returns `ImportCounts(created=len(rows), updated=0, skipped=0)`
    and `create_many` returns its items, so the figures are the adapter's own
    cost, not a database's. Batch update, delete and get are not measured (their
    per-row work is the store's); dry-run is one case because the adapter only
    forwards the flag.

- Settled by the reviewer, 2026-11-16: the metrics, per case, in the record's
  `counts` (the `measure` fixture already gives `wall_s` and `peak_bytes`,
  both process-wide, so tracemalloc includes worker threads):

    - `peak_bytes`: traced peak of the request, from the `measure` fixture; the
      app, its row list and the request body are built before `measure` starts
      and are not counted; the response is discarded as it is sent (below), so
      it is not counted either.
    - `wall_s`: from the fixture. Informational for imports; it is the
      user-visible symptom for the CSV export outlier.
    - Event-loop delay: a heartbeat task on the same loop,
      `while not stop.is_set(): t = perf_counter(); await asyncio.sleep(0.005); lags.append(perf_counter() - t - 0.005)`,
      started and given three intervals to settle before `measure` begins,
      `lags.clear()`, stopped when the response is complete. Record
      `loop_lag_max_s` (maximum lag, the primary figure: one blocking call
      stalls every other request for that long), `loop_lag_p99_s`
      (`sorted(lags)[int(0.99 * (len(lags) - 1))]`) and `heartbeats`
      (`len(lags)`). Where `heartbeats` is under 100 the p99 is not meaningful
      and the maximum is the figure: say so beside such rows. Lag measured this
      way includes GIL contention from worker threads (about the 5 ms switch
      interval), so a threaded handler shows a small non-zero floor; the
      baseline records that floor rather than hiding it.
    - `response_bytes` and `status` (must be 200; assert it after the
      `with measure(...)` block, but set every count **inside** the block: the
      fixture writes the record when the block exits, so a count set after it is
      silently lost; this cost one prototype run). Also record the request body
      size (`inputs["request_bytes"]`) for imports and batch create.

- Settled by the reviewer, 2026-11-16: how it runs. The app is driven through a
  small hand-written ASGI call (`await app(scope, receive, send)`) inside the
  test's own event loop, not through `httpx` or `TestClient`. Reasons,
  measured on the prototype:

    - `fastapi.testclient.TestClient` runs the app in an anyio portal on a
      separate thread and loop, so a heartbeat in the test's loop cannot see the
      app's loop delay. Unusable.
    - `httpx.AsyncClient(transport=httpx.ASGITransport(app=app))` shares the loop
      but buffers the whole response body in the client: the 100,000-row CSV
      export showed a 22,560,788-byte traced peak through it against 264,515
      bytes with the driver below. It would charge the client's buffer to the
      server. Driver contract: scope keys `type`, `asgi`, `http_version`,
      `method`, `scheme`, `path`, `raw_path`, `query_string`, `headers`
      (`content-length`, and `content-type` when there is a body), `server`,
      `client`; `receive` returns the whole body once as
      `{"type": "http.request", "body": body, "more_body": False}` and
      afterwards **blocks** (`await asyncio.Event().wait()`), it must not return
      `http.disconnect`: Starlette's `StreamingResponse` listens for a
      disconnect and cancels the stream on it, which turned the first CSV export
      prototype into a 0-byte response in 0.01 s. `send` keeps only the status
      from `http.response.start` and `sum(len(body))` from `http.response.body`.
      Multipart bodies are hand-built (`--boundary`,
      `Content-Disposition: form-data; name="file"; filename="rows.<ext>"`,
      closing boundary) before the measurement; import files are generated with
      `tablib.Dataset.export` outside it. Heartbeat and driver run in the one
      pytest-asyncio test loop (`pytest.mark.asyncio`, as
      `tests/test_transfer.py` does).

## Current behaviour

`packages/rn-forge-fastapi/src/rn_forge/fastapi/transfer.py`, which has no
measurement today (`tests/` has no `measure/`;
`docs/guides/performance-baselines.md` has Django, SQLAlchemy and data rows but
none for FastAPI, and says `web.transfer` has no export workload):

- **CSV export** (`tabular_response`, `:154-198`): `lines()` (`:179-190`) is a
  *synchronous* generator that validates and dumps one row per `yield` and
  yields one `StringIO` chunk per row; it is passed to
  `StreamingResponse(lines(), ...)` (`:192`). Starlette 1.6.0 wraps a sync
  iterator in `iterate_in_threadpool`, which does
  `await anyio.to_thread.run_sync(_next, it)` for **every item**: one
  thread-pool hop per row. Prototype figures on this commit, 100,000 rows × 10
  columns: validating and dumping the rows alone takes 0.204 s, the whole
  generator run synchronously 0.312 s, a trivial 100,000-item generator
  through `iterate_in_threadpool` 6.914 s, and the real row iterator through
  it 6.64 s. So the hop (about 69 µs each on this machine) is the cost, not
  the CSV work; the full request measured 12.15 s wall with a 264,515-byte
  peak and a loop-lag maximum of 0.011 s. The event loop stays responsive and
  memory is flat; the loss is time. Your `## Result` must re-establish this on
  the final harness (same three timings, run through the `task test` verb in a
  throwaway test you delete) and say whether chunking would remove it.
- **XLSX/TSV export** (`:194-196`, `_build_body :201-209`): the whole dataset is
  built in one `run_in_threadpool` call, so the loop is not blocked.
  Prototype: 10,000 rows 3.53 s, 100,000 rows 30.99 s wall, 29,711,061-byte
  peak, loop-lag maximum 0.025 s. The time is `rn_forge.data.write_xlsx`
  (`packages/rn-forge-data/src/rn_forge/data/excel.py:361`); the guide's
  `excel_write` row measured 16.4-18.0 s for 50,000 rows × 10 columns, the
  same slope. Confirm by timing `write_xlsx` alone at 100,000 rows and
  subtracting. It is not a FastAPI cost and not S22.10.2's to fix; record it
  as such.
- **Import** (`read_rows :221-258`, `_parse_rows :261-278`,
  `import_items :533-559`): `await upload.read()` (`:257`) loads the whole
  file, then one `run_in_threadpool` decodes it, `tablib` loads it,
  `dataset.dict` (`:281`) builds a list of dicts, and every row is validated
  into a model (`:275`), all four held at once. Prototype, 100,000 rows: CSV
  1.47 s, 218,338,441-byte peak, loop-lag maximum 0.112 s; XLSX 20.72 s,
  194,568,395 bytes, maximum 0.254 s; 10,000-row CSV 0.14 s, 22,470,351 bytes.
  Peak is about 2,180 bytes per CSV row for a 52-byte row in the file. The
  loop lag above the floor is GIL contention with the parsing thread. Dry-run
  (`?validateOnly=true`) is identical to a real import because the stub store
  ignores it: 1.48 s, 218,331,198 bytes.
- **Batch create** (`_checked_list :452-473`, `_list_guard :476-497`,
  `batch_create :653-668`): `await request.json()` (`:457`) parses the whole
  body and `items.validate_python(item)` (`:492`) validates every item, both
  **on the event loop**, then FastAPI validates the same body a second time
  (the `Body()` model), then the response dump (`:660`) also runs on the loop.
  Prototype, 100,000 items: 2.51 s wall, 342,693,092-byte peak, loop-lag
  maximum **1.26 s** (two heartbeats in the whole request); 10,000 items: 0.25
  s, 34,395,312 bytes, maximum 0.143 s. This is the one real
  event-loop-blocking outlier. Confirm which of the four stages (parse, guard
  validation, body validation, response dump) takes most of the 1.26 s, with
  evidence (for example a lag trace per stage in a throwaway test, or timing
  each stage on the same body), and record it.

The prototype figures above come from a run on this commit's tree (Apple M2 Pro,
macOS 27.2.1, Python 3.14.2, uv 0.13.8, other jobs possibly running); treat them
as hints, not the baseline. Your three-run table is the baseline.
