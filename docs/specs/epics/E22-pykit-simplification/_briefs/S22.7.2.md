# S22.7.2 — Implement bounded reporting

Brief for [S22.7.2](../F22.7-web.md#s2272-implement-bounded-reporting), written
at the S22.7.1 close.

## Goal

Make `run_checks_sync` report within one shared deadline without waiting for
stuck workers, on a process-wide bounded pool, as S22.7.1 settled. Exercise it
through direct calls and through Django readiness.

## Settled

S22.7.1's acceptance (owner, 2026-11-14), option A:

- One process-wide pool of at most 32 workers, created on first use. Requests
  never shut it down and never wait on a worker after the deadline.
- `deadline = time.monotonic() + timeout`, computed once per call. Each wait
  gets `max(0, deadline - time.monotonic())`.
- A slot is held from submission until the callable returns, released by the
  future's done callback. No queue: when no slot is free, that check gets
  `CheckResult(status="fail", reason="not run: health check capacity exhausted")`
  immediately.
- A timed-out check keeps `reason="timed out after {timeout:g}s"` (unchanged
  text), keeps running and keeps its slot.
- `timeout=None` waits indefinitely, as now.
- `run_checks` (async), `_run_one_sync`'s error handling, the `WebError` for an
  async check, aggregation and HTTP statuses do not change.
- No claim that a timeout cancels a callable (F22.7).

## Change

In `health.py`:

- Add one private module-level pool object holding the executor (32 workers), a
  slot counter guarded by a lock (or a non-blocking `threading.Semaphore`),
  and a method that submits a check if a slot is free, else returns `None`.
  Tests replace it with
  `monkeypatch.setattr(health, "<name>", <fresh object>)`, so give it a
  constructor that takes the worker cap.
- Rewrite `run_checks_sync`'s body to the settled contract. Keep its signature
  and the results' order and content.
- Docstring: state the shared deadline, the 32-worker bound, the capacity
  failure, and that a timed-out check keeps running and holding its slot.
- `packages/rn-forge-web/CHANGELOG.md`, `[Unreleased]`:
    - `### Fixed`: `run_checks_sync` returns at its deadline instead of waiting
      for stuck checks, and checks share one deadline.
    - `### Changed`: sync checks run on a shared 32-worker pool; a check that
      finds the pool full fails as `not run: health check capacity exhausted`.
- `packages/rn-forge-web/docs/guides/api-conventions.md:308-310` ("Each check
  runs with a 2-second timeout..."): say that all checks share one deadline,
  and add a bullet for the capacity-exhausted failure.

## Tests first

Each test releases its events in cleanup and waits for its workers to finish, so
no slot leaks into the next test. Tests that fill the pool use a fresh pool
object with a small cap via `monkeypatch`.

In `packages/rn-forge-web/tests/test_health.py`:

1. Remove the xfail markers from the two strict-xfail tests. They fail today as
   recorded above.
1. Replace `test_run_checks_sync_creates_a_pool_per_call` with
   `test_overlapping_blocked_calls_share_a_bounded_pool`. Use a pool capped at
   4 and 6 overlapping blocked calls, each with one check. Afterwards, at most
   4 checks have started, and the other two calls report the
   capacity-exhausted reason without waiting. The thread count grows by at
   most 4 pool workers plus the test's own caller threads. This fails today,
   because every call starts its own worker.
1. `test_a_full_pool_fails_the_check_without_queueing`: with a pool capped at 1
   and one blocked check holding it, a call with a passing check returns at
   once with that check failed, reason
   `not run: health check capacity exhausted`. Fails today: no cap.
1. `test_a_released_slot_is_reused`: after a blocked check is released and
   finishes, a new call on the cap-1 pool runs its check and passes. Expected
   to pass today (each call creates its own pool); keep it passing.

In `packages/rn-forge-django/tests/test_views.py`, `TestReadinessView`:

1. `test_a_blocked_required_check_reports_503_before_release`: use
   `readiness_view({"db": blocked, "cache": lambda: True}, required=["db"], timeout=0.05)`,
   where `blocked` waits on an event. The response arrives before the event
   is set, with 503 and `db` failed with `timed out after 0.05s`. Release in
   `finally`. Fails today: the view waits for release.
1. `test_a_blocked_optional_check_reports_200_before_release`: the same with the
   blocked check optional; expect 200. Fails today the same way.
