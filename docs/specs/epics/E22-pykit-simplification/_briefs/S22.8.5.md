# S22.8.5 — Share login admission between the adapters

Brief for
[S22.8.5](../F22.8-auth.md#s2285-share-login-admission-between-the-adapters), at
`20bb325`.

## Goal

`rn_forge.auth` owns what both adapters repeat after a verified login: resolving
the account, refusing a rejected or inactive one, building `SessionInfo` and
validating `return_to` (`admit_login`); reading the single transaction cookie
from raw `Cookie` headers (`TRANSACTION_COOKIE`, `transaction_cookie_value`);
and reading the string fields of a JSON login body (`json_string_fields`). The
FastAPI and Django route modules call them and keep session start, CSRF token
rotation, responses, form parsing, header access and rate limiting. No response,
audit event or log record changes.

## Settled

- Settled by the owner, 2026-11-16: the home is `rn_forge.auth`, not
  `rn_forge.web`. `rn_forge.web` is a dependency of `rn_forge.auth` and knows
  no accounts, contexts or sessions (ADR-0002 rules 1 and 2: place by
  signature).
- Settled by the reviewer, 2026-11-16: module placement. `admit_login` and its
  result `AdmittedLogin` go in a new module
  `packages/rn-forge-auth/src/rn_forge/auth/admission.py`, not in `flow.py`:
  `flow.py` imports neither `accounts`, `context` nor `audit` today
  (`flow.py:14-20`), and admission needs all three; a separate module keeps
  the flow free of account policy, as S22.8.2 did with `linking.py` and
  `records.py`. `TRANSACTION_COOKIE` and `transaction_cookie_value` go in
  `flow.py`, whose module docstring already describes the transaction cookie
  (`flow.py:3-7`) and which owns `LoginFailed`. `json_string_fields` goes in
  `local.py`, which holds the password provider whose form fields the JSON
  body stands in for. All five names are exported from
  `rn_forge/auth/__init__.py` and added to its `__all__` (README Conventions),
  in the sorted positions that file uses.
- Settled by the reviewer, 2026-11-16: the signature, all keyword-only after the
  first argument:
  `admit_login(completed: CompletedLogin, *, provider_id: str, accounts: AccountResolver, contexts: AuthorizationContextProvider, now: datetime, absolute_timeout: timedelta, return_to_prefixes: Sequence[str], default_return_to: str) -> AdmittedLogin`.
  `AdmittedLogin` is `@dataclass(frozen=True)` with `account_id: str`,
  `session: SessionInfo` and `return_to: str`, documented under `Attributes:`.
  `SessionInfo` is built exactly as both adapters build it now
  (`fastapi routes.py:455-467`, `django routes.py:355-368`):
  `session_version=context.session_version`, `provider=identity.provider`,
  `issuer`, `external_subject=identity.subject`, `created_at=now`,
  `expires_at=now + absolute_timeout`, `auth_time`, `amr`, `session_ref`,
  `id_token`. The audit events use the *provider_id* argument, as today, not
  `identity.provider`.
- Settled by the reviewer, 2026-11-16: raising. `AccountRejected` from
  `accounts.resolve(identity)` becomes
  `LoginFailed("account_not_provisioned", exc.reason)` after
  `audit("account.rejected", provider=provider_id, reason=exc.reason)`; an
  inactive context becomes
  `LoginFailed("access_denied", "account is not active")` after
  `audit("account.disabled", account_id=account_id, provider=provider_id)`.
  The audit event comes first, then the raise, as now. `admit_login` raises
  nothing else of its own; whatever `accounts.resolve` and `contexts.resolve`
  raise other than `AccountRejected` passes through.
- Settled by the reviewer, 2026-11-16: the "Login with … refused" warning stays
  in the adapters, and `login.success` stays in the adapters. What each emits
  today, read from the code: FastAPI `_LOGGER = logging.getLogger(__name__)`
  (`routes.py:76`), logger `rn_forge.fastapi.auth.routes`, call
  `_LOGGER.warning("Login with %s refused: %s", provider_id, reason)`
  (`routes.py:516`); Django `_LOGGER = AppLogger.get_logger(__name__)`
  (`routes.py:69`), logger `rn_forge.django.auth.routes`, call
  `_LOGGER.warning("Login with {} refused: {}", provider_id, reason)`
  (`routes.py:419`, brace style, rendered by the `AppLogger` record class,
  `commons/logging/logger.py:80-115,574-592`). Both render the same text,
  `Login with <provider> refused: <reason>`, at `WARNING`. They differ in
  logger name and, for Django, in the record class and call style. A single
  call in `rn_forge.auth` would give both one logger name
  (`rn_forge.auth.admission`), which changes the record (`name`, `module`,
  `pathname`) that an operator's logger filter or handler sees, so unification
  would change a log record. Decision: do not emit it in `admit_login`. Each
  adapter wraps the call:
  `except LoginFailed as exc: _LOGGER.warning(<its own form>, provider_id, exc.reason); raise`.
  The record, logger and rendered text stay identical; the audit event still
  precedes the warning, as now (audit inside `admit_login`, warning after it
  raises). `_refused` is deleted from both adapters. The wrapper must cover
  only the `admit_login` call, not `flow.complete`, whose own failures already
  log through `flow.py`. Django keeps the
  `# noqa: PLE1205  # brace-style log format` comment on its call.
- Settled by the reviewer, 2026-11-16: ordering. Both adapters today start the
  session first and compute `return_to` last (`fastapi routes.py:468-470`,
  `django routes.py:369-376`); `validate_return_to` is pure and `_return_to`
  already swallows `InvalidReturnTo`, so `admit_login` computing it before the
  session starts is not observable. `login.success` stays after the session
  starts (and, in Django, after `rotate_token`): adapter order is
  `admit_login`, session start, `rotate_token` (Django),
  `audit("login.success", ...)`, response. `now` is read by the adapter with
  `self.sessions.now()` immediately before `admit_login`; today it is read
  after the two resolvers and only on the success path. That moves one clock
  read earlier and onto the refusal path; no test counts clock reads, and the
  FastAPI and Django test clocks are fixed or advance only on explicit steps
  (check the clock fixtures of both `tests/auth/test_routes.py` while
  implementing; if one counts calls, pass the clock reader instead and tell
  the reviewer).
- Settled by the reviewer, 2026-11-16: `TRANSACTION_COOKIE = "__Host-login-tx"`,
  with its docstring, moves to `rn_forge.auth.flow`. Both adapters import it
  from `rn_forge.auth`. No alias is left: it is removed from
  `rn_forge/fastapi/auth/routes.py`, the `__all__` of `routes.py`,
  `rn_forge/fastapi/auth/__init__.py` (lines 27 and 47),
  `rn_forge/fastapi/__init__.py` (lines 10 and 65),
  `rn_forge/django/auth/routes.py` and its `__all__`, and
  `rn_forge/django/auth/__init__.py` (lines 12 and 30) (ADR-0002 rule 5). The

  `packages/rn-forge-fastapi/tests/auth/test_routes.py:36` and
  `packages/rn-forge-django/tests/auth/test_routes.py:43`; grep
  `TRANSACTION_COOKIE` over `packages docs` shows no other code and no package
  docs page names the symbol (the guides name the literal `__Host-login-tx`,
  so they stay). Spec pages other than this brief's `## Result` are not

- Settled by the reviewer, 2026-11-16:
  `transaction_cookie_value(headers: Iterable[str]) -> str | None` takes raw
  `Cookie` header values. It splits each on `;`, partitions on the first `=`,
  compares the stripped name to `TRANSACTION_COOKIE` exactly, strips the
  value, returns the one value or `None`, and raises
  `LoginFailed("login_failed", "more than one transaction cookie")` for two or
  more, in one header or across headers. The body is the existing
  comprehension, moved unchanged. FastAPI passes
  `request.headers.getlist("cookie")`; Django passes
  `[request.META.get("HTTP_COOKIE", "")]`. The two `_transaction_cookie` methods
  are deleted and their callers call the function. The reason that Starlette
  and Django keep one value per name goes in a `#` comment in the new function,
  not the docstring.
- Settled by the reviewer, 2026-11-16:
  `json_string_fields(body: bytes | str) -> dict[str, str]` returns the
  string-valued members of a JSON object, with names as `str`; `{}` for
  invalid JSON (`ValueError`, which includes `UnicodeDecodeError`) and for a
  document that is not an object. The body is the existing JSON branch of
  `_credentials`, moved unchanged including its `pyright: ignore` comments.
  Django passes `request.body`, FastAPI the awaited `request.body()`. Each
  adapter keeps its own `_credentials` (the media-type test,

  the JSON branch. The `json` import leaves both route modules if nothing else
  uses it (FastAPI: only `routes.py:675` does).
- Settled by the reviewer, 2026-11-16: the adapters keep session start,
