# S22.8.4 — Decide the retention bound

Brief for [S22.8.4](../F22.8-auth.md#s2284-decide-the-retention-bound), at
`01a8985`.

## Goal

This is a decision story. It does not pick the bound. Build an injected-clock
churn measurement and a reproduction of today's unbounded retention for
`AuthorizationContextCache`, record the baseline, and write an options
comparison in `## Result` for the owner to choose from. S22.8.1 implements the
choice. No production behaviour changes in this story.

## Settled

- Settled by the reviewer, 2026-11-16: no clock seam is needed.
  `AuthorizationContextCache.__init__` already takes
  `clock: Callable[[], float]` (`context_cache.py:109-128`, default
  `time.monotonic`) and `resolve` reads it once per call (`:133`). The tests'
  `Clock` (`tests/test_context_cache.py:15-21`) is the pattern. Add no source
  and change no signature.
- Settled by the reviewer, 2026-11-16: churn shape. A new account is resolved at
  each step; the clock advances 1.0 s per step; the default `ttl` of 60 s; a
  provider that returns a fresh
  `AuthorizationContext(active=True, session_version=1)` per call. Step `i`
  resolves account `f"a{i}"`, so every account is distinct and none is
  requested again. Sizes: 1,000, 4,000 and 16,000 accounts (the sizes S22.8.3
  uses for stores). Two more cases at 16,000 steps:
    - invalidated: as above, and `cache.invalidate(f"a{i}")` follows each resolve,
      so the version counters also grow;
    - hot set: each step resolves a new cold account `f"c{i}"` and then one of 20
      hot accounts, `f"h{i % 20}"`. A hot account recurs every 20 s, inside the
      ttl, but `ttl` counts from `stored_at` and a hit does not refresh it, so
      each hot account still misses once per 60 s. The count of provider calls
      is the figure that shows whether a bound evicts entries that are still in
      use.
- Settled by the reviewer, 2026-11-16: what is recorded, per case, through the
  `measure(case, inputs, kind)` fixture with kind `"cpu"`:
    - entry count retained over time: `counts["entries_q1"]` to
      `counts["entries_q4"]`, `len(cache._entries)` after 25%, 50%, 75% and 100%
      of the steps, and `counts["entries_end"]`; `counts["live_end"]`, the
      entries with `clock.now - stored_at < 60.0` at the end;
    - peak traced memory: the fixture's `peak_bytes`; and
      `counts["retained_bytes"]`, `tracemalloc.get_traced_memory()[0]` read
      inside the measured block after the last step;
    - lock hold time: the cache's `_lock` is replaced before the block by a small
      test-local `_TimedLock` that wraps the real lock. Its `__enter__` acquires
      the real lock and stores `time.perf_counter()`; its `__exit__` computes
      `time.perf_counter() - stamp`, releases the real lock, and updates a
      running `max`, a running `total` and a count of acquisitions (no
      per-acquisition list, so the proxy adds no memory growth). Hold time is
      the time between acquiring and releasing, not the time waiting to acquire
      (one thread, so none). Recorded as `counts["lock_acquisitions"]`,
      `counts["lock_hold_max_s"]` and `counts["lock_hold_total_s"]`. It runs
      under `tracemalloc`, which the fixture always starts, so absolute figures
      are inflated; they are comparable only to each other;
    - the invalidated case also records `counts["version_accounts"]`,
      `len(cache._versions._accounts)`, and the hot-set case records
      `counts["provider_calls"]` and `counts["entries_end"]`.
- Settled by the reviewer, 2026-11-16: the figures go in
  `docs/guides/performance-baselines.md`: a new
  `### S22.8.4 authorization-context churn baseline` section (a commit table
  with CPU, OS, Python and uv as the guide says, at the checkout the runs
  used) and a new Workloads row,
  `Auth | Authorization-context cache churn with an injected clock | 1,000 to 16,000 distinct accounts, plus a hot-set case; entries retained, lock hold | CPU`.
  Keep the existing Auth row.
- Settled by the reviewer, 2026-11-16: no production behaviour changes in this
  story: `context_cache.py`, the package `__init__`, `CHANGELOG.md` and every
  other source file stay as they are. The tests read the private `_entries`,
  `_lock` and `_versions._accounts`; tests are outside pyright
  (`pyproject.toml:57-60` ignores `tests`) and nothing public exposes
  retention.
- Settled by the reviewer, 2026-11-16: the reproduction is a characterization
  test in the ordinary suite that asserts today's growth, not an `xfail`. A
  strict `xfail` would need an assertion about the bound, and the bound is the
  open decision, so it would pin an invented number. The characterization test
  states a fact that holds today, passes the gate, and fails the moment
  S22.8.1 bounds retention, so S22.8.1 must replace it with its own assertion
  (its acceptance requires a documented finite bound).
- Settled by the reviewer, 2026-11-16: eviction never touches versions.
  `InMemoryAuthorizationVersions._accounts` (`:48`) grows with every account
  ever bumped (`:59`). Removing a counter resets it to 0, and a cache that
  shares the versions could then see an old entry stamped `(0, g)` as current:
  a stale context becoming current. So no option may prune the version
  counters. Their growth is measured here (invalidated case) and reported as a
  separate, unbounded figure; whether it needs a bound is an owner question
  for the Result.

## Current behaviour

`packages/rn-forge-auth/src/rn_forge/auth/context_cache.py`:

- `_Entry` (`:80-83`) holds the context, the `(account, global)` version pair
  and `stored_at`. `_entries: dict[str, _Entry]` (`:128`) has one entry per
  account.
- `resolve` (`:130-147`): reads versions (`:132`) then the clock (`:133`); a
  `get` under `_lock` (`:134-135`); returns the entry when its versions equal
  the current ones and `now - stored_at < ttl` (`:136-141`); otherwise calls
  the provider outside the lock (`:144`) and stores `_entries[account_id]`
  under `_lock` (`:145-146`). Nothing ever deletes an entry. An expired entry
  stays until the same account is resolved again.
- `invalidate` and `invalidate_all` (`:149-155`) only bump counters
  (`InMemoryAuthorizationVersions.bump`, `:56-59`; `bump_all`, `:61-63`); they
  do not touch `_entries`. The lock is a `threading.Lock`; critical sections
  are one dict `get` or one dict assignment, so a hold is O(1).
- Existing tests (`tests/test_context_cache.py`, all passing) cover hit, per
  account and global invalidation, ttl expiry, writer paths, ttl validation
  and shared versions. None observes retention. There is no `tests/measure`
  case for this cache; the existing cases are `test_key_refresh.py`
  (`auth_key_refresh`) and `test_contract.py`.

Verified by running equivalents on this commit (the shapes above, scratch files
removed afterwards):

- Plain churn: entries after each quarter are exactly a quarter of the steps and
  the end count equals the step count: 250/500/750/1,000 for 1,000 accounts,
  4,000 at the end for 4,000, and 4,000/8,000/12,000/16,000 for 16,000.
  `live_end` is 60 in every case. Re-resolving an expired account (`a0`)
  leaves the count unchanged: the bound today is the number of distinct
  accounts ever requested.
- Memory at 16,000 accounts: `peak_bytes` 6,919,214 and `retained_bytes`
  6,918,966; at 4,000, 1,598,798 and 1,598,550; at 1,000, 365,502 and 365,254
  (growth is linear, about 430 bytes per entry).
- Lock: `lock_acquisitions` is 2 per miss (32,000 at 16,000 accounts);
  `lock_hold_max_s` was about 4.7e-05 s, `lock_hold_total_s` about 0.025 s.
  These are indicative; the implementer records its own five runs.
- Hot set: `entries_end` 16,020 and `provider_calls` 21,340 (16,000 cold, plus
  each of the 20 hot accounts missing once per 60 s: 5,340).

## Result

Fill in this section; do not choose for the owner.

1. Commands and exit codes, the baseline commit, CPU/OS/Python/uv, and the
   five-run baseline table per case (the figures that go in the performance
   guide).

1. The options comparison, one row per option, with these columns: retention
   bound (entries, and what it depends on), memory at 16,000 accounts
   (prototype peak and retained bytes), lock hold (maximum and total), hot-set
   provider calls, interaction with version invalidation (state why a stale
   context cannot become current), implementation size and complexity, and any
   new public surface:

    - A: expire on insert, full sweep. When `now >= next_expiry` (a lower bound
      on every stored expiry, as S22.8.3 does for the stores), rebuild
      `_entries` without entries whose age is `>= ttl`, under the lock. Bound:
      the accounts resolved within one `ttl` plus those since the last sweep;
      no hard cap, so a burst can exceed it.
    - B: expire from the front. Store with pop-then-insert so insertion order is
      `stored_at` order (a dict overwrite keeps its old position), and on each
      insert pop expired entries from the oldest end until one is live.
      Amortized O(1); hold is O(k) for k expired entries. Same bound as A, no
      hard cap.
    - C: LRU `max_entries` (an `OrderedDict`, `move_to_end` on a hit, evict the
      oldest when over the cap). Hard cap; an expired entry can stay until it
      is pushed out; a hit now writes under the lock; a new public parameter
      and its default are a decision.
    - D: B plus C: expire from the front and cap at `max_entries`. Hard cap and
      prompt expiry, at the cost of both mechanisms.

    Each row must also say what the option does to a hit that no longer happens
    at TTL boundaries (the hot-set case), and whether an evicted account's next
    `resolve` recomputes under the current versions.

1. The unbounded version-counter growth: the invalidated case's
   `version_accounts` and bytes, and whether it needs its own decision.

1. Implementer's recommendation (one option, one paragraph, with the evidence it
   rests on), marked as input to the owner.

1. Anything the owner must settle (for example the `max_entries` default and
   whether a new public parameter is acceptable).
