Keep the ORM layer small; make bulk-upsert cost and concurrency claims match
what it can guarantee.

## Context

`upsert.py:61-82` builds keyed input, reads existing rows, builds a complete
write list and then executes an upsert. `_existing` chunks reads at a fixed 900
parameters (`:133-155`). The docstring calls counts exact although
classification happens before the write. Existing tests cover 33,000 rows and
composite keys but not competing writers. The package is only 679 source lines;
broad module splitting has no demonstrated benefit.

## S22.11.1 — Settle count semantics and resource targets

**State:** New

Compare two-session concurrent upserts with serial execution on supported
dialects. Specify whether counts describe the pre-write snapshot or require
serialization. Measure allocations/query counts for empty, unchanged, mixed and
large input.

**Acceptance:**

- A decision story records observed competing-writer outcomes and chooses
  accurate documentation or a justified transaction strategy before changing
  the algorithm.
- Baseline includes both single and composite keys, audit preservation, rollback
  and duplicate rejection.
- An invalid empty key produces a deliberate documented error rather than
  division by zero; valid empty input does no unnecessary query.

## S22.11.2 — Remove measured bulk overhead

**State:** New

Use the measured result to reduce repeated materialization or bound writes
without changing duplicate-key detection, skipped-row behavior or caller-owned
transactions. Retain the focused SQLite and Alembic wrappers unless a concrete
defect is found.

**Acceptance:**

- Large input has a recorded peak-memory/query comparison; the change meets the
  resource target settled in S22.11.1.
- SQLite and PostgreSQL cases preserve counts under the chosen semantics, audit
  columns, composite keys and rollback; PostgreSQL evidence comes from its
  actual integration service.
- Keyset null ordering, mixed directions, malformed cursor rejection and
  page-token compatibility remain covered.

## Acceptance

- S22.11.1: A decision story records observed competing-writer outcomes and
  chooses accurate documentation or a justified transaction strategy before
  changing the algorithm.
- S22.11.2: Large input has a recorded peak-memory/query comparison; the change
  meets the resource target settled in S22.11.1.
