The release cut takes every open Dependabot update, so no Dependabot pull
request is left open against `main`.

## Context

On 2026-11-21, after Release 11 merged, Dependabot opened pull request #42,
"Bump the python group across 1 directory with 7 updates":

| Package | Requirement floor | Member |
| -- | -- | -- |
| authlib | 1.9.1 to 1.9.5 | `rn-forge-auth` |
| typer | 0.26.8 to 0.29.1 | `rn-forge-cli` |
| tomlkit | 0.15.0 to 0.15.2 | `rn-forge-commons` |
| pandas | 3.0.3 to 3.1.1 | `rn-forge-data`, `pandas` extra |
| packaging | 24 to 26.3 | `rn-forge-devops` |
| django | 6.0.7 to 6.1.3 | `rn-forge-django` |
| fastapi | 0.141.1 to 0.162.7 | `rn-forge-fastapi` |

`uv.lock` moves with them, and moves transitive packages too (for example celery
5.7.0, billiard 4.3.2 and amqp 5.4.2).

The update lands on the release branch, not by merging the pull request into
`main`, as in
[F26.1](../E26-release-11-maintenance/F26.1-dependency-updates.md): a merge into
`main` starts a release run for every package whose manifest changed. Dependabot
closes the pull request once `main` carries its update.

Decision: Dependabot stays automatic against `main`, and the release cut absorbs
its updates. A `target-branch` in the generated `dependabot.yml` is rejected: it
names one fixed branch, so every release would need an edit to a generated file.
The generic rule is proposed upstream in kiln.

## S29.1.1 — The release runbook absorbs Dependabot updates

**State:** Closed (2026-11-21)

**Acceptance:**

- The release runbook's "Before the merge" steps include taking the open
  Dependabot updates on the release branch.
- The Release 12 page carries the standing exit criterion that no Dependabot
  pull request is open against `main`, or each open one is listed there as
  deferred with its reason.

## S29.1.2 — Take the Dependabot updates

**State:** New · **Depends on:** —

**Acceptance:**

- Every update in the Context table is in the members' `pyproject.toml` files
  and in `uv.lock`, at the version pull request #42 names or later.
- Anything the bumps break is fixed in the code, not by pinning the old version.
- Each released package whose runtime or extra requirement changed has a patch
  bump and a `CHANGELOG.md` entry moved from `[Unreleased]` under its new
  version: `rn-forge-auth` 0.2.2, `rn-forge-cli` 0.2.2, `rn-forge-commons`
  0.10.2, `rn-forge-data` 0.1.7, `rn-forge-devops` 0.5.1, `rn-forge-django`
  0.7.1 and `rn-forge-fastapi` 0.5.3. `rn-forge-devops` and `rn-forge-django`
  were not in Release 11's published set, because nothing in them changed;
  their current versions, 0.5.0 and 0.7.0, are their last releases.
- `task validate` passes.
