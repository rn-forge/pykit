Entry criteria: the work runs first as kiln's S7.2.4 rehearsal, from kiln
`feature/v1` on the cutover branch, and merges only once `[kiln] ref = "v0.1.0"`
and `kiln apply` re-renders (S16.3.1).

pykit adopts kiln's `python-lib` archetype in place: `kiln init`, then kiln's
generated CI replaces `main.yml`, with the docs already in kiln's format
(S16.3.3). The cutover follows `rn-forge-devops` and `rn-forge-data`, so kiln
renders their members, Sonar sources and import contracts from the start.
`rn-forge-auth` ([F13.2](../E13-auth/F13.2-auth-package.md)) may land before or
after the cutover; whichever lands second lists it in the kiln config, through
the [adding a package](../../../runbooks/adding-a-package.md) step below.

## Context

This is the one Release 8 feature that waits on another repository's software:
pykit cannot merge the cutover before kiln's `v0.1.0` tag exists. The
dependency is a version pin and an observable entry criterion, not acceptance
checked in kiln, so [ADR-0008](../../../adr/ADR-0008.md) still holds for every
acceptance line.

What pykit sets, and what it stops owning:

| pykit sets in `.rn-forge/kiln/config.toml` | Why |
| -- | -- |
| `archetype = "python-lib"`, `packages` = all ten workspace members | The workspace kiln renders for. The derived nav lists the package sites in this order, so it keeps the hand nav's: commons, cli, django, fastapi, sqlalchemy, tooling, web, devops, data, then auth. |
| `modules` = `rn_forge.<name>` for each member | pykit's members are namespace packages (kiln S6.1.3). |
| `import_contracts = "own"` | pykit's `.importlinter` contracts describe its layering; kiln's generic workspace contracts forbid it (kiln S6.1.4). pykit's contracts, including E15's per-package adapter contracts and `rn-forge-devops`'s contracts, move below kiln's END marker. |
| `[ci] release = "pypi"` | `python-lib` defaults to `tag-exists`, which renders none of [F21.3](../E21-pypi-distribution/F21.3-publish-from-release.md)'s publishing. `init` does not set it. |

[Adding a package](../../../runbooks/adding-a-package.md) gains a step: add the
member to `packages` and `modules` in `.rn-forge/kiln/config.toml`. A
repository-owned check that E15 adds, such as S15.1.2's adapter-to-extra check
if it is not in the planner, is wired through `[tasks] extra_refs`.

| pykit stops owning | Replaced by |
| -- | -- |
| `.github/workflows/main.yml`, and the hand-written `.github/actions/setup/action.yml` | kiln's generated `ci.yml`, and the setup action kiln renders in place of pykit's (a generated file, with kiln's provenance header). `ci.yml` runs kiln's planner, `kiln-devops`, through `task ci:*` (kiln F6.7); S16.3.4 removes pykit's copy. |
| The package-site deploy in `main.yml`'s `docs` job (versioned sites at `packages/<package>/latest/`) | The `docs` job of kiln's generated `ci.yml`, after `release`, which deploys the versioned package sites with mike. kiln renders no separate `docs.yml` for `python-lib`. |
| `.github/dependabot.yml` for GitHub Actions | kiln's pin table, through kiln upgrades; a Dependabot PR would edit a generated file (kiln F6.3). Hand-written workflows are the exception (S16.3.2) |
| Direct `uv run …` gates in docs and CI | `task` verbs (`setup validate lint format typecheck test …`) |
| `sonar-project.properties` sources passed by CI | kiln's template lists them from `packages` (kiln ADR-0014) |
| `docs/_update_board.sh` and pykit's own area rules | kiln's `docs:generate` derived regions and kiln's `_structure.md` files; pykit's specs and release pages already follow kiln's work model (S16.3.3) |

`kiln init` changes `pyproject.toml` only to add the task tools it lacks to its
dependency groups (kiln S6.6.2), so these stay as they are. The cutover must not
replace them with kiln's defaults:

| pykit keeps | Why |
| -- | -- |
| The root `[tool.ruff.lint.per-file-ignores]`, `[tool.ruff.lint.isort]` and `[tool.ruff.lint.flake8-bugbear]` tables, verbatim | A member has no `[tool.ruff]` table, so ruff applies the root's in a member-directory run. With kiln's default test ignore and no `known-third-party` or FastAPI immutable calls, every member fails `ruff check`. |
| The root `conftest.py` and the root pytest markers | The scaffold suite runs from the root ([F16.4](F16.4-member-gate.md)). |
| `packages/rn-forge-web/docs/guides/examples/` | `rn-forge-web`'s tests execute `asgi_app.py`, and the guides include all three examples. |
| `broker-profile.yml`, `internal-ranges.yml`, `umbrella-release.yml` and `scorecard.yml` | Hand-written workflows for work `ci.yml` does not do. Each stays, and S16.3.2 changes the first three to meet kiln's rules. |

## S16.3.2 — Generated CI replaces `main.yml`

**State:** New · **Depends on:** S16.3.1

**Build:**

- With `[ci] release = "pypi"`, the pinned kiln version renders this behaviour,
  which pykit requires in full:
    - each per-package task takes the member's `dir` from the plan matrix
      (`PACKAGE_DIR`), not from a hard-coded layout
    - `release` publishes only on a push to the default branch and waits on Sonar;
      a pull request's packaging check is `smoke`, not `release`
    - `ci.yml` has a `docs` job after `release` that deploys the versioned package
      sites with mike (`task ci:docs-publish`), and no separate `docs.yml` is
      rendered
    - a `redis` job, as kiln's `python-lib` renders it (kiln F6.8)
    - [F21.3](../E21-pypi-distribution/F21.3-publish-from-release.md)'s release
      behaviour:
        - `twine check --strict` on every build;
        - a trusted-publishing upload to PyPI under environment `pypi`, made before
          the GitHub release and skipped when PyPI already has the version;
        - a `testpypi` manual dry run;
        - PEP 740 attestations signed before upload (`task ci:release-sign`);
        - per-package GitHub releases with `--latest=false` and the package's
          changelog section as notes, from `kiln-devops notes`;
        - `external-install` from PyPI
- Before the merge, the owner adds a trusted publisher for workflow `ci.yml` on
  pypi.org (environment `pypi`) and test.pypi.org (environment `testpypi`) for
  each package, beside the `main.yml` ones F21.1 created.
- kiln's `kiln-devops` is the `rn-forge-devops` 0.3.1 planner (kiln F6.7 and
  F6.8), so the matrices kiln reads include the no-extras smoke entry.
- `.rn-forge/kiln/config.toml` declares `[[ci.jobs]] name = "internal-ranges"`,
  `uses = "./.github/workflows/internal-ranges.yml"`, and
  `[[ci.jobs]] name = "umbrella-release"`,
  `uses = "./.github/workflows/umbrella-release.yml"`, `events = ["push"]`,
  `contents = "write"`
  ([F21.3](../E21-pypi-distribution/F21.3-publish-from-release.md)). A caller's
  permissions cap the called workflow, so without `contents = "write"`
  `gh release create` gets a 403.
- `dependency-audit`, `licenses` and `secret-scan`, inline jobs in `main.yml`,
  stay pykit's. They move into a pykit-owned workflow with
  `on: workflow_call` (one, or one each), declared as `[[ci.jobs]]` entries,
  since `[[ci.jobs]]` only calls workflows. They are declared jobs, so kiln's
  generated `ci-ok` needs them. `scorecard.yml` and `broker-profile.yml` stay.
- Open, settled by the rehearsal: the hand-written workflows' action pins are
  not in kiln's pin table, and kiln's `dependabot.yml` watches only hook
  directories and uv. pykit keeps a repository-owned Dependabot
  `github-actions` entry for `.github/workflows/` if kiln's generated
  `dependabot.yml` lets one coexist; otherwise the pins are bumped by hand at
  each kiln upgrade.
- A pykit-owned task file, included through `[tasks] includes`, holds a task for
  each hand-written workflow's direct `uv` step, so `ci-entrypoint` passes:
    - `internal-ranges.yml`: `uv run rn-forge-devops requirements`;
    - `broker-profile.yml`:
      `pytest packages/rn-forge-auth -m broker -p no:randomly`; the Docker
      Compose steps stay in the workflow;
    - `umbrella-release.yml`:
      `git ls-remote … | uv run rn-forge-devops umbrella …`, with the pipe
      inside the task, writing to `$GITHUB_OUTPUT`.
- Those three workflows pass `github-token` to the generated setup action and
  run `task setup` after it, since it installs only uv and go-task.
  `umbrella-release.yml` drops its `sync` input.
- Delete `.github/workflows/main.yml`, including its `notes` call and its
  package-index step. Keep `.github/actions/setup/action.yml`:
  `kiln init` replaced it with kiln's generated setup action, which `ci.yml`
  uses, and deleting it would be drift.

**Acceptance:**

- `main.yml` no longer exists, and `kiln doctor . --full` exits 0 with no
  finding.
- A pull request run and a run on `main` pass; `ci-ok` is the only required
  check.
- After the run on `main`, each package's site is served at
  `packages/<package>/latest/` beside the root site.
- The workflow that holds `dependency-audit`, `licenses` and `secret-scan` is
  declared in `[[ci.jobs]]`, and `ci-ok` needs those jobs.
- The run on `main` runs `internal-ranges` and `umbrella-release`, and a manual
  run of `broker-profile.yml` passes.

Do not merge this story's change while both `main.yml` and kiln's `docs.yml`
exist: each push to `main` would run two Pages deploys in the `pages`
concurrency group, and the root-only deploy landing last would remove the
package sites from the live site. The `docs` job above is why the two never
coexist.

  maintainer (owner accepted, 2026-11-03). Every declaration's floor is
  `assertpy>=2.35`, and the lock moved from 1.1.
- `testing.py` casts the result of the positional call `assert_that(val,
  description)` to `Any`: with an `Any` argument, assertpy 2's overloads resolve
  to Unknown under pyright strict.
- `TruncateModelMixin.truncate` runs the statements of Django's
  `connection.ops.sql_flush`, so pykit formats no SQL. `SequenceGenerator`
  composes its two statements with `psycopg.sql.Identifier`, imported on the
  PostgreSQL path only, because psycopg is not a runtime dependency.
- The PostgreSQL-marked tests were not run locally; the cutover's pull request
  run covers them with the Sonar gate.
- 2026-11-03: pyright 0 errors; commons and django 1,820 passed, 8 skipped.
