Entry criteria: the work runs first as rehearsals from kiln `feature/v1` on the
cutover branch, and merges only once `[kiln] ref = "v0.1.0"` and `kiln apply`
re-renders (S16.3.1). This page holds the whole cutover, so it can be rerun from
the page alone, many times, before the cutover merges: the `kiln new` input
(three files beside this page), every step as a script and the acceptance block.
kiln keeps only the general
[cutover runbook](https://github.com/rn-forge/kiln/blob/main/docs/runbooks/cutover.md),
and its S7.2.4 is a gate that links here.

The cutover runs on kiln's `feature/v1` before kiln tags `v0.1.0`, with
`[kiln] ref = "feature/v1"`, so kiln keeps being refined from pykit's findings.
Once the tag exists, `[kiln] ref` becomes `"v0.1.0"` and `task kiln:apply`
re-renders. The steps are S16.3.1's numbered list; a rerun follows them
verbatim.

The order of the branches and commits:

1. `feature/release-8` holds the spec commits, this page among them.
1. `feature/kiln-cutover` is cut from it with
   `git switch --no-track -c feature/kiln-cutover feature/release-8`; a
   tracking branch would push straight to the release branch. Its commits, in
   order: "F16.3 Refinement" (these docs), S16.3.11 (the format commit),
   S16.3.12 (the derived-region commit), S16.3.1's groups with the
   documentation first, so the largest mechanical difference is reviewed
   first, then the post-cutover stories.
1. `feature/kiln-cutover` merges back into `feature/release-8` with
   `git merge --no-ff`, so the release branch shows the cutover as one branch.
   That merge may happen before kiln's tag. Only `feature/release-8` → `main`
   waits for `v0.1.0` and the `[kiln] ref` bump.

kiln's generated `ci.yml` runs on pull requests to `main` and pushes to `main`
only, so every acceptance line that needs a GitHub run (S16.3.2's pull request
and `main` runs, S16.3.5's Sonar gate) is observed on the `feature/release-8` →
`main` pull request.

pykit adopts kiln's `python-lib` archetype in place. S16.3.1 is an overlay: it
copies what kiln owns from a reference repository that `kiln new` built, applies
pykit's nuances as explicit steps, and keeps pykit's git history. kiln's
generated CI then replaces `main.yml` (S16.3.2), with the docs already in kiln's
format (S16.3.3). The cutover follows `rn-forge-devops` and `rn-forge-data`, so
kiln renders their members, Sonar sources and import contracts from the start.
`rn-forge-auth` ([F13.2](../E13-auth/F13.2-auth-package.md)) may land before or
after the cutover; whichever lands second lists it in the kiln config, through
the [adding a package](../../../runbooks/adding-a-package.md) step below.

pykit cannot merge the cutover before kiln's `v0.1.0` tag exists. The dependency

## S16.3.11 — Format to kiln's formatters ahead of the overlay

**State:** New · **Depends on:** none · pre-cutover

This is pykit's application of step 2 of
[kiln's cutover runbook](https://github.com/rn-forge/kiln/blob/main/docs/runbooks/cutover.md).
kiln's `task format` rewraps Markdown, TOML and YAML that pykit's own formatter
left alone, and without this story every rerun of S16.3.1 carries those hunks in
files pykit owns, which buries the overlay's real diff. The story reformats
those files once, in a commit of their own on `feature/kiln-cutover`, right
after the "F16.3 Refinement" commit, so the overlay's diff is only what kiln
owns and the nuances.

It extends S16.3.3 (Closed, "Docs format ahead of `kiln init`"), which did the
same for Markdown: this story adds TOML and YAML and takes kiln's current
formatter configuration, which includes `yamlfmt`. It is the step a rerun of
S16.3.1 does not repeat.

**Steps.** Start on `feature/kiln-cutover` right after the "F16.3 Refinement"
commit, with a clean worktree and the reference built (S16.3.1, "The input"). No
branch is cut and nothing is rebased. Run every command from the repository
root.

1. [`format.sh`](F16.3-cutover/format.sh) takes the patch path, which must be
   outside the repository. It runs S16.3.1 steps 01 to 04 (which bring kiln's
   files and its formatter configuration: `.editorconfig`, `.mdformat.toml`,
   `.taplo.toml`, `.yamlfmt.yaml`), saves `git status --porcelain` as
   `<patch-path>.overlay`, runs `task setup` and `task format`, writes the
   `git diff` of the changed `*.md`, `*.toml`, `*.yml` and `*.yaml` paths that
   are not on the overlay list to `<patch-path>`, prints the files in it, and
   stops. It resets and cleans nothing. Between `task setup` and `task format`
   it installs `google-yamlfmt==0.21.0` into the throwaway environment: the
   root `pyproject.toml` gains that tool only in step 6, and the next
   `task setup` removes it.
1. Throw the overlay away: `git reset --hard && git clean -fd`.
1. Apply the patch: `git apply <patch-path>`. Check that `git status --short`
   lists only `*.md`, `*.toml`, `*.yml` and `*.yaml` files, and none of the
   paths in `<patch-path>.overlay`.
1. Commit by path as `S16.3.11`:
   `git commit -m S16.3.11 -- $(git diff --name-only)`.
1. The existing gate cannot pass, and this story records that. Under pykit's old
   `.mdformat.toml`, `uv run mdformat --check docs` already fails on 26 files
   at `2d2fdbc` (24 at `fb95c40`, and 2 more from the F16.7 and F18.6 pages),
   so the old gate fails before this story. This story is what clears them.
   The commit stays on `feature/kiln-cutover`: it does not merge into
   `feature/release-8` ahead of the cutover.

### Run it

```bash
PATCH="$HOME/pykit-s16.3.11.patch"
bash docs/specs/epics/E16-kiln-adoption/F16.3-cutover/format.sh "$PATCH"
```

Inspect the files it prints: every one is a `*.md`, `*.toml`, `*.yml` or
`*.yaml` file pykit owns, and `"$PATCH.overlay"` holds the overlay's paths.
Then, one command at a time:

```bash
git reset --hard && git clean -fd
git apply "$PATCH"
git status --short
git commit -m S16.3.11 -- $(git diff --name-only)
```

Inspect `git status --short` before the commit and `git show --stat HEAD` after
it.

Redo the story only when kiln's formatter configuration (`.editorconfig`,
`.mdformat.toml`, `.taplo.toml`, `.yamlfmt.yaml`) or the formatter pins change.
A rerun of S16.3.1 starts from this commit and does not repeat it.

**Acceptance:**

- The commit changes only `*.md`, `*.toml`, `*.yml` and `*.yaml` files:
  `git diff --name-only HEAD~1 HEAD | rg -v '\.(md|toml|ya?ml)$'` prints
  nothing.
- No file on the overlay's path list changes:
  `git diff --name-only HEAD~1 HEAD | grep -cxF -f <(sed 's/^...//' "$PATCH.overlay")`
  prints `0`.
- pykit's existing gate on that commit is not expected to pass (step 5 above).
- A rerun of S16.3.1 from it shows no formatting-only hunk in a file pykit owns.

## S16.3.12 — Specs take kiln's derived regions

**State:** New · **Depends on:** S16.3.11 · pre-cutover

kiln's `task docs:generate` fills only fences it finds. Without a
`<!-- BEGIN derived board -->` fence in `docs/specs/index.md` it skips every
spec region, and `kiln doctor` skips the work-model checks too; pykit's
`board:start` and `scope:start` fences are the old script's. So without this
story the cutover's step 13 would update nothing, and deleting
`docs/_update_board.sh` (step 5) would leave no generator. The story puts kiln's
fences in and fills them, in a commit of its own right after S16.3.11, so
S16.3.1 carries no spec-table noise.

What kiln derives, and from where:

| Region | Page | Fence | Table, and its source |
| -- | -- | -- | -- |
| Board | `docs/specs/index.md` | `derived board` | Releases (status, feature counts by state) and the Backlog of features with no Iteration, from the release and feature pages. |
| Epic list | `docs/specs/epics/index.md` | `derived epics` | One table per range of ten epics: state, feature counts and iterations, from the epic and feature pages. |
| Features | each epic page with `F*.md` files | `derived features` | Feature (the file's title), State, Iteration and story counts. No summary column. |
| Stories | each feature page | `derived stories` | Story, State and Depends on, from the `## S… — title` headings and each `**State:**` paragraph. |
| Scope | each release page | `derived scope` | Feature (the file's title), Epic and State, for the features whose `Iteration` names the release. |

The fences are `<!-- BEGIN derived <name> -->` and
`<!-- END derived <name> -->`. `docs:generate` inserts the features and stories
fences after the metadata table when a page lacks them, but needs the board
fence first, and the epics and scope fences must already exist (a doctor finding
otherwise). An epic with no `F*.md` file keeps its hand-written table, and a
hand-written row whose ID has a file is a doctor error.

**Steps.** Start on `feature/kiln-cutover` right after the S16.3.11 commit, with
a clean worktree. Run every command from the repository root.

1. [`derive.sh`](F16.3-cutover/derive.sh) takes the patch path, which must be
   outside the repository. It runs S16.3.1 steps 01 to 04, saves
   `git status --porcelain` as `<patch-path>.overlay`, runs `task setup` and
   installs `google-yamlfmt==0.21.0` as `format.sh` does. It renames the board
   and scope fences, rewrites the board page's sentence to say
   `task docs:generate`, removes each hand-written feature row whose feature
   has a file (saving the rows as `<patch-path>.removed`), runs
   `task docs:generate`, `task format` and `task docs:generate` again, checks
   that one more run changes nothing, writes the `git diff` of the changed
   Markdown under `docs/` and `packages/*/docs` that is not on the overlay
   list to `<patch-path>`, prints the files in it, and stops. It resets and
   cleans nothing.
1. Throw the overlay away, apply the patch and commit by path as `S16.3.12`, as
   S16.3.11 does.
1. `docs/_update_board.sh --check` does not pass from here on: its fences are
   gone. The old gate already does not pass after S16.3.11. Step 5 of S16.3.1
   deletes the script.

### Run it

```bash
PATCH="$HOME/pykit-s16.3.12.patch"
bash docs/specs/epics/E16-kiln-adoption/F16.3-cutover/derive.sh "$PATCH"
```

Inspect the files it prints and `"$PATCH.removed"`. Then, one command at a time:

```bash
git reset --hard && git clean -fd
git apply "$PATCH"
git status --short
git commit -m S16.3.12 -- $(git diff --name-only)
```

Inspect `git status --short` before the commit and `git show --stat HEAD` after
it.

**What the replacement loses.** The hand-written epic tables of E6, E9, E10, E12
to E21 carry a `Scope` summary per feature (and E12 a `Trigger` and `Tags`
column) that kiln does not regenerate. `<patch-path>.removed` holds the 75
removed rows. A feature's title in the derived tables is the file's own title,
which can differ from the hand-written row (F6.1's row said "Structured-log
redaction", its file says "Structured-log secret redaction"), and a release's
Scope table shows titles where the old one showed IDs. Epics without feature
files keep their tables.

**Acceptance:**

```bash
set -euo pipefail
absent() { local rc=0; rg -q --hidden --glob '!.git' "$@" </dev/null || rc=$?; [ "$rc" -eq 1 ]; }
absent 'board:start|scope:start' docs/specs/index.md docs/releases/release-*/index.md
grep -qx '<!-- BEGIN derived board -->' docs/specs/index.md
for r in docs/releases/release-*/index.md; do grep -qx '<!-- BEGIN derived scope -->' "$r"; done
for e in docs/specs/epics/E*/index.md; do
  if compgen -G "$(dirname "$e")/F*.md" >/dev/null; then grep -qx '<!-- BEGIN derived features -->' "$e"; fi
done
for f in docs/specs/epics/E*/F*.md; do grep -qx '<!-- BEGIN derived stories -->' "$f"; done
# the commit changes only Markdown under docs/ and packages/*/docs, and no overlay path
test "$(git diff --name-only HEAD~1 HEAD | grep -vcE '^(docs|packages/[^/]+/docs)/.*\.md$' || true)" = 0
test "$(git diff --name-only HEAD~1 HEAD | grep -cxF -f <(sed 's/^...//' "$PATCH.overlay") || true)" = 0
```

## S16.3.1 — Cut over by overlay

**State:** New · **Depends on:** S16.5.3, S16.3.5, S16.3.6, S16.3.11, S16.3.12

The method is an overlay of a reference repository that `kiln new` built. A
repository's nuances live in the repository's own story, not in kiln's logic,
and the repository's git history is kept, which a `kiln new` followed by a copy
of the source would not do. The story copies onto pykit what kiln owns and
applies pykit's own nuances as explicit steps. It also takes the root config as
`kiln new` writes it (steps 3 and 6 to 8).

**The reference** is
`/Users/rohitnarayanan/Devel/workspaces/rn-forge/_reference/pykit` at commit
`c9cc5da`, built by `kiln new` at kiln `c94f5e0` (`feature/v1`) from the input
below: pykit's ten packages, `import_contracts = "own"`,
`[ci] release = "pypi"`, and the `umbrella-release` and `scorecard` checks. The
story only reads it. When kiln changes, the reference is rebuilt from the input
below, this paragraph's commit line is updated, and the "Runs" line is replaced;
nothing else in the story moves.

**The input.** The input of `kiln new` is three files beside this page, in
[`F16.3-cutover/`](F16.3-cutover/):

- [`pykit-new.toml`](F16.3-cutover/pykit-new.toml), the file passed to
  `kiln new --config`: pykit's ten packages, `import_contracts = "own"`,
  `[ci] release = "pypi"`, and the `umbrella-release` and `scorecard` checks.
- [`pykit-deps.sh`](F16.3-cutover/pykit-deps.sh), 41 `uv add` calls that give
  the members pykit's real dependencies and extras.
- [`build-reference.sh`](F16.3-cutover/build-reference.sh), which runs
  `kiln new` with the TOML, then the deps script, `task setup` and
  `task validate`, in the reference directory. It needs kiln checked out clean
  on `feature/v1` next to pykit.

To rebuild the reference, delete the old one and any leftover staging directory
by hand (the script refuses to run while either exists), then run the script:

```bash

  /Users/rohitnarayanan/Devel/workspaces/rn-forge/kiln/.staging/pykit
bash docs/specs/epics/E16-kiln-adoption/F16.3-cutover/build-reference.sh
```

Then commit the reference in its own repository, update the commit lines in "The
reference" above and in step 0, and replace the "Runs" line.

`task validate`, the script's last command, is expected to fail, and only at
`python:lint:imports`, with `No contracts found in the configuration.`: kiln's
block carries no contracts under `import_contracts = "own"`, and pykit's
contracts come below it (step 3). Every other stage passes. A failure anywhere
else means the reference is wrong: stop and rebuild it.

**Rerunning.** The cutover is rerun many times before it merges. A kiln finding
becomes a kiln story. When that story lands, rebuild the reference from "The
input" at the new kiln commit, update the reference line above, then reset the
branch to the S16.3.12 commit and rerun the steps:

```bash
git reset --hard "$(git log -1 --format=%H --grep='^S16.3.12$')"
git clean -fd
```

Rerun S16.3.1 from step 0 to step 16 and replace the "Runs" line. A rerun does
not commit (step 17). Nothing from the earlier run is carried over except the
S16.3.11 and S16.3.12 commits. S16.3.11 is not redone unless kiln's formatter
configuration or pins changed, and S16.3.12 only when kiln's derived regions
change. A difference pykit needs inside a managed file or block is a kiln
finding, never an edit of the copy.

`[kiln] ref = "feature/v1"` until kiln tags `v0.1.0`. The cutover is not merged
before the tag; see the entry criteria above.

**The rule that decides every difference.** The reference's
`.rn-forge/kiln/state.json` says which of kiln's classes each path is in, and
the provenance header or the fence in the file says the same.

| Class | What it is | What the overlay does |
| -- | -- | -- |
| Managed | The whole file is kiln's, with a provenance header, in `state.json` as `managed` | Copied from the reference, byte for byte. pykit never keeps a variant. |
| Managed block | A fenced region of a repository file (`AGENTS.md`, `.gitignore`, `.importlinter`) | The block is copied from the reference, byte for byte; pykit's text around it stays. |
| Seeded | Written once, then the repository's (`seeded` in `state.json`) | pykit's content wins where it is pykit's own work (docs pages). Configuration the reference shows kiln-shaped is taken from the reference. |
| Repository-owned | In neither list | pykit's content wins. Where it is configuration that kiln shapes, it is aligned to the reference, and each pykit nuance on top is one step below. |

If pykit needs something different in a managed file or block, the story does
not do it: it is a kiln finding (config or code), and the file stays the
reference's.
