# F19.1 — How packages find each other by version

|  |  |
| -- | -- |
| **State** | New |
| **Parent** | [E19](index.md) |
| **Iteration** | [Release 6](../../../releases/release-6/index.md) |

| **Source** | Owner request, 2026-10-24 |

A version range needs somewhere to look a version up, which a git URL cannot
offer. This feature settles where that is, what a range between two pykit
packages looks like, and how [ADR-0004](../../../adr/ADR-0004.md) changes.

## Design

**Proposed: a static PEP 503 simple index on GitHub Pages.**

- Every release already uploads its wheel and sdist to its GitHub Release (the
  `release` job's `gh release create`).
- A static index at `https://rn-forge.github.io/pykit/simple/` lists those
  files, with one page per project and links to the release assets carrying
  `#sha256=` fragments.
- The docs job, which already deploys Pages after `release`, writes it
  ([F19.2](F19.2-package-index.md)).

Nothing new is hosted: the files stay where they are, and the index is HTML in
the Pages artifact.

**Ranges.** An internal requirement names a distribution and a range, never a
URL: `rn-forge-commons[pydantic]>=0.7.0,<0.8`.

- **The floor** is the dependency's version the dependent was released against.
- **The ceiling** is the dependency's next breaking version. Before 1.0 that is
  the next minor, because a minor carries breaks (commons 0.6.0, tooling 0.3.0).
  From 1.0 on it is the next major.
- **The bump follows from it.** Before 1.0, a release with a breaking change
  bumps the minor, and any other release bumps the patch. pykit has bumped the
  minor for additive releases (`rn-forge-devops` 0.2.0); under this rule that
  would cross every dependent's ceiling and force the re-tags ranges remove.

**The workspace** keeps `[tool.uv.sources] <sibling> = { workspace = true }`
for development. Those sources do not reach a built wheel, so a wheel's
metadata carries the ranges alone.

**A consumer** that wants ranges declares the index once:

```toml
[[tool.uv.index]]
name = "rn-forge"
url = "https://rn-forge.github.io/pykit/simple/"
```

uv's default `first-index` strategy searches a declared index before PyPI and
stops at the first index that has the name. An `rn-forge-*` name therefore
always resolves from pykit's index, and a package of that name on PyPI is never
considered. pip's `--extra-index-url` merges indexes, which allows exactly that
substitution, so the guide recommends uv and states the risk for pip.

**ADR-0004, revised in place** with a dated Background sentence:

- *Decision* keeps "each package has its own version and a tag named for it".
- It replaces "Consumers declare package dependencies as pinned Git direct
  URLs" with: *Packages declare each other by name and version range, floor at
  the version released against and ceiling at the next breaking version (the
  next minor before 1.0). pykit publishes a PEP 503 index of its GitHub Release
  files at `https://rn-forge.github.io/pykit/simple/`. A consumer may declare
  that index and use ranges, or pin a tag by direct URL, as before.*
- It drops the interim branch-pin paragraph, which ended at release-1.
- *Decision* gains the bump rule: before 1.0, minor for a breaking change and
  patch otherwise; from 1.0, semantic versioning.
- *Consequences* gains: an additive release needs no release of its dependents;
  a breaking release needs each dependent to widen its ceiling.
- *Alternatives considered* gains the two options under *Considered and
  rejected* below.

## Stories

### S19.1.1 — Decide the index and the range rule, and revise ADR-0004

**State:** New

**Acceptance:**

- The owner accepts the design above, or picks PyPI (see below).
- ADR-0004 is revised as described, with
  `**Status:** accepted (2026-09-10), revision accepted (<date>)`.
- If PyPI is chosen instead, F19.2 is `Removed` and replaced by a feature that
  publishes to PyPI from the `release` job.

## Considered and rejected

- **Publish to PyPI.** It is the simplest for consumers: no index to declare,
  and no confusable name. But it changes where pykit lives, needs a PyPI
  project per package and trusted publishing set up per package, and makes
  every package public on PyPI's terms. It stays the fallback if the owner
  prefers it, and would remove the index.
- **A hosted private index** (devpi, a cloud artifact registry). It brings a
  server or an account to keep alive for files that GitHub already hosts.
- **GitHub Packages.** It has no Python registry.
- **A flat `--find-links` page.** uv and pip both read it, but it is not a
  standard index: a consumer cannot scope it to `rn-forge-*` the way an index
  entry plus `first-index` can.
- **Reserving the `rn-forge-*` names on PyPI as empty placeholders.** It guards
  pip users, but it is a squat on a public index; the guide's advice to use uv
  covers the risk.
