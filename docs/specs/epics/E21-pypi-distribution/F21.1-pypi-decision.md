This feature records the distribution decision in
[ADR-0004](../../../adr/ADR-0004.md) and has the owner set up the PyPI side, so
CI can upload.

## Design

The owner accepted these on 2026-10-26 ([E21](index.md#context)); the settled
rules (publish to PyPI by trusted publishing, no index declaration, immutable
versions, tags and umbrella releases) are in
[ADR-0004](../../../adr/ADR-0004.md), and the upload workflow is in the
[release runbook](../../../runbooks/releasing-packages.md).

- **Ownership.** The projects belong to the PyPI organization
  [`rn-forge`](https://pypi.org/org/rn-forge/), approved 2026-10-28. Pending
  publishers are added on the owner's account, so each project is created
  there by its first upload and then added to the organization
  ([S21.3.3](F21.3-publish-from-release.md#s2133-first-pypi-release-and-the-umbrella)).
  The test.pypi.org projects stay on the owner's account; TestPyPI has no
  `rn-forge` organization.
- **Licence.** MIT ([F21.2](F21.2-package-metadata.md)).

## S21.1.2 — The PyPI projects can accept uploads from CI

**State:** Closed

The owner completes these steps; none of them can be scripted:

1. Make the owner's membership of the `rn-forge` GitHub organization public.
1. Link the owner's PyPI and GitHub accounts under PyPI's *Account
   associations*.
1. Tell PyPI staff both are done, and correct the organization request's URL to
   `https://github.com/rn-forge`.
1. Create the GitHub environments in `rn-forge/pykit`:
    - `pypi`, with a deployment branch policy allowing only `main`;
    - `testpypi`, with no branch policy, so the dry run can run from a release
      branch.

The trusted publishers are not part of this story. The workflow cannot create a
project, so the owner creates each project and attaches its publisher before the
first publish
([F21.3](F21.3-publish-from-release.md#registering-the-publishers)).

**Acceptance:**

- Both environments exist, and `pypi` allows only `main`.
- The owner's membership is public.
