# S32.2.2 — Migrations into a named schema

Brief for
[S32.2.2](../F32.2-alembic-env-helper.md#s3222-migrations-into-a-named-schema),
written at the S32.2.1 and S32.1.3 merges on `feature/release-12`. Read the
feature's Design first. `schema` is settled there.

## Goal

`run_migrations(..., schema=...)` upgrades a PostgreSQL database inside a named
schema, with `alembic_version` in that schema too. This is how an application
tests its migrations on `postgres_schema`.

## Settled

- **`run_migrations`** in
  `packages/rn-forge-sqlalchemy/src/rn_forge/sqlalchemy/migrate.py` gains the
  keyword-only `schema: str | None = None`, after `revision`.
    - When `schema` is not `None`, validate before building the `Config` or
      touching any database.
    - `schema == ""` raises `ValueError("schema must not be empty")`.
    - If `make_url(db_url).get_backend_name() != "postgresql"`, raise `ValueError`
      naming the backend, for example
      `"schema needs a PostgreSQL URL, got 'sqlite'"`.
    - Then set `config.attributes["schema"] = schema`.
    - Docstring: add `Args:` and `Raises:` entries.
- **`run_env`,** inside `_configure_and_run`, when
  `config.attributes.get("schema")` is set, follows Alembic's own multi-tenant
  recipe:
    1. `connection.exec_driver_sql(f'SET search_path TO "{schema}"')`, then
       `connection.commit()`, so the setting survives Alembic's transaction.
    1. `connection.dialect.default_schema_name = schema`.
    1. `options["version_table_schema"] = schema`, set before `**configure` is
       applied, so the caller's keywords still win.
    - The docstring mentions the schema.
- **Usage guide:**
    - In `### env.py`, or a new `### Migrating into a schema` subsection, cover:
      `schema=` on `run_migrations`; PostgreSQL only, with a `ValueError`
      otherwise; tables and `alembic_version` land in that schema; the schema
      must already exist.

    - Give the per-test example:

        ```python
        def test_migrations_reach_head(postgres_schema):
            run_migrations("myapp:migrations", postgres_schema.url, schema=postgres_schema.name)
        ```

        Note that it is sync, or uses `asyncio.to_thread` from an async test.
- **Changelog:** add to `CHANGELOG.md` `## [0.2.5]` `### Added`:
  "`run_migrations` takes `schema`, to upgrade a PostgreSQL database inside a
  named schema." Do not bump the version.

## Current behaviour

`run_migrations(..., schema="x")` raises
`TypeError: run_migrations() got an unexpected keyword argument 'schema'`. Each
new test fails with that error.

## Change

1. Write the tests below first, and confirm the `TypeError`.
1. Make the `run_migrations` and `run_env` changes, then the docs and the
   changelog.

## Tests first

Add these to `packages/rn-forge-sqlalchemy/tests/test_migrate_env.py`, reusing
its script-directory helper, whose `env.py` calls `run_env`. The plugin is
loaded by `tests/conftest.py`, so `postgres_schema` is available. The revisions
create unqualified tables (`CREATE TABLE one (id INTEGER)`), so they land in the
search path.

- `test_run_migrations_into_schema`, marked `postgres`: run
  `run_migrations(scripts, postgres_schema.url, schema=postgres_schema.name)`
  through `asyncio.to_thread` from an async test, or directly from a sync
  test. Over `postgres_schema.engine`, `information_schema.tables` shows
  `one`, `two` and `alembic_version` with
  `table_schema == postgres_schema.name`, and none of them in `public`.
- `test_run_migrations_into_schema_twice_changes_nothing`, marked `postgres`:
  two upgrades leave `SELECT version_num FROM "<schema>".alembic_version` with
  one row, the head.
- `test_run_migrations_schema_rejects_sqlite`, unit: `schema="x"` with a SQLite
  URL under `tmp_path` raises `ValueError` matching `sqlite`, and the database
  file does not exist afterwards.
- `test_run_migrations_rejects_empty_schema`, unit: `schema=""` raises
  `ValueError`.
