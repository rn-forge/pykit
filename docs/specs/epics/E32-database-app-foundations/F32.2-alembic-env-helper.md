An application's `env.py` becomes one call, `run_env(target_metadata)`, in place
of the thirty lines it copies from the usage guide today, and `run_migrations`
can upgrade into a named PostgreSQL schema, which is how an application tests
its migrations on a per-test schema.

## Context

The usage guide's `env.py` (*Embedded migrations*) is boilerplate every
application copies: the `configure_logger` check, an async engine with
`NullPool`, `asyncio.run` and `render_as_batch`. It passes no `target_metadata`,
so autogenerate finds nothing until the application edits it. Running migrations
into a schema other than the server default needs `search_path` on the
connection and `version_table_schema`, which a copied `env.py` has to work out
alone.

The predecessor is F32.1: S32.2.2's tests run on its fixture.

## Design

**`rn_forge.sqlalchemy.migrate.run_env(target_metadata, **configure)`**, called
from an application's `env.py`:

```python
from rn_forge.sqlalchemy.migrate import run_env
from myapp.db.models import Base

run_env(Base.metadata)
```

- It reads `context.config`, calls `fileConfig` only when a config file is set
  and `config.attributes.get("configure_logger", True)` is true.
- Online mode only: it builds an async engine from the config's `sqlalchemy.`
  options with `NullPool`, connects, and runs the migrations through
  `connection.run_sync` inside `asyncio.run`. Offline mode
  (`alembic upgrade --sql`) raises `NotImplementedError` naming it.
- It passes `target_metadata` to `context.configure`, with `render_as_batch`
  true on SQLite and false otherwise. Keyword arguments in `configure` are
  passed through to `context.configure` and win over these defaults.

**`run_migrations(..., schema: str | None = None)`** stores the schema in
`config.attributes["schema"]`. When it is set, `run_env` sets the connection's
`search_path` to that schema before configuring, and passes
`version_table_schema=schema`. A schema on a non-PostgreSQL URL raises
`ValueError` before any connection is made.

## S32.2.1 — `run_env`

**State:** Closed (2026-11-22)

**Acceptance:**

- `rn_forge.sqlalchemy.migrate` defines and exports `run_env` as in the Design.
- `test_run_env_reaches_head`: a script directory whose `env.py` is the two
  lines in the Design upgrades a SQLite database to head through
  `run_migrations`.
- `test_run_env_leaves_root_logger_alone`: with an `alembic.ini` passed to
  `run_migrations`, the root logger's handlers and level are unchanged.
- `test_run_env_passes_target_metadata`: `alembic.command.revision` with
  `autogenerate=True` against an empty SQLite database writes a revision that
  creates the metadata's table.
- `test_run_env_offline_raises`: `alembic.command.upgrade` with `sql=True`
  raises `NotImplementedError`.
- `test_run_env_configure_overrides_default`:
  `run_env(metadata, render_as_batch=False)` on SQLite reaches
  `context.configure` with `render_as_batch=False`.
- The usage guide's `env.py` section shows `run_env` in place of the copied
  module, and says the stock Alembic template is replaced, not extended.

## S32.2.2 — Migrations into a named schema

**State:** New · **Depends on:** S32.2.1

**Acceptance:**

- `run_migrations` takes `schema` as in the Design.
- `test_run_migrations_into_schema` (marked `postgres`): upgrading into
  `postgres_schema.name` creates the revision's table and `alembic_version` in
  that schema, and neither in `public`.
- `test_run_migrations_into_schema_twice_changes_nothing` (marked `postgres`): a
  second upgrade into the same schema leaves the head revision unchanged.
- `test_run_migrations_schema_rejects_sqlite`: a `schema` with a SQLite URL
  raises `ValueError`, and no database file is created.
- The usage guide documents `schema`, with the per-test example using
  `postgres_schema`.
