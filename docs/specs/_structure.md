# specs/ — what belongs here

## Belongs here

- Work to do, or a record of work done, as an epic, a feature or a story — done work
  included, so the tree is the inventory of what this repo is made of.
- Design for work not yet built.
- Ideas not yet agreed as work.

## Does not belong here

| Instead of | Put it in |
| -- | -- |
| Behaviour that already exists | `architecture/` |
| A decision | an ADR under `adr/` |
| Which features ship in which release | `releases/` — it links here |
| History and evidence | the commit message |
| A `progress.md`, `decisions.md` or `overview.md` | the epic, an ADR, or the README |

## File types

### Board — `specs/index.md`

Purpose: the single page that answers what ships in which release and what is on no
release yet. It is the current-status entry point.

Path and naming: `specs/index.md`, one per repository.

Belongs / does not belong:

- The `<!-- board:start -->` … `<!-- board:end -->` region is generated by
  `docs/_update_board.sh` from the epic and release pages, and must not be edited by
  hand.
- A retired epic gets a line here, in prose, naming what replaced or absorbed it. A
  retired feature keeps its row on its own epic's page with State `Removed` instead
  ([IDs and state vocabulary](#ids-and-state-vocabulary)).
- Ideas not yet agreed as work are linked from here, not listed here; they live in
  `ideas.md`.

Template:

```markdown
# <Repo> work

<one paragraph: what this page is, and that the generated region must not be hand-edited>

<!-- board:start -->
<!-- generated by docs/_update_board.sh: do not edit -->
<!-- board:end -->

<!-- optional: a retired epic, in prose, and what replaced it -->

Ideas not yet agreed as work are parked in the [ideas list](ideas.md).

## Conventions

<the short form of this file's rules, for a reader who will not open it>
```

### Epic — `epics/E<n>-<slug>/index.md`

Purpose: everything known about one epic — its features, or, for a pre-taxonomy epic,
the commits that delivered it.

Path and naming: `epics/E<n>-<slug>/index.md`. `E<n>` is permanent.

Belongs / does not belong:

- A done epic whose work predates this taxonomy, its specs written after the code,
  keeps its features as rows in its own table with a `Commits` column instead of
  linking to feature files ([E1](epics/E1-foundation-and-boundaries/index.md) is an
  example).
- `## Considered and rejected` and `## Open questions` are optional, and appear in
  that order when both are present.

Template:

```markdown
# E<n> — <Title>

| | |
| --- | --- |
| **State** | New \| Active \| Closed \| Removed |
| **Tags** | deferred                            <!-- optional -->
| **Start Date** | <date>                        <!-- required when State is Active or Closed -->
| **Closed Date** | <date>                       <!-- required iff State is Closed -->
| **Entry criteria** | <short phrase>             <!-- required iff tagged deferred -->

<one-paragraph summary of the epic's scope>

[Back to the work index](../../index.md)

| Feature | Scope | State |
| --- | --- | --- |
| [F<n>.<m> — <Title>](F<n>.<m>-<slug>.md) | <what it delivers> | <state> |

<!-- optional: cross-references, the ADRs that govern the epic -->

## Considered and rejected     <!-- optional -->

- <a rejected option, and why>.

## Open questions              <!-- optional -->

- <a question the epic blocks on>.
```

### Feature — `epics/E<n>-<slug>/F<n>.<m>-<slug>.md`

Purpose: one deliverable within an epic. A feature file, once written, stays when its
work is done.

Path and naming: `F<n>.<m>-<slug>.md`, beside its epic's `index.md`.

Belongs / does not belong:

- `**Source**`, when present, cites a current document, or the owner decision and its
  date.
- Release assignment lives only on the feature's `Iteration` field; the release page's
  Scope table is generated from it ([releases/_structure.md](../releases/_structure.md)).
- Reasoning behind a `Source`, `Predecessors` or `Entry criteria` value that will not
  fit the table cell goes in `## Context`, not in the cell.

Template:

```markdown
# F<n>.<m> — <Title>

| | |
| --- | --- |
| **State** | New \| Active \| Closed \| Removed |
| **Parent** | [E<n>](index.md) |
| **Iteration** | [Release <r>](../../../releases/release-<r>/index.md)  <!-- required when State is Active; optional otherwise -->
| **Tags** | deferred                            <!-- optional -->
| **Start Date** | <date>                        <!-- required when State is Active or Closed -->
| **Closed Date** | <date>                       <!-- required iff State is Closed -->
| **Predecessors** | <IDs, links, or "—"> |
| **Source** | <short citation>                  <!-- optional (when present) -->
| **Entry criteria** | <short phrase>             <!-- required iff tagged deferred -->

<one-paragraph summary>

## Context                     <!-- optional: reasoning behind a table cell, or trigger/background -->

## Design                      <!-- optional: design for what this feature builds -->

## Stories

### S<n>.<m>.<k> — <Title>

**State:** New

**Acceptance:** <criteria>

## Acceptance                  <!-- required when there are two or more stories -->

## Considered and rejected     <!-- optional -->

## Open questions              <!-- optional -->
```

### Story — inline `### S<n>.<m>.<k>` heading, or its own file

Purpose: one acceptance-checked unit of work inside a feature.

Path and naming: a `### S<n>.<m>.<k> — <Title>` heading inside its feature file. Give a
story its own file only when its acceptance runs past about a screen.

Belongs / does not belong: a story keeps its single `**State:**` line and
`**Acceptance:**` list or block — it is never tableized like an epic, feature or
release. A story maps to an ADO User Story; call it "story" in prose.

Template:

```markdown
### S<n>.<m>.<k> — <Title>

**State:** New \| Active \| Closed (<date>) \| Removed

**Acceptance:** <the observable result, or a list of them>
```

### Epic design — `epics/E<n>-<slug>/design.md`

Purpose: design for work not yet built that spans more than one feature. Design for a
single feature stays in that feature's `## Design` instead.

Path and naming: `design.md`, beside the epic's `index.md`.

Belongs / does not belong:

- A working proposal: nothing in it is decided until it becomes an ADR or a feature.
- `**Settled by**` names the feature that settles the design into ADRs and
  implementation features.

Template:

```markdown
# E<n> — <Title> design

| | |
| --- | --- |
| **Epic** | [E<n>](index.md) |
| **Settled by** | [F<n>.<m>](F<n>.<m>-<slug>.md)   <!-- optional -->
| **Depends on** | <ADR link(s)>                    <!-- optional -->

<one paragraph: what this design covers, and that nothing is decided until it becomes
an ADR or a feature>

[Back to E<n>](index.md)

## <design sections, as the design needs>

## Considered and rejected     <!-- optional -->

## Open questions              <!-- optional, or kept on the settling feature instead -->
```

### Ideas — `ideas.md`

Purpose: ideas not yet agreed as this repository's work.

Path and naming: `specs/ideas.md`, one per repository.

Belongs / does not belong:

- An idea takes no ID and no status, and does not authorize starting work.
- Promoting an idea moves its section into the new epic or feature file and deletes
  its row; a dropped idea's row is deleted too.

Template:

```markdown
# Ideas

<one paragraph: what this page is, and that an entry does not authorize work>

[Back to the work index](index.md)

| Idea | Summary | Source |
| --- | --- | --- |
| [slug](#slug) | <one-line summary> | <source, or where it was retired from> |

## slug                        <!-- optional: only when there is more to record -->

<detail>
```

## IDs and state vocabulary

This maps 1:1 to Azure DevOps's Agile process, so the templates port directly: Epic and
Feature keep their names; a story maps to a User Story. See [Tracker
mapping](#tracker-mapping) for the field-by-field correspondence.

- IDs are permanent: never renumber; a moved story keeps its ID. Gaps are fine.
- Work no longer needed is retired in place, never deleted and never renumbered: a
  retired story's heading, a retired feature's row in its epic's feature table, and a
  retired epic's line on the board all stay, with State `Removed` and one line saying
  why.
- An epic's feature table, and a release's generated Scope table, share one column
  shape: the feature first (`Fn.m — Title`, linked to its file when one exists; a row
  for a done pre-taxonomy epic or an unelaborated deferred item, which may have no
  file, shows the bare ID instead, with no title or link), then a `Scope` column
  describing the work, then any epic-specific column the table needs (`Commits`,
  `Trigger`, `Entry criterion and disposition`), then `State` last. Prefer `Scope` over
  other names (`Work`, `Delivered`, `Item`) for the description column unless an
  epic's column means something genuinely distinct.
- A bare `**State:**` line appears only on a story; an epic, feature or release
  carries its state (or, for a release, its `Status`) in the metadata table at the top
  of the page instead.
- The metadata table at the top of an epic, feature or release page uses only that file
  type's allowed keys, in the fixed order its template gives, with no duplicates: a key
  that does not apply is omitted, never left blank. A value is short — a state word, a
  date, an ID, a link, or a short phrase — with no trailing period and no commit hash;
  `—` means none. `docs/_update_board.sh` validates this shape on every epic, feature
  and release page.
- Epic and feature state is one of these — the ADO Agile standard, minus `Resolved`,
  which ADO offers but is never used — and `index.md`'s Releases and
  Backlog sections, and each release page's Scope table, are generated from the epic
  and feature pages by `docs/_update_board.sh`:

| State | Means |
| -- | -- |
| `New` | Agreed, not yet started. Untagged and with no `Iteration`, its stories or design are not yet settled (formerly "elaborating"). Tagged `deferred`, it is not scheduled (formerly "deferred"), and carries an `**Entry criteria**` row. With an `Iteration` and no `deferred` tag, its stories are written and it is on a release (formerly "planned"). |
| `Active` | At least one story started; carries a `**Start Date**` row and, for a feature, an `**Iteration**` row. |
| `Closed` | Every story's acceptance holds; carries `**Start Date**` and `**Closed Date**` rows (formerly "done"). Means implemented, not released — the release pages record what shipped. |
| `Removed` | Retired: no longer needed. Stays in place with one line saying why. |

- A feature's `Iteration` field is the single source of truth for release assignment;
  a release page's Scope table is a generated region built from it, never hand-edited
  ([releases/_structure.md](../releases/_structure.md)).
- Story state is `New`, `Active`, `Closed (<date>)` or `Removed`. A story in a
  feature or epic tagged `deferred` is `New`, inheriting the deferral from its
  parent's tag.

## Tracker mapping

These specs are a lightweight, file-based stand-in for an Azure DevOps (Agile
process) backlog. A migration maps directly, field by field:

| Docs | ADO |
| -- | -- |
| Epic / Feature / Story | Epic / Feature / User Story, linked by `Parent` |
| `E<n>` / `F<n>.<m>` / `S<n>.<m>.<k>` prefix | Work item title prefix |
| Release | Iteration Path |
| `State`: New, Active, Closed, Removed | Same (ADO's `Resolved` is unused) |
| `Tags: deferred` | Tags |
| `Entry criteria`, `Source` | Custom fields |
| `Predecessors` | Predecessor links |
| `Acceptance` | Acceptance Criteria |
| `design.md`, ADRs, `architecture/`, `guides/`, `runbooks/`, release pages | Stay in the repo; published to the ADO wiki as a code wiki |
| `ideas.md` | Stays in the repo; not agreed work, so never a work item |
| Commit subjects naming an ID | `AB#<id>` commit links |

## Writing acceptance

- Each line is an observable result, and the tests that prove a story belong in
  its acceptance, not in a story of their own.
- A decision the work needs is its own story, so other work can depend on the
  decision without depending on its implementation.
- A feature with several stories has a `## Acceptance` block that exercises
  every story, each line tagged with the story it proves; a one-story feature
  keeps its acceptance on the story. What cannot be scripted, such as an
  approval, is listed under the block.
- The block fails loudly: `set -euo pipefail`, never `|| echo`, and negative
  checks through these helpers rather than a bare `! cmd`, which `set -e`
  ignores:

```bash
absent() { local rc=0; rg -q --hidden --glob '!.git' "$@" </dev/null || rc=$?; [ "$rc" -eq 1 ]; }
fails_with() { local out rc=0; out=$("${@:2}" 2>&1) || rc=$?; [ "$rc" -ne 0 ] && grep -qF -- "$1" <<<"$out"; }
```

**Checking removed behaviour:** a check that a removed symbol is gone asks "does
any current page describe it as present?", not "does the name appear?". A page
may name removed behaviour to say it is gone.

## Lifecycle

**Parking an idea:** add a row to `ideas.md`, and a section linked from the
row if it needs more than a line. Do not elaborate an idea unless the
owner asks. A dropped idea is deleted.

**Adding an epic or a feature:**

1. Take the next free ID. Never renumber a sibling. An idea promoted from
   `ideas.md` carries its section into the new file, and its entry is deleted.
1. Create `epics/E<n>-<slug>/index.md` with its state: `New` while it has no
   stories or is not yet scheduled, tagged `deferred` with entry criteria when
   it is not scheduled and should not be started.
1. Write one feature file per feature, stories inline. Give a story its own file
   only when its acceptance runs past about a screen.
1. Put design at the lowest level that fits: the feature's `## Design`; the
   epic's `design.md` when it spans features; a link to `architecture/` when
   it describes current behaviour.
1. Run `docs/_update_board.sh` and `task docs:nav`.

**Working on and closing out work:**

1. Starting: flip the feature, and the epic, to `Active`, with a `Start Date`;
   set the feature's `Iteration` to its release.
1. A story is `Closed (<date>)` when its acceptance holds; run the feature's
   acceptance block, then flip the story's state.
1. When every story is closed, the feature is `Closed` with its `**Closed
   Date**` row; its `Iteration` stays if it shipped on a release. When every
   feature is closed, the epic is `Closed` with its `**Closed Date**` row and
   the acceptance as run. Closed work is never deleted.
1. An answered open question becomes an ADR, or a rejected option recorded on
   the feature under *Considered and rejected*; the question is then removed.

**Deferred work:** do not start or elaborate an epic or feature tagged
`deferred` unless the owner asks. When its entry criteria hold, drop the
`deferred` tag and the `Entry criteria` row; set `Iteration` once it has a
release. Nothing renumbers.

**Retiring work:** a story, feature or epic no longer needed becomes `Removed`
in place — its heading, feature row or board line stays, with one line saying
why. Drop the `**Retired**` metadata row this replaced.

**The board:** after changing a feature's state or `Iteration`, run
`docs/_update_board.sh` to regenerate the board's Releases and Backlog
sections and each release page's Scope table, and to validate every epic,
feature and release page's metadata table (allowed keys, order, no
duplicates, a valid state, `Closed Date` present iff `Closed`, `Entry
criteria` present iff tagged `deferred`, `Iteration` present iff `Active`, an
`Iteration` pointing at a release page that exists); `--check` is the CI
form, and fails when either generated region is stale or the specs are
inconsistent.

## Other repositories

- Every acceptance line is checkable inside this repository. When acceptance
  needs a host, such as an application or a library workspace, a test builds
  one in a temporary directory.
- A dependency on another repository's software is a version or git pin in the
  manifest of the code that uses it, plus at most an entry criterion that can
  be observed from outside that repository ("its release-1 tags exist").
- Another repository's pages, paths, spec IDs and internal status are not cited
  or restated. A requirement or finding that came from elsewhere is written
  here in full, as this repository's own.
- No page here is written for another repository to cite.
